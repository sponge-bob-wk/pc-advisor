## 1. 背景与问题定义

### 1.1 已有资产做到了什么

现有工具是一个单文件 HTML，已经解决了几件事：

- **价格不是拍脑袋**：到手价含国补，标注「页面价」的单独区分
- **CPU 分可追溯**：走 Cinebench R23 双锚点换算，手改分数构建直接失败
- **国补分类算**：电脑归家电类，15% 立减、单台封顶 1500、无价格门槛
- **不适用维度退场**：内存条没有 CPU，性能存 `null` 并从加权摘除，不判 0 分
- **优缺点强制成对**：缺 `pros` 或 `cons` 构建失败

数据纪律是好的。问题在交互形态，以及**两个还没补上的维度**。

### 1.2 六个结构性缺口

| 缺口 | 现状 | 后果 |
|---|---|---|
| **性能分没有 GPU** | 只有 Cinebench R23 | 游戏本的核心指标缺失，天选 7（RTX 5050）和核显轻薄本拉不开 |
| **性能分只有一种负载** | 只有 R23 持续渲染 | 轻薄本被系统性低估 8~13 分，而准大学生用的正是轻薄本 |
| **入口门槛太高** | 必须先自选品类、填预算、选侧重 | 说不清需求的人用不了 |
| **只回答被问到的** | 用户不问「宿舍限电吗」，就不提 | 准大学生不知道自己该问什么，这是致命的 |
| **不能应对家长** | 只给学生看 | 出钱的人看不到理由，决策推不动 |
| **数据是死的** | 2026-11 快照 | 三个月后这份榜单就是误导 |

### 1.3 最关键的一条：用户不知道自己该问什么

这是本产品与「筛选器」的根本分界。

> 一个准大学生不会问：「我宿舍限电吗？这影响我能不能买游戏本吗？」
> 他只会问：「8000 块买什么电脑好？」
>
> 而「宿舍限电」这个信息，能直接决定游戏本能不能进候选集。

**智能体的核心价值不是回答得更好，是替用户问出他想不到要问的问题。** 这条贯穿全文，具体机制见 §3.4。

## 2. 产品定位

### 2.1 是什么

**一个决策陪跑者 + 一个翻译器**：把学生的模糊需求问清楚，把技术参数翻译成家长能听懂的话，把购买路径铺到最后一步。

### 2.2 不是什么

| 不做 | 理由 |
|---|---|
| **不做手机** | 维度体系不同（mAh vs 续航小时、影像主观分），混一套权重会互相污染 |
| 不做导购带货 | 有返佣就会扭曲推荐 |
| 不让 LLM 排序 | 排序必须走确定性引擎，见 §7 |
| 不做全品类比价 | 只覆盖 4 个电脑品类，做深不做宽 |
| 不预测价格走势 | 内存周期有共识但拐点不可预测，只给历史与现状 |
| 不做二手估价 | 成色无法结构化 |
| **不替学生做决定** | 给候选、给理由、给缺点，最后一步让人自己走 |

### 2.3 三层架构

```
┌─────────────────────────────────────────────┐
│  智能体层（LLM）                             │
│  理解需求 · 主动提问 · 调工具 · 翻译成人话    │
└───────────────┬─────────────────────────────┘
                │ 只调用，不重算
┌───────────────▼─────────────────────────────┐
│  决策引擎层（确定性代码）                     │
│  排序 · 分档 · 三把尺子加权 · 国补 · 退场     │
└───────────────┬─────────────────────────────┘
                │ 只读
┌───────────────▼─────────────────────────────┐
│  数据层（prices.json + sources）              │
│  22 条机型 · 13 条来源 · 构建期校验           │
└─────────────────────────────────────────────┘
```

HTML 不废弃，降级为**渲染层**：智能体把候选集渲染成可分享的静态页。这个页面有一半是给家长看的。

## 3. 目标用户：准大学生

### 3.1 这个群体的四个特殊性

| 特殊性 | 具体表现 | 对产品的含义 |
|---|---|---|
| **信息盲区最大** | 不知道专业要什么软件、不知道宿舍条件、不知道要不要带去教室 | 必须主动问，不能等他问 |
| **决策不是一个人** | 父母出钱、学长给建议、B站给评测 | 输出要能同时说服三类人 |
| **一次性大额支出** | 5000~10000，普通家庭一个月收入 | 错了不是换一台，是四年难受 |
| **时间窗极窄** | 8 月中到 9 月初集中买 | 决策周期短，容错低 |

### 3.2 决策链：三个人，三种语言

```
学生 ──（提需求）──▶ 智能体 ──（讲理由）──▶ 家长
  ▲                                            │
  └──────────（钱）─────────────────────────────┘

学长 / B站评测 ──（干扰项）──▶ 学生
```

| 角色 | 关心什么 | 需要什么语言 |
|---|---|---|
| **学生** | 能不能打游戏、好不好看、够不够快 | 「这个能跑 60 帧」「开 20 个网页不卡」 |
| **家长** | 为什么这么贵、能用几年、坏了怎么办 | 「四年不用换」「全国联保」「比同配置便宜 800」 |
| **学长** | 参数、跑分、避坑 | 「R23 多核 15475」「留了内存插槽」 |

**同一个推荐要能切换三种说法。** 这是 v0.3 新增的硬要求：回答里同时给「一句话结论」+「给家长的说法」+「可核对的数字」。

### 3.3 痛点清单（12 条，按时间分三段）

#### 买之前

| # | 痛点 | 真实场景 | 严重度 |
|---|---|---|---|
| P1 | **专业没定，怕买错** | 大一大二有转专业可能，买了文科本结果要跑 CAD | ★★★★★ |
| P2 | **不知道该信谁** | 学长推荐的都是自己买的（确认偏误），B站评测多恰饭 | ★★★★★ |
| P3 | **预算被内存涨价吃了** | 2026 年 DRAM 暴涨，同样 5000 块今年只能买去年 4000 的配置 | ★★★★☆ |
| P4 | **说不清为什么多花 2000** | 家长只看到价格，看不到「多核高 60%」的意义 | ★★★★☆ |
| P5 | **品类名是黑话** | 「轻薄本 / 全能本 / 游戏本」对他是三个陌生词 | ★★★☆☆ |

### 3.4 「入学前必问五问」——本产品的核心机制

**这五个问题，准大学生自己想不到问，但每一个都能改变推荐结果。** 智能体必须在合适时机主动提出来。

| # | 问题 | 答案如何改变推荐 | 触发时机 |
|---|---|---|---|
| Q1 | **专业定了吗？要跑什么软件？** | 文科/商科 → `daily` 侧重；设计/建筑 → `work` + GPU；计算机 → 大内存 + `work` | 用户说「办公」「学习」时 |
| Q2 | **宿舍限电吗？大概多少瓦？** | 限 500W → 游戏本降权或直接排除；不限 → 正常推 | 用户提到「游戏本」或「打游戏」时 |
| Q3 | **要带去教室/图书馆吗？** | 要 → `carry` 权重上升，续航进维度；不要 → 便携降权 | 用户说「宿舍用」时反向确认 |
| Q4 | **寒暑假带回家吗？** | 带 → 重量硬约束（>2.3kg 要警告）；不带 → 放开 | 用户是外地生源时 |
| Q5 | **四年内打算换吗？** | 不换 → `upgrade` 权重显著上升 + 主动查设计缺陷 | 用户说「能用久一点」时 |

**问法要求：每次最多问一个，且必须先给一个答案再问。**

反例：
> 「请问您的专业、宿舍功率限制、是否携带、预算范围？」

正例：
> 「先按 6000 上下的全能本来：无界 14X 是这批里唯一既留内存插槽、又用 R7 H255 的。不过你要是学设计要跑 PS/PR，显卡这块得再看 —— 你专业定了吗？大概要跑什么软件？」

### 3.6 采购时间窗（观察，非承诺）

| 时间 | 状态 | 建议 |
|---|---|---|
| 6 月（高考后） | 了解期 | 别急着买，先定专业方向 |
| 7 月 | 比价期 | 关注历史价，建立候选集 |
| 8 月中~9 月初 | **需求高峰，价格偏硬** | 刚需可买，非刚需可等 |
| 10~11 月 | 双 11，常见回落 | **性价比窗口** |
| 次年 3 月 | 开学季小高峰 | 次选 |

**这一条标注为「观察」，不写成承诺。** 内存周期有共识但拐点不可预测，说「一定会降」就是编造。

对 8 月已买的学生，正确说法是：「你买的时候是需求高峰，这个时间点价格通常偏硬。如果还能退，现在（11 月）可以看看；如果已经用了两个月，不建议为几百块折腾。」

### 3.7 用户画像（用于 prompt 设计）

**典型用户 A：小镇做题家，预算 5500**
- 家在县城，父母是普通工薪，5500 是咬牙出的
- 专业：计算机（已定），要跑虚拟机、写代码
- 宿舍：6 人间，限电 800W，桌子 70cm
- 寒暑假：坐火车回家，要带
- 自己想法：「听说要 32G 内存？」（信息来自抖音，半对）

**典型用户 B：城市中产，预算 9000，想打游戏**
- 父母愿意出，但要求「别买太贵的」
- 专业：工商管理（课业轻）
- 宿舍：4 人间，不限电
- 自己想法：「要 5070」（其实 5060 就够他玩的游戏）

**这两个画像的推荐结果应该完全不同**，而现在的工具有可能给他们同一台。这是要解决的问题。

### 4.2 维度 × 品类矩阵

| 维度 | 轻薄本 | 游戏本 | 台式 | 内存/固态 |
|---|---|---|---|---|
| 价格 | ✓ | ✓ | ✓ | ✓ |

| GPU | ✓（核显） | ✓（主导） | ✓ | **null** |

三处注意：
- **轻薄本的 GPU 也要算**：Intel Arc 130V 与 Radeon 780M 差距明显，对「能不能剪视频」是硬差异。

### 4.3.1 为什么价格必须存三个数

重建数据时实测出来的问题：**同一个 SKU，同一时间，「到手价」能报出四种数**。

战 66 八代 14 寸 R7 H255 / 16G + 512G：

| 口径 | 数值 | 来源 |
|---|---|---|
| 页面标价 | ¥5,799 | 京东商品页 |
| 普通活动到手 | ¥5,749 | ZOL 报道 |
| 叠加国补后 | ¥4,674 | ZOL「直降超千元」 |
| 带人脸的 1T 版 | ¥5,864 | 京东另一个 SKU |

小新 16 同样：页面 ¥5,599、ZOL 报道 ¥6,288、另有渠道算出国补后 ¥4,462。

差异来源是**地区补贴资格、优惠券、PLUS 会员、店铺、下单时段**。这不是数据错误，是电商业态。

所以：

```
priceBest ≤ price ≤ priceList
```

**只存一个 `price` 会有两个后果**：一个是推荐时按最高价算，用户实际能买更便宜，觉得我们不准；另一个是用户按最低价预期，到页面发现更贵，觉得被坑。**两者都在损耗信任。**

`build.py` 会校验这个大小关系 —— 到手价比标价贵、最低价比到手价贵，都直接构建失败。

### 5.2 关键约束

**`rank_offers` 必须是纯函数。** 同样入参必须给出同样顺序。LLM 参与排序会导致同一数据两次顺序不同，用户第二次就发现了。

**`check_price_now` 允许失败且必须显式。** 返回 `{ok:false, reason}`，不拿旧价假装新价。

**`cite` 不是装饰。** 渲染层从 `sourceIds` 自动补脚注，不能靠 LLM 自觉。

**`ask_expert` 是本产品区别于筛选器的关键。** 它不返回答案，返回「还缺哪些信息」。智能体据此决定下一个问题，而不是靠 LLM 自由发挥。

## 6. 性能分：三把尺子

v0.3 的核心变更。原来一把（R23），v0.2 加到两把（+3DMark），v0.3 定到三把。

### 6.1 为什么必须三把

| 尺子 | 测什么 | 谁在意 |
|---|---|---|
| **Cinebench R23** | 10 分钟持续渲染，吃散热与功耗墙 | 剪视频、跑仿真、编译大项目 |
| **Geekbench 6** | 短任务爆发，不吃持续散热 | **开软件、切标签、日常响应** |
| **3DMark Time Spy Graphics** | 显卡渲染 | **打游戏、GPU 加速** |

只用 R23 的问题：**轻薄本会撞功耗墙，被系统性低估。** 而对准大学生来说，轻薄本 + 短任务恰恰是主流组合。

### 6.2 实测对比：同一颗 CPU 在两把尺子下的排名会变

| CPU | R23 换算分 | GB6 换算分 | 差 |
|---|---|---|---|
| Ryzen 7 9800X3D | 73 | **91** | **+18** |
| Ultra 5 226V | 48 | **61** | **+13** |
| Ultra 5 338H | 62 | **73** | **+11** |
| i5-13420H | 45 | **56** | **+11** |
| Ryzen 7 260 | 56 | **67** | **+11** |
| Ultra 5 225H | 62 | **70** | +8 |
| Core 5 320 | 50 | 55 | +5 |
| Ultra 7 255HX | 78 | 83 | +5 |
| Ryzen 7 H 255 | 62 | 66 | +4 |
| Ultra 7 251HX | 77 | 78 | +1 |
| i5-14600KF | 75 | 76 | +1 |
| Ryzen 9 9955HX | 94 | 89 | **−5** |

**规律：低功耗芯片在 GB6 上系统性高 8~13 分，高功耗 HX 反而略低。**

两个直接后果：

1. **单核排序会矛盾**：R23 单核 251HX（2,096）> 255HX（2,027），但 GB6 单核 255HX（2,940）> 251HX（2,908）。两把尺子给出相反的答案 —— 说明**任何单一跑分都有负载偏向，不能独信**。
2. **多核差距会被压缩**：9955HX 对 255HX，R23 多核高 34%，GB6 多核只高 7%。因为 GB6 多核是短时爆发，不考验持续散热。

### 6.3 三套换算口径

```
cpuSustained = 100 × (0.5 × R23单核/2400   + 0.5 × R23多核/40000)
cpuBurst     = 100 × (0.5 × GB6单核/3400   + 0.5 × GB6多核/22000)
gpuPerf      = 100 × TimeSpy图形分 / 25000
```

**三个锚点都取「当季消费级上限」，所以三套分数可横向比较**：

| 尺子 | 单核锚点 | 多核锚点 | 依据 |
|---|---|---|---|
| R23 | 2,400 | 40,000 | 14900KS / 9955HX 级 |
| GB6 | 3,400 | 22,000 | 9800X3D 实测 3,336 / 9950X3D 22,041 |
| 3DMark | — | 25,000 | RTX 5090 Laptop 满血 175W |

### 6.4 Geekbench 6 实测数据（电脑 CPU，2026-11 取数）

| CPU | GB6 单核 | GB6 多核 | 换算分 |
|---|---|---|---|
| Ryzen 7 9800X3D | 3,336 | 18,346 | 91 |
| Ryzen 9 9955HX | 3,180 | 18,612 | 89 |
| Ultra 7 255HX | 2,940 | 17,370 | 83 |
| Ultra 7 251HX | 2,908 | 15,391 | 78 |
| i5-14600KF | 2,781 | 15,636 | 76 |
| Ultra 5 338H | 2,743 | 14,448 | 73 |
| Ultra 5 225H | 2,715 | 13,395 | 70 |
| Ryzen 7 260 | 2,555 | 12,923 | 67 |
| Ryzen 7 H 255 | 2,551 | 12,673 | 66 |
| Ultra 5 226V | 2,585 | 10,052 | 61 |
| i5-13420H | 2,320 | 9,760 | 56 |
| Core 5 320 | 2,550 | 7,800 | 55 |

**Core 5 320 的数据有两个口径**：topcpu 2,584/8,070、cpu-monkey 2,502/7,554、LaptopMedia 实测 2,467/7,084。取中位 2,550/7,800，`gb6` 字段存区间因为跨度大。

Core 5 320 是 10~15W 超低功耗芯片（2P+4E，6 线程），多核只有 8,070 —— 比 R7 H255 的 12,673 低 36%。**这再次验证了「同价位不同芯片不能同分」**。

### 6.5 3DMark 实测数据（Time Spy Graphics）

| 显卡 | 中位数 | 样本区间 | 换算分 |
|---|---|---|---|
| RTX 5090 Laptop (175W) | 25,015 | — | 100 |
| RTX 5080 Laptop | 20,010~22,033 | 跨源差异大 | 80~88 |
| RTX 4090 Laptop | 20,166 | — | 81 |
| RTX 5070 Ti Laptop | 16,622 | 18 样本 | 66 |
| RTX 5070 Laptop | 13,235 | **10,851~14,771** | 53 |
| RTX 5060 Laptop | 11,937 | 9,090~12,719 | 48 |
| RTX 5050 Laptop | 9,122 | 7,166~9,828 | 36 |
| RTX 4060 Laptop | 10,397 | — | 42 |
| Radeon 8060S（核显） | 10,038 | — | 40 |

**两个必须记住的坑：**

**坑一：Graphics 分 ≠ 总分。** `Time Spy Graphics Score` 只测显卡，`Time Spy Score` 把 CPU 也算进去。同一张 RTX 5070 配不同 CPU，总分能差 1,000 而图形分应该一致。业界数据源经常混用，**这是新的污染源，必须在校验里拦住**。

**坑二：GPU 的「同芯片不同分」是事实，不是污染。** RTX 5070 区间 10,851~14,771，跨度 36%，那是功耗墙（TGP）差异 —— 115W 和 140W 是两台不同的机器。

### 6.6 规则升级：从「同芯片同分」到「同芯片同功耗档同分」

上一轮定的是「同款芯片只能有一个性能分」，针对 U7-251HX 被写成 48 和 52。

**但 GPU 不适用这条。** 所以要细化为：

```
同款芯片：
  |TGP_a − TGP_b| ≤ 15W  →  三个性能分必须相等（否则构建失败）
  |TGP_a − TGP_b| > 15W  →  允许不同，但两台都必须填 tgp 字段
```

**判据不是「同芯片必同分」，是「同芯片同功耗档必同分」。** 前者会为了追求一致性把真实差距抹平，那是反向的错误 —— 和编造一个分数同样有害。

### 6.7 核显怎么处理

| 情况 | `gpuSource` | 做法 |
|---|---|---|
| 有实测图形分 | `measured` | 直接换算 |
| 无实测，但同架构同单元数有分 | `inferred` | 推算，**页面必须标「推算」** |
| 完全查不到 | `none` | `gpuPerf: null`，按不适用退场 |

**`inferred` 必须和 `measured` 在视觉上区分。** 允许推算，不许把推算说成实测。

### 6.8 六个侧重（v0.3 新增 `daily`）

| 侧重 | 主维度 | 对准大学生的意义 |
|---|---|---|
| `value` 省钱优先 | 无（综合分） | 预算紧，能省则省 |
| `daily` **日常流畅** | **`cpuBurst`** | **开软件、切标签、上网页 —— 文科/商科主力** |
| `game` 游戏优先 | `gpuPerf` | 打游戏 |
| `work` 重度生产力 | `cpuSustained` | 剪视频、跑仿真、编译 |
| `carry` 便携优先 | `portable` | 背回家、带去教室 |
| `future` 能加装优先 | `upgrade` | 四年不换 |

**`daily` 是本版新增，也是最该默认的。** 因为准大学生问「买什么电脑好」时，绝大多数真实负载是短任务。默认用 `cpuSustained` 会把他们推向「多核跑分高但笨重」的机器。

权重按品类区分：轻薄本的 `daily` 侧重里 `cpuBurst` 0.30、`cpuSustained` 0.10；游戏本的 `game` 侧重里 `gpuPerf` 0.40。

## 7. 排序引擎契约（硬约束）

### 7.1 四级排序

```
1. 超预算 → 排最后（容差 5%，5009 对 5000 不算超）
2. 主维度分三档（0=最弱 / 1=中 / 2=最强）
3. 同档内按主维度原始值降序
4. 仍相同 → 加权总分 → 最后按 id 兜底（保证顺序唯一）
```

### 7.2 九条不可违反的规则

| 规则 | 违反的后果 |
|---|---|
| 分数必须能由实测推出 | 手改分数、不改依据，构建失败 |
| 同款 CPU 必同分 | 同一个 CPU 两台机器两个分 = 污染 |
| **同款显卡同 TGP 必同分，不同 TGP 允许不同** | 同 TGP 两个分 = 污染；不同 TGP 不同分 = 事实（RTX 5070 的 115W 与 140W 差 36%） |
| **CPU 校验与 GPU 校验必须分开** | 同 CPU 配不同显卡是正常配置（天选 7 是 5050、天选 6 是 5060），合在一起比会误报 |
| Graphics 分与总分不可混用 | 等于用含 CPU 的数衡量 GPU |
| 不适用维度必须退场 | 判 0 分 = 「因为不涉及所以它最差」 |
| 平局是事实，不能打散 | 五台轻薄本同拿 62 分，因为 R23 多核都在 15500~16400 |
| 推算值必须标推算 | `inferred` 说成 `measured` 就是编造 |
| **三套性能分不可互相替代** | 拿 R23 的高分去暗示游戏性能，是误导 |

### 7.3 智能体层禁止做的事

- ❌ 自己算加权总分
- ❌ 自己判断「这台性价比更高」
- ❌ 引入工具没返回的数字（包括「大约」「差不多」）
- ❌ 数据缺失时用行业常识补位
- ❌ 把 `inferred` 的分数当实测讲
- ❌ **没问过 Q1~Q5 就给出确定性推荐**

### 9.2 构建期校验

| 校验 | 失败条件 |
|---|---|
| `cpuSustained` 可由 `cb23` 推出 | 差 > 1 分 |
| `cpuBurst` 可由 `gb6` 推出 | 差 > 1 分 |
| `gpuPerf` 可由 `tsGraphics[1]` 推出 | 差 > 1 分 |
| 同芯片同 TGP 档三个分数一致 | 差 > 1 分 |
| `upgrade` 品类三个性能分都是 null | 任一非 null |
| `gpuSource = measured` 时必须有 `tsGraphics` | 缺字段 |
| `gpuSource = none` 时 `gpuPerf` 必须 null | 有值 |
| `tgp` 合理区间 | 独显 < 35W 或 > 250W → 警告 |
| **`loadWatt` 必须 ≥ `tgp`** | 整机功耗不该低于显卡功耗 |
| `priceHistory` 日期递增 | 非递增 |
| `useCases` 非空 | 空数组 |

## 10. 评测方案

### 10.1 硬门槛（不达标不上线）

| 指标 | 门槛 | 怎么测 |
|---|---|---|
| **编造率** | **必须为 0** | 300 条抽样，逐句核对数字能否追到 source |
| 单位混用 | 0 | 扫描 Graphics 分与总分是否并排 |
| 推算当实测 | 0 | `inferred` 机型回答里必须出现「推算」 |
| 性能分串用 | 0 | 用 R23 高分暗示游戏性能 |
| 死循环澄清 | 0 | 同一问题被问第二次即失败 |

### 10.2 准大学生专项指标（v0.3 新增）

| 指标 | 目标 | 说明 |
|---|---|---|
| **关键提问覆盖率** | ≥ 70% | 在需要 Q1~Q5 的场景里，实际问出来的比例 |
| **限电场景召回** | 100% | 用户提到游戏本时必须问宿舍功率 |
| **家长话术可得性** | ≥ 90% | 推荐里能给出「给家长的说法」的比例 |
| 画像区分度 | 100% | 用户 A（5500/计算机）与用户 B（9000/工商）的推荐不应完全相同 |

**「画像区分度」这条是防止推荐退化成「最贵的就是最好的」。** 两个预算差 3500、用途完全不同的用户，如果拿到同一台，产品就失败了。

## 14. 风险与未决问题

### 14.1 已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **电商到手价不稳定** | 推荐价与用户实付价对不上 | 三价并存（§4.3.1）+ 标注取数时间 + 不承诺「你能买到这个价」 |
| **同名机型 SKU 混淆** | 同一个名字下有 16G/32G、LCD/OLED、i7/Ultra7、Linux/Windows 多个版本，价格差可达 3000 | `spec` 必须写全配置；`priceNote` 注明是哪个 SKU；回答里主动提醒核对 |
| **17 台显卡数据查不全** | GPU 维度不完整 | 允许 `gpuSource: none` + 退场，但页面标注 |
| **`loadWatt` 数据几乎没人测** | 宿舍限电这条做不了 | 按「CPU TDP + GPU TGP + 50W 余量」估算，标 `inferred` |
| **核显跑分样本少** | 轻薄本 GPU 靠推算 | `inferred` 显式标注 |
| **三套分数让用户更困惑** | 「为什么三个性能分」 | 回答里默认只讲一个，问「为什么」时再展开 |
| **8B 模型漏掉必问五问** | 核心机制失效 | 关键词路由兜底：命中「游戏」必执行 Q2 |
| **实时价格抓取不稳** | 数据陈旧 | `lastChecked` + 过期声明 |
| **台式只有 2 台** | 该品类可信度低 | 明示样本量，<3 台不排序只列清单 |

### 14.2 待决问题

1. **三套性能分在界面上怎么呈现？** 全展示会让人懵，只展示一个又会掩盖差异。
2. **`loadWatt` 怎么取？** 实测几乎没有，估算的误差能到 20%，宿舍 500W 的临界判断会受影响。
3. **要不要做「专业 → 软件 → 配置」映射表？** 这是 Q1 的基础，但专业太多，做粗了没用，做细了维护不起。
4. **家长版分享页要不要单独做？** 还是同一页加一段「给家长看」？
5. **本地还是云端？**
6. **要不要实时抓价？**

第 1、2、3 三个直接决定能不能落地，建议先定。

## 15. 附：产品宪法

> **每个数字都要能追到底，追不到的就说不追不到。**
>
> 一、分数必须有实测依据，推算必须标明是推算。
> 二、同芯片同功耗档必须同分；不同功耗档不同分，那是事实不是污染。
> 三、不适用就说退场，不说 0 分。
> 四、Graphics 分和总分不是一个量，不许混用。
> 五、三个性能分测三件不同的事，不可互相替代。
> 六、平局是事实，不是缺陷。
> 七、查不到就说查不到。
> 八、**没问过就断言，比答错更坏 —— 用户不知道自己该问什么，所以我们得替他问。**
>
> 前七条管数字，第八条管态度。
