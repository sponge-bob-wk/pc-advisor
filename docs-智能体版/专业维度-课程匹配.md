# 专业维度：按学校课程匹配

> 生成于 2026-11-11。核心方法：**以具体学校的培养方案为准，不以专业大类为准。**
> 配套文件：`data/majors.json`（课程映射库 + 采样学校）、`data/prices.json`（机型）

---

## 一、为什么必须按课程，而不是按专业

按专业大类做，会得出错误结论。**同样的「计算机科学与技术」，三所学校给出三种硬件要求：**

| 学校 | 关键课程 | 内存 | 显存 | 需独显 | 结论 |
|---|---|---|---|---|---|
| **长沙理工** | FPGA 应用与开发、虚拟化、大数据 | 32G | — | ❌ 不需要 | 核显本可胜任 |
| **浙工大** | 深度学习、并行计算、FPGA | 32G | 6G（可选） | ❌ 可选 | 核显够，有独显更方便 |
| **海南大学** | **虚幻引擎游戏开发**、游戏开发基础 | 32G | **8G** | ✅ **必须** | 核显本直接出局 |

海南大学开「虚幻引擎游戏开发」，UE5 的工程动辄 100G+，实时预览要 RTX 级显卡。**这不是"性能偏好"，是"能不能上课"的问题。**

如果按专业大类一刀切说「计算机专业核显就够」，海南大学的学生会买错。

## 二、数据结构

```
schools[]              采样学校
  └─ majors[]          该校的专业
      └─ courses[]     课程（含学期 + 映射到的规则 id）
          └─ courseId ──┐
                        ↓
courseSoftware[]       课程 → 软件 → 硬件门槛（核心资产，可复用）
majorTemplates[]       查不到具体学校时的兜底（按专业大类）

machines (prices.json) 机型，带 ram / vram / colorGamut 字段
```

**匹配流程**：

```
用户给「学校 + 专业」
  → 查该校该专业的 courses
  → 每门课匹配 courseSoftware 里的规则
  → 取所有课程门槛的最大值（内存、显存、是否需独显、是否需 Windows）
  → 用这个门槛筛机型
  → 查不到学校 → 退回 majorTemplates，并明确告知这是粗口径
```

**两条必须注意的设计**：

**「深度学习」的 `gpuRequired` 是 false。** 课程作业基本能用学校服务器、Colab、AutoDL 跑，本地有 GPU 只是方便调试。如果把这条设成 true，会把所有计算机专业学生推去买游戏本。

**「计算机图形学」≠「三维渲染」。** 前者写小规模渲染器（核显够），后者做影视级资产（要独显）。这两个词很容易混，映射时必须分开。

## 四、匹配实测（当前 36 台机型）

| 学校 | 门槛 | 满足台数 | 最便宜的方案 |
|---|---|---|---|
| 长沙理工 | 32G，核显可 | 3 台 | 荣耀 MagicBook Pro 14 ¥7,000 |
| 浙工大 | 32G，核显可 | 3 台 | 同上 |
| **海南大学** | **32G + 8G 显存独显** | **0 台** | **无** |

### 这个「0 台」暴露了两个真问题

**问题一：数据池覆盖不了工科/设计的真实需求。**

全池只有 3 台 32G 内存机型，而且**全是核显本**。所有独显机型（天选、苍龙、暗影精灵）标配都是 16G。

**问题二：`ram` 字段只记了标配，没记「能不能自己加」。**

天选 6 Pro 有双内存插槽，自己加两条 16G 就到 32G，完全满足海南大学要求。但当前数据里 `ram: 16`，匹配时被判为不合格。

**这是数据模型的缺陷，不是机型的问题。** 需要补 `ramSlots`（插槽数）和 `ramMax`（最大支持容量）两个字段。

## 五、怎么采培养方案

培养方案一般在**各校教务处或学院官网**，格式不一：

| 来源 | 形式 | 拿到什么 |
|---|---|---|
| 学院官网「培养方案」栏目 | HTML 表格 | 课程名 + 学分 + 学时 + 学期 |
| 教务处「教学计划」 | PDF | 同上，更完整 |
| 招生网「专业介绍」 | 文字 | 只有课程大类，不够细 |

**搜索关键词**：`<学校名> <专业名> 培养方案 2026` 或 `<学校名> 教学计划 课程设置`

**已知可用的三所**（已入库）：

| 学校 | URL |
|---|---|
| 长沙理工大学 | `csust.edu.cn/jtxy/info/1975/28927.htm` |
| 海南大学 | `cs.hainanu.edu.cn/info/1066/13080.htm` |
| 浙江工业大学 | `cs.zjut.edu.cn/ueditor/jsp/upload/file/20260923/1790127282132085263.pdf` |

**采集要点**：
1. 只取**专业必修 + 专业选修**，通识课（高数、思政、体育）对配置没影响，跳过
2. **必须记学期** —— 大一上就要用的软件，不能等到大三才配
3. 课程名 → 规则 id 的映射，映射不上就填 `null`，不要硬凑

## 六、当前状态与待补

| 项 | 状态 |
|---|---|
| 课程映射规则 | 23 条 ✅ |
| 采样学校 | **3 所**（全部是计算机专业）⚠️ |
| 已映射课程 | 49 / 54 门 |
| 专业大类兜底 | 10 个 ✅ |
| 全国本科院校 | **1200+，覆盖率 0.25%** ⚠️ |

**三个明显缺口：**

1. **样本太少且单一**：只采了 3 所学校的计算机专业。设计、机械、土木、影视这些「硬件要求更高」的专业一所都没采，而那恰恰是最需要精确匹配的。
2. **缺 `ramSlots` / `ramMax`**：导致「可自行升级内存的机型」被误判为不合格。
3. **课程名 → 软件的推断有不确定性**：培养方案只写「计算机图形学」，不写用什么软件。库里用 `confidence` 标了高/中/低。

**建议的最小可用集**：每个专业大类采 3~5 所代表学校（985 / 211 / 普通本科各一所），覆盖 10 个专业 = 30~50 所学校，约 300~500 门课程。这个量级能撑起真正可用的专业匹配。
