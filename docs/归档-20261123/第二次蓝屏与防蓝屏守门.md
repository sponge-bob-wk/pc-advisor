## 二、这次的具体原因

我写了个 `debug_zero_loss4.py`，想对比 4 种 Trainer 配置
（bf16 / gradient_checkpointing / optim）看哪个导致 loss=0。

**脚本在同一个进程里连续加载了 4 次模型。**

```python
for name, bf16, gc, optim in CASES:
    model = AutoModelForCausalLM.from_pretrained(...)   # 每次 +11 GB commit
    ...
    del model, trainer
    torch.cuda.empty_cache()                             # ← 这个不够
```

**为什么 `del` + `empty_cache()` 不够**：

| 机制 | 是否真正归还 |
|---|---|
| `del model` | 只减引用计数，GC 不保证及时 |
| `torch.cuda.empty_cache()` | 只释放 CUDA 缓存，**不归还 Windows commit** |
| 进程退出 | ✅ **唯一能真正归还的方式** |

**Windows 的 commit 是「已承诺」不是「已使用」** —— 进程退出才归还。
所以同一进程里连续加载 N 个模型 = commit 累积到 N×11 GB。

4 × 11 = 44 GB > 提交上限 30 GB → 内核分配失败 → 蓝屏。

## 三、这次加了什么

### 3.1 `safe_run.py` —— 独立的加载守门

```python
from safe_run import check_before_load, mark_loaded
check_before_load()          # 不足会 raise SystemExit
model = AutoModelForCausalLM.from_pretrained(...)
mark_loaded()
```

**两条规则**：

| 规则 | 阈值 | 拦什么 |
|---|---|---|
| commit 余量 | >= 13 GB | 内存不够时加载 |
| 同进程加载次数 | **最多 1 次** | 连续加载（这次蓝屏的原因） |

**为什么是 13 GB**：实测每次加载 4bit 模型 commit 涨约 11 GB，留 2 GB 余量。

**为什么限制 1 次**：`del` + `empty_cache()` 不能归还 commit，
只有进程退出才行。需要多组对比就**每次开新进程**：

```bash
for case in a b c d; do python probe.py --case $case; done
```

### 3.2 批量注入到 8 个脚本

```python
# inject_guard.py 自动插入
try:
    from safe_run import check_before_load as _guard, mark_loaded as _mark
    _guard()
    _mark()
except ImportError:
    pass          # safe_run 不在时跳过（不阻塞脚本）
```

注入的 8 个脚本：

| 脚本 | 作用 |
|---|---|
| `train_route_lora.py` | 训练 |
| `eval_lora.py` | 评估 adapter |
| `measure_real.py` | 测内存峰值 |
| `measure_mem.py` | 分段测内存 |
| `probe_maxlen.py` | 探测 max_length 上限 |
| `debug_zero_loss2/3/4.py` | loss=0 排查 |

**注入时踩了个坑**：`probe_maxlen.py` 的 `from_pretrained` 在 `try:` 块内
（缩进 8 空格），注入后缩进错乱 → `unexpected indent`。手工修了。

### 3.3 验证

```

```

## 四、今天的另一个大发现：loss=0 的真根因

### 4.1 现象

v4 训练启动后，loss 从第 5 步开始**全是 0.0**，`grad_norm` 也是 0。

### 4.2 排查过程

| 假设 | 验证方法 | 结论 |
|---|---|---|
| labels 被 mask | 统计每条样本的有效 label 数 | ✅ **确实是 0** |
| system prompt 太长 | 量 token 数 | ✅ 1055 token > max_length 512 |
| collator 弄丢 label | 对比 Seq2Seq vs 手写 collator | ❌ 都正常（168/8条） |
| 模型算不出 loss | 单条样本直接 `model(**batch)` | ❌ loss=1.5438 正常 |
| num_items_in_batch 摊薄 | 传 vs 不传对比 | ❌ 结果一样 |

### 4.3 真根因

**昨天修「system prompt 不一致」时，把它从 56 字符改成了 2170 字符，
但没同步调 `max_length`。**

```
system prompt = 1055 token
max_length    = 512
→ _prep 里 n_prefix = min(len(prefix_ids), len(full_ids)) = 全部
→ labels = [-100] * 全部
→ **没有可学习的 token** → loss 恒等于 0
```

**这是我自己的修复引入的连锁问题。**

### 4.4 修法：压缩 prompt

`probe_maxlen.py` 实测 8GB 显存的硬上限：

| max_length | 结果 |
|---|---|
| 512 | ✓ 成功（显存峰值 11.76 GB，借用统一内存） |
| 640 | ✗ OOM |
| 768 | ✗ OOM |

**512 是硬上限。** 所以 prompt 必须压到 `512 - 107（CoT 90分位）- 20 = 385 token` 以内。

压缩结果：

| 版本 | 字符数 | token 数 | 装得下 512？ |
|---|---:|---:|---|
| 完整版 | 2170 | 1055 | ✗ |
| 中等压缩 | 875 | 446 | ✗（+107 = 553） |
| **激进压缩** | **562** | **238** | ✅ **余量 167 token** |

压缩版保留：
- 输出格式
- 七类 intent 的**区分特征**（不是完整定义）
- 十一类 topic 的关键词
- fit 的判据
- 6 条最易混的对照

砍掉：冗长解释、大部分例句、"注意""判据""⚠️"这类提示词。

### 4.5 验证

重建训练集后：

```
prefix（system+user+提示）: 中位 255 token
full（完整对话）:          中位 276 token
有效 label: 中位 21（不带 CoT）/ 70（带 CoT）
**label 全被 mask 的条数: 0 / 30**
被截断（full > 512）: 0 条
```

**零 mask、零截断。**

## 六、教训

### 6.1 同一个进程不能连续加载模型

这是**第二次因为同一类原因蓝屏**。

`del` + `torch.cuda.empty_cache()` **不归还 Windows commit**。
只有进程退出才行。

**需要多组对比就写 shell 循环，每次开新进程。**

### 6.2 改一个参数要检查关联参数

昨天改 system prompt 长度（56 → 2170 字符），
没检查 `max_length`（512）够不够 → 所有 label 被 mask。

**关联参数清单**：
- system prompt 长度 ↔ `max_length`
- `max_length` ↔ 显存（512 是 8GB 的硬上限）
- 训练 token 预算 ↔ 推理 `num_predict`

### 6.3 指标好看不等于训练有效

v3 的 eval_loss 0.6022 → 0.1946（降 68%），看起来很好，
但实际模型是坏的（输出死循环）。

**v4 更极端：loss 恒等于 0，说明根本没在学。**

**判断训练是否有效，要看**：
1. loss 是否在合理范围（不是 0，也不是常数）
2. grad_norm 是否非 0
3. 训完能不能正常推理

### 6.4 蓝屏的代价被低估了

两次蓝屏，每次：
- 系统重启 2-3 分钟
- 未保存的工作丢失
- 调试进度中断
- 可能损坏文件（这次没坏，但风险真实）

**13 GB 的守门检查花 0.1 秒，能避免这一切。**
