## 四、防蓝屏措施（本次全程无事故）

### 4.1 训练前的守门拦截

```
=== 加载前检查 ===
  commit 可用: 12.6 GB（单次加载需 13 GB）
✗ commit 不足，拒绝加载
```

**守门正确拦住了** —— 差 0.4 GB。如果没这个守门，很可能又蓝屏。

### 4.2 腾内存后的水位

| 动作 | commit 可用 |
|---|---:|
| 初始 | 12.6 GB（**不足**） |
| 停 Ollama | — |
| 关浏览器 23 个 + 微信 13 个 | **16.2 GB** ✓ |

### 4.3 训练中的水位追踪

| 时点 | commit 可用 | 物理可用 | 显存 |
|---|---:|---:|---:|
| 训练前 | 16.2 GB | 7.5 GB | 957 MiB |
| 训练中 | 7.0 GB | 5.9 GB | 7019 MiB |
| 训练后 | 16.6 GB | 8.6 GB | 306 MiB |

**训练中 commit 从 16.2 掉到 7.0**（吃 9 GB），这是正常的：
4bit 模型 + CUDA 上下文 + 统一内存。

**蓝屏判据**：commit 低于 3 GB 才危险。7 GB 安全。

### 4.4 训练前的 label 验证

```
prefix（system+user+提示）: 中位 255 token
full（完整对话）:          中位 276 token
有效 label: 中位 21
**label 全被 mask 的条数: 0 / 30**
```

**这一步是必须的** —— 11-23 那次 loss=0 就是因为 label 全被 mask，
跑了 28 分钟才发现白跑。

## 七、给论文用的材料

### 7.1 「补数据 → 能力提升」的完整实证

这是一个**可完整论证的案例**：

```
① 现象：analyze 意图判不对（判成 ask_current）
② 排查：查训练集 → analyze 样本数 = 0
③ 归因：11-21 加了代码没加数据，靠规则兜底掩盖
④ 干预：补 63 条种子（55 正 + 8 负）
⑤ 结果：v5 上 analyze 5/5 全对
```

**关键论点**：
- 「规则兜底」能让系统"看起来能用"，但**模型能力并未具备**
- 功能测试（`test_analyze.py` 27 断言全绿）**无法发现**这个问题
- 必须**单独测模型层**（绕过规则）才能暴露

### 7.2 「防蓝屏守门」的工程价值

| 事故 | 损失 | 守门能否预防 |
|---|---|---|
| 11-22 蓝屏 | 31 步训练白跑 | ✅ commit 守门 |
| 11-23 蓝屏 | 调试进度中断 | ✅ 同进程单次加载 |
| 11-23 loss=0 | 28 分钟白跑 | ✅ label 验证 |

**论点**：在消费级硬件（8GB 显存 / 15.2 GB 内存）上做私有化部署，
**资源约束是真实的技术挑战**，不是配置问题。

守门代码共约 300 行，换来的是**每次 30 分钟训练不白跑**。
