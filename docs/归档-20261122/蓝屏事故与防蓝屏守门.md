## 二、根因（不是显卡驱动）

系统日志的关键证据：

```
18:42:39  [Resource-Exhaustion-Detector] 虚拟内存不足
          python.exe (4264) 使用了 10,194,669,568 字节（9.5 GB）
18:44:54  虚拟内存不足
          python.exe (3836) 使用了 10,603,859,968 字节（9.9 GB）
18:47:16  虚拟内存不足
          python.exe (31992) 使用了 10,603,499,520 字节（9.9 GB）
18:50:04  虚拟内存不足
          python.exe (10544) 使用了 10,995,703,808 字节（10.2 GB）
18:50:03  [Application Popup] audiodg.exe 应用程序错误
18:50:44  SQL Server CEIP 服务意外终止
18:56:02  蓝屏 0x0000003B (0xc0000005)
```

**0x3B = SYSTEM_SERVICE_EXCEPTION，参数 0xc0000005 = 访问违规。**

这个错误码常见于驱动问题，但这次的**触发链是内存耗尽**：

```
训练进程 11 GB
+ Fusion360（三维建模，也在跑）
+ SQL Server
+ 浏览器 1.4 GB
+ 系统本身
> 15.2 GB 物理内存
→ 内核在分配内存时拿不到页 → 访问违规 → 蓝屏
```

`audiodg.exe` 报错、SQL Server 服务崩溃，都是**内存耗尽的连带现象**，
不是独立的故障。

### 4.2 训练脚本内置守门

`train_route_lora.py` 在加载模型**之前**检查内存：

```python
_avail = psutil.virtual_memory().available / 1024 ** 3
if _avail < 9.0:
    print("✗ 内存不足，拒绝训练（防蓝屏）")
    ...
    return 1
```

**为什么放在加载模型之前**：模型一加载就是 4-5 GB，
等加载完再检查已经晚了。

### 4.3 安全线怎么定的

| 可用内存 | 判定 | 理由 |
|---|---|---|
| ≥ 11 GB | ✓ 可以跑 | 训练峰值实测值 |
| 9~11 GB | ⚠️ 偏紧 | 加上系统波动可能不够 |
| < 9 GB | ✗ **拒绝** | 2026-11-22 就是这么崩的（4.4 GB） |

**9 GB 这个线是「11 GB 峰值 × 0.8 余量」**，不是拍脑袋。

## 六、这次训练配置的改动

### `max_length` 1024 → 512

**依据**：实测训练集样本极短

```
字符数    中位 122 / 90分位 219 / 最大 413
粗估 token 中位 81 / 90分位 146 / 最大 275
```

**1024 是 4 倍浪费。** 降到 512 后，90 分位样本（146 token）仍有 3.5 倍余量。

**效果**：改之前 CUDA OOM（928 MiB 分配不出），改之后能跑起来了。

| vivo | vivo |

**为什么这是真 bug 不只是测试问题**：

新增 `fix_missing_brand.py`，从机型名推断（规则保守：名称前缀 > 名称包含 > 别名表），
推断不出的保持 None 并报告。实测 6/6 全部推断成功。

**修复后**：品牌数 14→16，各品牌之和 223 = 总数 ✓

### 7.2 新增 `test_analyze.py`（17 断言）

与 `adversarial_v2.py` 的分工：

| | 测什么 |
|---|---|
| `adversarial_v2.py` | 意图分类（模型判断对不对） |
| `test_analyze.py` | 计算结果（代码算得对不对） |

分三层：

| 层 | 是否调模型 | 测什么 |
|---|---|---|
| 引擎层 | 否 | 给定结构化查询，算出的数字和手工核对一致 |
| 解析层 | 是 | 自然语言 → 结构化查询结构正确 |
| 端到端 | 是 | 完整问句 → 数字正确 |

**基准值全部手工核对**，不是从引擎输出抄的。

**引擎层 17/17 全绿。**

一个设计决策：分组断言写成「组数 >= 10 且各组之和 == 总数」，
**不写死组数** —— 补数据/加机型都会变，写死就会假失败。

## 八、教训

### 8.1 长任务必须有前置检查

训练要跑 35 分钟，中途蓝屏就全白跑。
**花 2 秒做内存检查，能避免 35 分钟的损失** —— 这个交易永远划算。

### 8.2 报错信息会骗人

`0x0000003B SYSTEM_SERVICE_EXCEPTION` 看起来像驱动问题，
但真正的证据在**事件日志的时间顺序**里：
4 次「虚拟内存不足」在前，蓝屏在后。

**查崩溃要看时间线，不要只看错误码。**

### 8.3 「能跑」是有前提的

11-18 那次成功不代表这次能成功 —— 差别在「当时还开着什么程序」。
**把前提写进检查脚本，而不是记在脑子里。**

### 8.4 checkpoint 间隔决定损失大小

`save_steps=50`，跑到 31 步崩了 → 0 个 checkpoint。
如果 `save_steps=20`，至少能保住 20 步。

**但对 189 步的总量来说，20 太密**（写盘开销）。
折中：`save_steps=30`，损失上限 30 步。
