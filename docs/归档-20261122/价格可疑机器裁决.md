## 二、调查：先看这些数的来源

拿「华硕天选6 Pro」（+39%）举例，看它在库里的完整记录：

```json
priceSnapshots: {
  "jd": 11799,          ← 京东平台价
  "zolRef": 8489,       ← ZOL 参考报价
  "merchantMin": 8404,  ← 经销商最低
  "merchantMax": 8405,  ← 经销商最高
  "_source": "ZOL detail 页（参考报价/平台快照/经销商区间）",
  "_capturedAt": "2026-11-16 18:46"
}
```

**关键观察**：

| 来源 | 价格 | 与 zolRef 的差 |
|---|---:|---:|
| zolRef（参考报价） | 8489 | — |
| merchantMin（经销商） | 8404 | **-1%** |
| jd（京东平台价） | 11799 | **+39%** |

**zolRef 和 merchantMin 只差 1%，而 jd 高出 39%。**

这不是「某一边数据错了」，而是**两个不同的价格口径**：
- `zolRef` / `merchantMin`：裸机价 / 低配 SKU 价
- `jd` / `tmall`：**当前挂牌 SKU 的价**（可能是高配，或含服务包）

## 三、另一个决定性证据：这 15 台全部没有到手价

```python
for x in suspects:
    assert x["real"] is None    # 15/15 全部成立
```

`real` 是「到手价」（net/final），需要京东商品页直读才能拿到。

**这 15 台一台都没有到手价** —— 说明它们只从 ZOL 详情页抓了标价快照，
没有做京东商品页直读。

而 `priceBasis` 自己写着：

> 「ZOL 参考报价，非到手价。net/final 需京东商品页直读，本轮未取得。」

**数据自己承认了「没有实价」。**

## 四、结论：不该裁决数据，该改判定规则

### 4.1 现在的判定逻辑有缺陷

`price_cross_check.py` 把 `zolRef` / `jd` / `tmall` / `merchantMin`
都当成「平台标价」放进同一个池子比。

**但它们不是同一类**：

| 来源 | 实际含义 | 可比性 |
|---|---|---|
| `zolRef` | ZOL 编辑给的参考价 | 参考 |
| `merchantMin` | 经销商最低报价 | 裸机价 |
| `jd` | 京东**当前挂牌 SKU** 价 | 特定 SKU |
| `tmall` | 天猫**当前挂牌 SKU** 价 | 特定 SKU |

**同一台机器在 ZOL 有多个 SKU 页时，`zolRef` 取哪个、`jd` 取哪个，
本来就可能不是同一个配置。**

### 4.2 应该怎么改

**方案 A：分级比较（推荐）**

```
第一组（同口径，可比）: zolRef ↔ merchantMin
第二组（同口径，可比）: jd ↔ tmall
跨组比较（不可比）:     zolRef ↔ jd / tmall   ← 不判定为冲突
```

理由：`zolRef` 和 `merchantMin` 都是「非挂牌价」，差 1% 属正常；
`jd` 和 `tmall` 都是「当前挂牌价」，可以互相比。

**方案 B：只在有到手价时判定**

```
有 real（到手价）→ 拿 real 和标价比，差 >30% 才报
无 real          → 标记「仅标价，不作判定」
```

理由：到手价是唯一「用户真实要付」的数。没有它，标价差异只是
「不同店铺不同 SKU」，报出来也没法处理。

**我建议两个都做**：
- 分级比较解决「同型号不同 SKU」的假冲突
- 无到手价标记解决「没法处理」的噪音

## 五、这 15 台的真实状态

**数据没错，只是缺一手实价。**

| 项 | 状态 |
|---|---|
| 配置（cpu/ram/gpu/screen） | ✓ 完整（从参数页补全） |
| 标价快照 | ✓ 有（但多来源口径不同） |
| 到手价 | ✗ **全部缺失** |
| 用户能不能用 | ⚠️ 能看配置，但价格是「标价快照」不是「到手价」 |

**前端已经在做这件事**：`priceIsEstimate: true` 时显示
「这个价是平台标价快照，不含国补和平台券 —— 不要说成到手价」。

所以**用户不会被误导**，只是这 15 台的价格精度低于其他机器。

## 六、要不要补一手价？

**要，但不是现在。**

补一手价需要去京东商品页直读（`net`/`final`），
这是 `refresh_engine.py` 的 `prices` 预设在做的事。

**优先级判断**：

| 任务 | 价值 | 成本 |
|---|---|---|
| 改判定规则（分级比较） | 高 —— 消除 15 台假警报 | 低（改一个脚本） |
| 补 15 台一手价 | 中 —— 15 台的价格精度 | 高（要抓 15 个商品页） |
| 补全部 223 台一手价 | 高 | 很高 |

**建议**：先改判定规则（现在就能做），补价放到下次全量刷新时一起做。

## 七、这次调查的方法论收获

### 7.1 「差异大」不等于「数据错」

15 台报可疑，查下来 **0 台是真错**。全部是口径混用。

如果直接按「>30% 就改数据」去处理，会把正确的数据改坏。

### 7.2 先看「有没有实价」，再看「差多少」

`real = null` 这个字段比价差本身更能说明问题 ——
它告诉你「这台根本没有可比的真价」。

**判据的优先级应该是**：
1. 有没有实价？（没有 → 不判定）
2. 配置是否同一 SKU？（不同 → 不判定）
3. 同口径来源差多少？（>30% → 才报）

### 7.3 数据自己会说话

`priceBasis` 字段里写着：

> 「ZOL 参考报价，非到手价。net/final 需京东商品页直读，本轮未取得。」

**数据已经明确标注了它的局限，是判定脚本没读这句话。**
