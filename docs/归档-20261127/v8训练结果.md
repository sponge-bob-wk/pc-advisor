## 四、这次做对了什么

### ① fit 字段污染：在数据层修，不在规则层补

**症状**：模型对「打游戏」「写代码」输出

```json
{"intent": "fit", "topic": "none", "fit": true}
                ↑ intent 字段被填成了 "fit"
```

**根因**：训练数据里有这种错配

```
「预算 5000，写代码」 → {"intent": "state_new_need", ..., "fit": true}
```

`fit` 的定义是「true = 拿用途问**当前这台**行不行」，
只在 `intent=ask_current` 时才有意义。但数据里到处乱标。

模型看到大量「用途词 + fit:true」的配对，学成了
「有用途词 → fit 该是 true」，然后把这个信号挤到了 intent 字段。

**修法**（三层）：

1. 修训练数据：`intent ≠ ask_current` 时 `fit` 一律 false（22 条）
2. SYS_TMPL 明确写「fit 只在 ask_current 时为 true」「intent 不要填 fit」
3. 模型输出非法 intent 时，**不再丢整条推理** —— 保留 topic/fit

第 3 条很重要：原来 `ok=False` 会让调用方走「模型不可用，全规则降级」，
把 topic 和 fit 一起丢了。但那两个字段合法且有用
（`fit:true` 正是"在问用途匹配"的信号）。

**结果**：重建后 fit 错配 **0 条**，4 条相关错误自然消失。

### ② 边界样本要成对给，不能只给正例

新增 155 条，重点是**对照**：

| 类型 | 条数 | 教什么 |
|---|---:|---|
| 「有没有XX牌」 | 92 | 换品牌 = 换台，不是问当前这台 |
| 「还有X吗」 | 18 | 换台 vs 要全部清单 |
| 计数类 | 15 | 「联想有几台」→ analyze |
| 「预算卡死X」 | 10 | 明确给预算 → state_new_need |
| 装机语境 | 10 | 「一套下来多少钱」→ 装机，不是问单价 |
| 纯指示词 | 10 | 「那个」→ unknown |

「还有X吗」这条给的是**成对样本**：

```
还有别的吗 / 还有其他的吗 / 这个价位还有别的不  → refuse_switch
全部列出 / 都列出来 / 剩下的都给我              → list_others
```

只给一边，模型学不会分界；两边都给，它才知道判据在哪。

### ③ 台式品类词：加了保守的规则兜底

v8 把这几句判成 `refuse_switch`：

```
台式机 / 要台式机 / 桌面机行吗 / 得有台式
```

端到端行为是对的（走 `build_pc`），但**意图标签错**。

模型为什么判错：训练数据里「换个台式的」这类带"换"字的
和纯"台式"句混在一起，模型学到「台式 → 倾向换台」。

**规则兜底**（判据保守）：

```
台式词 + 模型判 refuse_switch + 无换台动词 → state_new_need

「台式机」            → 无换台动词 → 改 ✓
「换个台式的」        → 有"换"   → 不动 ✓
「不要笔记本了，台式」 → 有"不要" → 不动 ✓
```

同时修正测试集 1 条错标注：「换个台式的」标 `state_new_need` 是错的，
有"换个"就是换台。

## 五、训练期间顺手修的两个 bug

### Bug 1：analyze 极值答 8 万机器

日志实测：

```
用户: 最便宜的是哪台
回答: 最便宜的是联想拯救者 创世 Ultra，售价 84999 元
```

池子里**真有**这台（顶配市场价确实 8 万+），数据没错。
错的是 analyze 在**整池**上排极值，没做合理性过滤——
8 万的机器当"最便宜"报给用户，比不回答还糟。

**修法**：新增 `_drop_price_outliers()`，top/bottom 查询时
排除「价格 > 中位数 × 6」的离群点。

```
池子 223 台，中位 ¥8,799，上限 ¥52,794
去掉 2 台：¥84,999 / ¥52,999 的拯救者创世 Ultra
修后 → ¥1,999 惠普11-F011TU ✓
```

为什么 ×6：能留下 4 万档的真·高端机，排除 8 万+ 的顶配/工作站。
为什么用中位数：均值受离群点自身影响。

### Bug 2：审计层误报「库外机型:['拯救者']」

**根因是查错了数据源**：

```python
check_outside_products 用 core.load()["offers"]   ← 34 条（早期手写示例）
agent 实际推荐用      core.pool_offers()          ← 223 台
```

拯救者在真正的池子里有 **42 台**，但不在那 34 条里
→ 被 `OUTSIDE_BLACKLIST` 命中 → 误报"库外"。

**危害不只是日志噪音**：审计层对正确回答报警，可能触发重写把好答案改坏。

**为什么之前没暴露**：`OUTSIDE_BLACKLIST` 里的词
（XPS/ThinkPad/外星人…）大部分确实不在库里，平时不报错。
只有拯救者、ROG 这类近年进了池子的系列才暴露。

## 九、训练速度为什么会变慢（顺手记下来）

v7 是 6.3 秒/步，v8 是 12.4 秒/步。查下来：

```
显存占用  7.25 / 8.19 GB（88%）
GPU 利用率 50% 左右
功耗      40-60W（上限 71W）
```

**典型的显存不足导致 GPU 空转**：显存吃满后 PyTorch 频繁做
显存整理和碎片回收，GPU 等内存的时间比算的时间还多。

原因：条数几乎一样（1381 vs 1382），但**句子变长了**
（新增大量带思维链的边界样本，CoT 比例 31% → 35%）。

`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` **两轮都没生效**
—— Windows + 这个 PyTorch 版本不支持，日志里都有
`not supported on this platform`。

下次如果还要提速，可以考虑降 `max_length`（512 → 384），
但会截断长样本、影响 CoT 学习效果。这次为了效果没动。
