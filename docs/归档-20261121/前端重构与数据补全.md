### 1.4 踩的三个坑（都很隐蔽）

#### 坑 1：替换脚本把 `:root` 里的定义也改了

```
第一版结果：--bg: var(--bg);  --surface: var(--surface);  …
→ 31 个变量自引用 → 整个样式崩掉
```

**根因**：正则替换没排除 `:root` 块内部。

**修法**：先切出所有 `:root{...}` 块原样保留，只替换块外部分。

#### 坑 2：`var` 声明遮蔽了 `defineProperty` 访问器

```js
// 我写的兼容层
Object.defineProperty(window, 'slots', {get(){return S.slots}, set(v){S.slots=v}});
var slots, asked, seen, ...;   // ← 这行让 window.slots 变成 undefined
```

**根因**：`var` 在 IIFE 内声明了局部变量，遮蔽了 window 上的访问器。

**修法**：删掉 `var` 声明，靠未声明标识符向上找 window。

#### 坑 3：`refresh.js` 的 `$ is not defined`（**原版就有的 bug**）

```
原版 index.html 里两个 <script> 各自是 IIFE：
  第一个定义 var $ = ...
  第二个用 $('...')
→ 作用域不共享 → 刷新面板一执行就 ReferenceError
→ **刷新功能其实一直是坏的**
```

**修法**：
- `app.js` 末尾 `window.WB = {apiCall, wbHeaders, toast, esc, money}`
- `refresh.js` 自带 `$` 工具，从 `window.WB` 取其余

## 二、数据补全

### 2.1 先纠正一个误判

我以为 `screenSizeIn` / `refreshHz` / `colorGamut` 覆盖率是 0%。
**实际上它们 100% 覆盖，只是在 `screen` 子对象里，不在顶层。**

```
machine_pool.json 里 screen 子字段：
  sizeInch     243/243
  widthPx      243/243
  heightPx     243/243
  refreshHz    243/243
  panel        242/243
  colorGamut   191/243
```

**真正 0% 的是**：`ports`、`cooling`、`brightness`、`dGPU`。

### 2.2 补全结果

| 字段 | 补前 | 补后 |
|---|---:|---:|
| `ports`（接口） | 0% | **91.5%**（204 台） |
| `cooling`（散热系统） | 0% | **29.1%**（65 台） |
| `brightness`（亮度） | 0% | **39.9%**（89 台） |
| `dGPU`（独显直连） | 0% | **25.1%**（56 台） |
| `screen`（结构化屏幕） | 0% | **100%** |

### 2.3 关键教训：写对位置才算补上

第一版补全脚本把字段写到**顶层**：

```python
patch["screenSizeIn"] = 16.0     # ← 顶层
```

但 `_pool_to_offer` 读的是 `m["screen"]["sizeInch"]`。**数据进了 json，core 读不到，覆盖率还是 0。**

第二版改成：

```python
sc = m.setdefault("screen", {})
sc["sizeInch"] = 16.0            # ← 子对象
patch["screen.sizeInch"] = 16.0  # patch 用点号键，落盘时拆开
```

### 2.4 补投影：数据有了还要传到 offer

`_pool_to_offer` 原来没投影 `ports`/`cooling`/`brightness`/`dGPU`/`screen`，
上层拿不到 → 用户问「接口够不够」只能答"没记录"。

补投影后覆盖率才有意义。

## 三、让模型真正回答（不是规则）

### 3.1 先量化：模型 vs 模板

```
预算8000打游戏       模型调用 4 次（有返回 4 次）  模板兜底 ✓ 没用
预算6000轻薄本上课用   模型调用 4 次（有返回 4 次）  模板兜底 ✓ 没用
学设计的，预算7000    模型调用 2 次（有返回 2 次）  模板兜底 ✓ 没用
```

**结论：模型 100% 在工作，模板兜底一次都没用。**

所以「死板」不在输出层，在**数据没给到模型**。

### 3.2 三个主题从「空」到「有」

| 主题 | 补前 | 补后 |
|---|---|---|
| 屏幕 | 空 | `16 寸 2560×1600 OLED 240Hz / DCI-P3 100% / 500 nit` |
| 散热 | 空 | `显卡 TGP 115W（这是芯片功耗上限，不是整机功耗）` |
| 接口 | 空 | `USB-A ×2、USB-C ×1、雷电4 ×1` |

### 3.3 踩的两个坑

#### 坑 1：`elif` 插到了别的函数里

`_topic_facts` 里的分支被 edit 匹配到 `agent.py` 的另一处
（`is_relax_budget` 附近），导致新分支永远不执行。

**修法**：用脚本按 `_topic_facts` 函数边界定位插入点。

#### 坑 2：白名单没加新主题

`_topic_facts` 里有一个 `elif topic in ("售后", "做工", ...)` 白名单，
「屏幕/散热/接口」不在里面 → 走 else 兜底 → 裁空。

而且上面还有一段**更早的「屏幕」分支**只查 `pros/cons`，
我的新分支永远到不了。

**修法**：把三个主题加进白名单，删掉旧的屏幕分支。

### 3.4 路由修复：参数主题优先于 fit

**实测事故**：

```
问「接口够不够」→ 模型给 fit=True（理解成"问够不够用"）
→ L5908 的 `not ask_fit` 失败
→ 走 _answer_current（判用途匹配）
→ 答成整机配置，一个字没提接口
而数据里明明有「USB-A ×2、雷电4 ×1」
```

对比「屏幕怎么样」模型给 `fit=False`，正常走 followup，答得很好。

**修法**：

```python
_topic_now = _topic_of(user_text)
_is_param_topic = _topic_now in (
    "接口", "散热", "屏幕", "键盘", "续航", "重量", "颜色",
    "做工", "触控板", "性能", "内存硬盘", "充电")
if o and ask_detail and (not ask_fit or _is_param_topic) \
        and not _is_fit_question(user_text):
```

**判据**：「够不够」问的可能是参数够不够，不一定是用途匹配。
只要 `_topic_of` 认得出参数主题，就该按"问这一面"处理。

### 3.5 加 `_vague_praise` 判据

**实测**：问「散热行不行」，回答写了

> 「这台机器散热表现**中规中矩**」
> 「它作为游戏本的核心优势就是**能维持高负载下的性能释放**」
> 「这点是**符合预期**的」

每句都是凭定位猜的，但 `_praise_no_review` 抓不到
（它靠「细腻/通透/高端」这类具体形容词匹配）。

**修法**：新增 `_vague_praise`，抓「中规中矩/符合预期/核心优势/能维持」这类
**更隐蔽的措辞**。自测 7/7。

### 3.6 品类切换 bug

**实测**：已有 `cat=gaming`，用户说「轻薄本」→ `extract_slots` 正确抽到 `thin`
→ 但继承逻辑看到 `purpose` 里还有 `gaming`，**又改回 gaming**。

**修法**：

```python
_cat_from_user = bool(CAT_EXPLICIT.search(user_text or ""))
if "gaming" in _purpose_now and slots.get("cat") == "thin" \
        and not _cat_from_user:
    slots["cat"] = "gaming"
```

**判据**：用户明说品类 > 用途推断。

验证 4/4：

| 输入 | 期望 | 结果 |
|---|---|---|
| 轻薄本（已知 gaming） | thin | ✓ |
| 游戏本（已知 thin） | gaming | ✓ |
| 我想打游戏（已知 thin） | gaming | ✓ |
| 换轻薄本 | thin | ✓ |

## 四、整链对抗测试 `adversarial_v2.py`

### 4.1 与旧版的区别

| | `harvest_cot.py` | `adversarial_v2.py` |
|---|---|---|
| 测什么 | 只测意图分类 | **整条链**（意图→槽位→约束→筛选→审计→表达） |
| 用例来源 | 我手写的模板 | 本轮真实事故 |
| 失败样本 | 只记答案 | **记完整纠错思维链** |

### 4.2 结果：9/19 = 47.4%

**修复前 36.8%，修好 2 条后 47.4%。**

修好的 2 条：

| 句子 | 修前 | 修后 |
|---|---|---|
| 宿舍限电400瓦 | `state_new_need/battery/True` | `state_new_need/none/False` |
| 限电500W能用吗 | `state_new_need/config/True` | `state_new_need/none/False` |

**根因**：`classify()` 的限电规则只改了 `intent`，`topic`/`fit` 仍取模型值 ——
三个字段是一个整体，只改一个会自相矛盾。

**修法**：`why` 以 `rule:` 开头时（规则否决了模型），`topic`/`fit` 也用规则值。

### 4.3 剩余 10 条失败（全是模型判断错，已收训练集）

| 句子 | 期望 | 实际 |
|---|---|---|
| 接口够不够 | `ask_current/config/False` | `.../True` |
| 散热行不行 | `ask_current/noise/False` | `.../True` |
| 轻薄本 | `state_new_need/none` | `state_range/none` |
| 有没有机械革命的同配置的 | `ask_current/config` | `state_new_need/config` |
| 我是软件工程专业的，平时也喜欢打游戏 | `state_new_need/none/True` | `ask_current/none/False` |
| 平时主要打游戏 | `state_new_need/none/True` | `ask_current/none/False` |
| 主要用来剪视频和修图 | `state_new_need/none/True` | `.../config/False` |
| 再看看别的吧 | `refuse_switch` | `list_others` |
| 除了这台还有吗 | `list_others` | `refuse_switch` |
| 预算 5000，写代码 | `state_new_need/none/True` | `state_range/config/False` |

**观察到的模式**：
- **fit 污染**：3 条把用途陈述判成 `ask_current`（fit 值不对）
- **换台/列清单混淆**：2 条边界模糊
- **预算+用途**：`state_range` vs `state_new_need` 分不清

## 六、下一步

### P0：重训模型

### P1：`_answer_current` 的提示词要改

现在第 1 条硬规则是「第一句就回答系统判定」，
但问接口/散热时这个判定（匹配/不匹配）根本不相关。

虽然路由已经修好（走 followup），但如果某天又走回这条路，
提示词应该能自适应用户问的是参数还是用途。

### P2：把「数据补全」做成定期检查

本轮发现 `ports`/`cooling` 覆盖率低，是**手动查出来的**。
应该写个脚本定期报告覆盖率，低于阈值就告警。

### P3：`refresh.js` 的 bug 说明什么

原版刷新面板**一直是坏的**（`$ is not defined`），但没人发现 ——
因为没人点过那个按钮。

**教训**：拆文件时顺手跑一遍所有交互，能发现陈年老 bug。
