## 案例 1：品牌名被当成专业（最严重）

### 现象

用户实测日志第 1-8 条：

| 轮次 | 用户 | 专业（slots._majorName） |
|---:|---|---|
| 1 | 我是**软件工程**专业的… | 软件工程 ✓ |
| 2-7 | （继续对话） | 软件工程 ✓ |
| **8** | 有没有**机械**革命的同配置的 | **机械设计制造及其自动化** ✗ |

**用户从头到尾没说机械，是品牌名里的「机械」触发了专业匹配。**

### 思维链（我的排查过程）

```
① 先看日志：第 8 条 slots._majorName 变成「机械设计制造及其自动化」，
   而 known._majorName 是「软件工程」→ 本轮被覆盖了

② 查 match_major：
   core.match_major('有没有机械革命的同配置的')
   → ('机械设计制造及其自动化', '机械设计制造及其自动化')

③ 查专业索引，发现别名表里有一条：
   '机械' -> '机械设计制造及其自动化'
   而「机械革命」是笔记本品牌

④ 这和 2026-11-17 的「游戏」是同一类错误：
   '游戏' -> '游戏艺术设计'，导致「打游戏」被当成专业
   根因都是：**别名太宽，是日常词汇或品牌名的子串**

⑤ 为什么后果严重：
   专业决定硬约束（内存底线、要不要独显）
   软件工程 = 16G 起 + 要能加装
   机械设计 = 32G 起 + 要独显
   → 推荐逻辑整个变了，用户看到莫名其妙的要求
```

### 修法（两层）

**第一层：删宽别名，加精确别名**

```python
# 删掉
'机械' -> '机械设计制造及其自动化'      ❌ 品牌名子串

# 换成
'机械设计' -> '机械设计制造及其自动化'   ✅
'机械制造' -> '机械制造及自动化'        ✅
'机械电子' -> '机械电子工程'           ✅
'机械制图' -> '机械设计制造及其自动化'   ✅
'农机'    -> '农业机械化及其自动化'     ✅
'农业机械化' -> '农业机械化及其自动化'   ✅
```

**验证 5/5**：

| 句子 | 期望 | 结果 |
|---|---|---|
| 有没有机械革命的同配置的 | 不匹配 | ✓ |
| 机械革命性价比高吗 | 不匹配 | ✓ |
| 我是学机械设计的 | 机械设计制造及其自动化 | ✓ |
| 机械制图要跑CAD | 机械设计制造及其自动化 | ✓ |
| 农业机械化 | 农业机械化及其自动化 | ✓ |

**第二层：已确定的专业不许被单轮覆盖**

```python
_MAJOR_DECLARE = re.compile(r"(我是学|我学|我专业是|我读|就读|学的|专业是|主修)")
if g and known and known.get("_majorId") and g.get("id") != known.get("_majorId"):
    if not _MAJOR_DECLARE.search(user_text or ""):
        # 不是明确声明换专业 → 保留原来的
        g = <known 的专业>
```

**为什么加第二层**：就算别名修对了，用户也可能在对话里**引用**别的专业名
（「我室友学机械的，他那台怎么样」）。只有明确声明才允许改。

## 案例 2：品牌串台（把惠普说成机械革命）

### 现象

同一轮（第 8 条），模型回答里写：

> 「这台机器属于**机械革命**暗影精灵系列」

但暗影精灵是**惠普**的产品线。

### 思维链

```
① 数据核对：core.get_offer(...).brand = '惠普'  ← 数据是对的
② 所以是模型编的，不是数据错
③ 为什么编：用户上一句问「有没有机械革命的…」，
   模型把刚听到的品牌名安到了当前机器上
④ 为什么危险：品牌归属决定售后/保值判断，说错了直接误导决策
   而且读起来毫无破绽 —— 不熟这两个品牌的用户发现不了
```

### 修法：加 `_brand_mismatch` 判据

```python
# 归属句式：这台/该机/它 + (可选品类词) + 属于/是/来自/出自
pat = re.compile(
    r"(?:这台|该机|这款|它|本机|此机)"
    r"(?:机器|笔记本|电脑|机型)?"
    r"(?:属于|是|来自|出自|为)"
    r"([\u4e00-\u9fa5A-Za-z]{2,10})")
```

**关键区分**：只查**品牌名**，不查产品线名。
「属于暗影精灵系列」是对的（暗影精灵是系列，不是品牌）。

**自测 7/7**：

| 文本 | 期望 | 结果 |
|---|---|---|
| 这台机器属于机械革命暗影精灵系列 | 抓 | ✓ |
| 这台属于机械革命 | 抓 | ✓ |
| 该机来自联想 | 抓 | ✓ |
| 这台是惠普的机器 | 放行 | ✓ |
| 它属于暗影精灵系列 | 放行 | ✓ |
| 这台机器的品牌是惠普 | 放行 | ✓ |
| 它搭载 R9 处理器 | 放行 | ✓ |

### 踩的坑：第一版正则抓不到

```python
# 错：{0,6} 贪婪吃掉了「属于」
r"(?:这台|该机)[^。；\n]{0,6}(?:属于|是|...)"
# 「这台属于机械革命」→ 匹配失败
```

改成把中间收窄成"可选的品类词"：

```python
r"(?:这台|该机|...)(?:机器|笔记本|电脑|机型)?(?:属于|是|...)"
```

## 案例 3：限电 400W 记了但没回应

### 现象

日志第 4 条：

```
U: 宿舍限电400瓦
stage=recommend
A: 暗影精灵11 锐龙版…按你的专业要求：软件工程（编程数据组）…
   ← 一个字没提限电
```

### 思维链

```
① 用户给了具体约束（400W），系统 stage 是 recommend（有重推），
   说明槽位可能抽到了
② 但回答里完全没提限电 —— 用户会以为系统没听见
③ 对比 2026-11-17 修的「限电 500W」：
   那次是 fit 分支被 detail 截胡，答了屏幕参数
   这次是 recommend 分支，专业要求念了一遍，限电没提
④ 共同点：**槽位抽到了，但回答没体现**
⑤ 根因：限电的事实通道只在 _answer_current 里加了，
   recommend 路径（compose）没有
```

### 修法

`compose()` 的 `_audit` 加了 `power=_power_guess(t)`，
但**事实通道**（告诉模型该怎么说）还没加到 compose。

**待办**：把「有 dormWatt 时补一句」的逻辑也加到 `compose()`。

## 这三个案例的共同教训

| 案例 | 表面现象 | 真正根因 | 教训 |
|---|---|---|---|
| 1 | 专业变了 | 别名是品牌名子串 | **别名表要防日常词/品牌名** |
| 2 | 品牌说错 | 模型把刚听到的词安到当前对象 | **归属类事实要单独判据** |
| 3 | 没回应用户 | 事实通道只加在一条路径 | **同一机制要覆盖所有输出路径** |

### 通用判据（写进 AGENTS.md 值得）

1. **别名/触发词表里不许有"能出现在品牌名/产品名里的词"**
   - 反例：`'机械'`（机械革命）、`'游戏'`（游戏本）
   - 自查方法：把别名和所有品牌名做子串比对，有交集就报警

2. **用户提过的实体 ≠ 当前讨论的实体**
   - 模型容易把上一句听到的词安到当前对象上
   - 要有判据专门查"归属/来源"类陈述

3. **同一机制必须覆盖所有输出路径**
   - 这个项目有 4 条路径（compose / followup / answer_current / intro）
   - `audit_matrix.py` 就是为此写的，但**事实通道**（给模型看的指令）
     还没有类似的覆盖检查
