## 一、这一轮到底改了什么（按重要性）

### 1.1 找到「很死板」的真正根因（最重要）

用户说回答 low、死板。查下来**不是模型不会说，是它说的话被整段删了**。

实测链路（`预算8000打游戏`）：

```
模型第一次输出：
  「它属于高配游戏本，适配 240Hz 高刷新率屏幕，适合对画面流畅度
    有要求的玩家。适配器标称 280W，但整机实际功耗数据未记录…」

审计判定：
  power='整机功耗数字'   ← 误杀：模型说的是"未记录"
  untr=[280]            ← 误杀：这台 adapterW=None，280 确实是编的
  bad=['保修','充电器']  ← 误杀：模型说的是"没有记录保修""只有充电器功率"

旧逻辑：命中 → txt = template_reply(first)  ← 整段扔进垃圾桶
结果：用户看到 117 字的干巴配置罗列
```

**三处误杀，一处整段丢弃。**

### 1.2 三处修复

| 问题 | 修法 | 位置 |
|---|---|---|
| 诚实声明被判成编造 | `check_fabrication` 加**分句级否定语境检测** | `agent.py` |
| 「适配器标称 280W」被判成推测整机功耗 | `_power_guess` 加诚实声明排除 + 适配器限定词放行 | `agent.py` |
| 命中就整段换模板 | 新增 `_strip_violations`，**只删违规句**，保留其余 | `agent.py` |

**效果：117 字 → 271 字，模型的表达留住了。**

### 1.3 专业要求的 GPU 约束从来没生效

用户实测：车辆工程专业（要求独显 4G 起），系统回答里**自己都说**
「要独立显卡（4G 显存起）」，却连续推荐两台核显机。

根因：`req.gpu` / `req.vramMin` / `hardGates[dim=gpu]` 三项
**只被用来拼文案**，从没落进 slots 当筛选条件。

修法：
1. `agent.py` 把 GPU 要求落成 `_wantDgpu` + `_minVram`
2. `core.build_recommendation` 真正过滤
3. `_minVram` 加进 `HARD_KEYS`（跨轮继承）

**判据演进（第一版错了，记下来）**：
- 第一版只排除 `gpu_igpu(o)`（`gpuKind=='integrated'`）
- 结果 Redmi Book Pro 14 被放行 —— 它的 `gpuKind` 是 **None**
  （人工层 34 台全都没有 GPU 字段）
- 改成 `has_dgpu(o)` 前先量了风险：
  采集层 `gpuKind=discrete` 的 129 台，`has_dgpu` 全部 True
  → 误杀台数 = **0**

### 1.4 「换一台」死循环复发（测试自己抓到的）

`test_chain.py` 一跑就报「换台后还是同一台」。

查下来：**是测试的 bug，不是产品的** ——
`run()` 靠 `seen` 参数才能排除看过的机器，测试没传。

传了之后正确换台（暗影精灵 → 极光X）。

### 1.5 限电 bug 复发（第二次了）

「宿舍限电400瓦」又被判成 `ask_current/battery`。

**为什么复发**：2026-11-17 修的是**训练集**（加了样本），
但模型没重训 → 行为没变。

**这次真正修好**：在 `classify()` 里加**规则兜底**：

```python
if re.search(r"(限电|供电|插座|跳闸|功率限制|限功率)", t) and \
        re.search(r"\d+\s*[Ww瓦千]|[一二三四五六七八九十百]+\s*瓦", t):
    return INTENT_STATE_NEW_NEED, "rule:限电/供电约束（补充条件）"
```

**教训（写进文档了）**：
> 光有训练样本不够。高频且判据明确的句子必须有规则兜底 ——
> 这正是「模型为主、规则兜底」的正确用法。

## 二、新增：整链对抗测试 `test_chain.py`

### 2.1 为什么要有

用户原话：「这时候的对抗测试才是有意义的，而且是一条链条的训练」

现有测试各测一段，但**真实事故都发生在衔接处**：

```
用户原话
  ↓ ① 意图     intent 判对了吗（模型）
  ↓ ② 槽位     cat/budget/purpose/专业 抽对了吗（模型+规则）
  ↓ ③ 约束     专业要求落成硬约束了吗（规则）
  ↓ ④ 筛选     选出的机器满足约束吗（规则）
  ↓ ⑤ 审计     回答没被误杀吗（规则）
  ↓ ⑥ 表达     回答包含该说的信息吗（模型）
```

**任何一环断了，整条链就是错的。**

### 2.2 六条用例（全部来自真实事故）

| 用例 | 来源事故 |
|---|---|
| 车辆工程→要独显 | 2026-11-18 推荐核显机 |
| 软件工程→问机械革命 | 2026-11-18 专业被覆盖 |
| 限电约束 | 2026-11-17 答非所问 |
| 换台不重复 | 2026-11-17 死循环 |
| 诚实声明不被误杀 | 2026-11-18 回答太短 |
| 品牌归属不许串 | 2026-11-18 机械革命暗影精灵 |

**13 个断言点，全绿。**

## 五、关于「模型为主，规则兜底」的边界（这次想清楚了）

用户反复强调这一点。**这次终于能说清边界在哪**：

| 环节 | 谁说了算 | 为什么 |
|---|---|---|
| 理解用户说什么 | **模型** | 用户说法无法穷尽，规则必然有限 |
| 抽槽位（专业/用途/预算） | **模型 + 规则校验** | 模型抽，规则防明显的（如"机械革命"不是专业） |
| 专业要求 → 硬约束 | 规则 | 这是查表，不需要模型 |
| 选哪台机器 | **代码排序** | 约束求解，模型会编（历史上编过"这是最贵的"） |
| 怎么说 | **模型** | 表达是模型强项 |
| 说了什么不该说的 | 规则审计 | 出口必须拦编造 |

**关键洞察**：用户说「都交给模型」是对的，
但**「选机器」不是「理解用户」** —— 那是约束求解。
模型在这里没有优势，反而有编造风险（历史事故）。

真正该扩大模型权限的是**前三环和最后一环**，
而不是让它去算"哪台满足 32G + 独显 + 7500"。

### 但这次确实扩大了模型的表达空间

`_strip_violations` 的意义就是：**不再因为一句话有问题就否定整段**。
这是把表达权还给模型的实际动作。

## 七、关键技术发现（别再踩）

### 7.1 `think=False` 必须显式传

`qwen3.5-4b` 默认开 thinking，而且**thinking 会无限自我怀疑**：

```
探测实测（num_predict=1600）：
  done_reason: length
  eval_count: 1600
  thinking 长度: 4109 字
  content: ""          ← 空的！
  thinking 结尾：「Okay, I'll go with this」← 想好了但就是不输出
```

**项目里 `chat()` 已经有 `"think": False`**（L3572），所以主链路没问题。
但**任何绕过 `chat()` 直接调 API 的地方都会中招**。

### 7.2 `tasklist` 输出不许按位置解析

2026-11-18 上午踩过（停止服务时杀 Ollama）：

```
第一版取 parts[1] → 'ollama app.exe' 名字带空格，parts[1] 是 'app.exe'
第二版从后往前找纯数字 → 取到 Session# 的 '9'，杀不存在的 PID
第三版：taskkill /F /IM，按映像名杀
```

### 7.3 日志是 UTF-16

PowerShell `Tee-Object` 默认写 UTF-16 LE（BOM `0xff 0xfe`）。
Python `io.open(encoding="utf-8")` 读会抛异常，**而且不报错**。

`training_record.py` 和 `watch_training.py` 都有 BOM 自动识别。
