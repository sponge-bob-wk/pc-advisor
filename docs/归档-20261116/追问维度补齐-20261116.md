>
> 查下来不是没数据 —— **数据早就抓回来了，只是没映射进池子**。

---

## 1. 根因：参数页里有，映射表漏了

`data/zol/params-2026-11-16.jsonl`（163 台参数页原始记录）里：

```
保修相关键: [('保修政策', 60), ('质保时间', 60), ('质保备注', 38)]
```

**60 台有「质保时间 = 2年」**，但 `zol_map_fields.py` 的映射表没收录这个键，
所以池子里 `warrantyYears` 一台都没有 → 问「保修几年」只能答不知道。

顺着把参数页**所有键**扫了一遍，发现不止保修：

| 参数页键 | 覆盖台数 | 用户会问 |
|---|---:|---|
| `保修政策` / `质保时间` | 60 | ✅「保修几年」 |
| `续航时间` | 84 | ✅「能用多久」 |
| `厚度` | 130 | ✅「厚不厚」 |
| `触控屏` | 121 | ✅「能触屏吗」 |
| `操作系统` | 157 | ✅「带不带 Windows」 |
| `蓝牙` / `无线网卡` | 152 | ✅「有蓝牙吗」 |
| `摄像头` | 146 | ✅「摄像头多少像素」 |
| `扬声器` / `音频系统` | 147 | ✅「音质怎么样」 |

**这些都不是"要不要加"的问题，是"已经抓到了却没接上"。**

## 2. 做了什么

### 2.1 新增 `fill_extra_fields.py`

从参数页补 15 个维度进池：

```
bluetooth        153 台    touchScreen     121 台
wifi             152 台    shellMaterial    98 台
speakers         147 台    gpu.vramType     95 台
webcam           146 台    warrantyYears    60 台
keyboard         140 台    warrantyPolicy   60 台
audioSystem      132 台    warrantyNote     38 台
                           batteryLifeH     34 台
```

保修年限分布：`2年 34 台 / 1年 25 台 / 3年 1 台`。

### 2.2 打通四层（每层都漏了）

| 层 | 问题 | 修法 |
|---|---|---|
| 数据 | 池子里没有这些字段 | `fill_extra_fields.py` 补录 |
| `core._pool_to_offer` | 池→offer 没透传 | 加 15 个 `.get()` 字段 |
| `agent.answer_followup` | 没传给模型 | 加 15 个键（键名用中文人话） |
| `agent._topic_facts` | 只从 pros/cons 裁，读不到结构化字段 | 加「售后」「做工」两个主题，直接从字段取 |

### 2.3 三处硬编码把答案拦掉了

**① `_topic_facts` 没有「售后」主题**

原来注释写「service 的事实散在各面里，映射到 None 让回退逻辑原样返回全部优缺点」。
但 `pros` 里根本没有保修信息 —— 那是结构化字段。所以永远裁空 → 回退 → 答"没记录"。

新增 `TOPIC_TRIGGER["售后"]`，并在 `_topic_facts` 里直接从
`warrantyYears / warrantyPolicy / warrantyNote` 拼事实。

**② `_warranty_stretch` 审计误判**

这个审计函数防的是「把'一年上门保修'这项服务说成'整机保修一年'」。
判据是：`corpus` 里有「保修一年」字面串才放行。

但我们数据是 `warrantyYears=1` + `warrantyPolicy="全球联保"`，
**语料里没有「保修一年」这四个字** → 永远判成扩大 → 触发重写 →
重写后输出"库里没记录"。

修法：结构化字段有值就放行（参数页写的质保年数比语料描述更权威）。

**③ 兜底模板只看 `pros`**

```python
svc = [p for p in (m.get("pros") or []) if "保修" in p or "售后" in p]
if not svc and not note:
    parts.append("保修年限这一项，库里对 %s 没有记录。")
```

这段不认新字段。改成：结构化字段优先，有就直接报。

## 3. 顺带修的：模型念字段名

首版输出「质保年数为 1.0 年」「支持触控：否」——字段名口吻。

在 `FOLLOWUP_SYS` 加了 2b 条：

```
说人话，不要念字段名：
  「质保年数为 1 年」→ 应该说「整机质保 1 年」
  「支持触控：否」  → 应该说「不支持触控」
  「续航_小时：5」  → 应该说「续航大约 5 小时」
```

## 5. 回归（这次两个测试都拦住了我）

```

```

### `test_weight` 的 W8 拦了一次

我在「做工」主题里写了 `m["weightKg"]`，W8 结构性检查立刻报错。
改成 `core.effective_weight(m)` 后恢复。

### `test_neg` 拦了两次，第二次我才看对

**第一次**：新增的「做工」主题触发词里有「手感」，把「键盘手感」抢走了
（那应该是键盘面）。删掉「手感」，只留材质类词。

**第二次**：判据改完后还失败。查了半天发现 **`run_case` 的第二个参数语义**我理解反了 ——
它是「文本是否包含某词」，不是「判据是否报错」。

更关键的是：**`gaming-tianxuan7` 是人工层那台，有 pros 但没键盘数据**，
走的是「库里跟这一项相关的只有这些：…」这条**划清界限**的分支，
而不是采集池那台的「要看实机」分支。

判据要同时认两种诚实兜底形态。这个细节写进注释了。
