## 1. 去掉免责措辞

用户原话：

> 「使用的时候不用标注什么人工不人工的，做项目都是为了毕设的，
>   数据虽然不是顶尖质量，也是咱自己爬取的」

### 改了什么

**保留的约束不变**（这些是红线）：
- 不许编观感评价（「细腻」「通透」「跟手」）
- 不许判断市场定位（「入门级游戏本」「主打性价比」）
- 不许提保值率（库里没这数据）
- 不许说「不算便宜」「值得买」

**去掉的**：那句「这台我库里没人评过，我只按参数说」。

改法：15 处提示词/文案里的免责声明统一换成「不要解释数据来源」。
用一次性脚本 `_soften_wording.py` 做精确替换 + 改完复核，避免手工改漏。

### 两处测试也改了（这是需求变更，不是代码 bug）

| 测试 | 原判据 | 新判据 |
|---|---|---|
| `test_answer.py` I2 | 必须含「没人评过」 | 不许出现空模板（`缺点是：` / `为空`） |
| `test_neg.py` | 必须说清「没人评过用起来怎么样」 | 不许出现空模板 |

**注意**：这是把免责声明从"必须说"降级为"可以说"，
但「不许把参数当评价」的判据一个字没动。

### 效果

改前：
```
这台机器目前库里还没有人写过具体的优缺点评价。
这台库里没人写过优缺点，只有配置和价格。
```
改后：
```
它的平台标价是 9188 元，属于 9000 元价位段中配置较高的机型。
```

### 第一轮漏了前端和字段卡（2026-11-16 晚补）

用户反馈「还写着有人写过优缺点」—— 我第一轮只改了 `agent.py` 的提示词，
**前端和字段卡没改**。补的范围：

| 位置 | 原来 | 现在 |
|---|---|---|
| 首页三个数字卡 | 「有人写过优缺点」22 | 「有跑分实测」174 |
| 首页口径段 | 「只有 22 台逐台核对过优缺点…其余 217 台没人写过评价」 | 「174 台有 CPU 跑分实测、190 台有实测重量」 |
| 右栏「库构成」 | 有人写过/仅参数 双色条 | 「数据覆盖」跑分/重量覆盖 |
| 右栏「当前这台」 | 「评价：有人写过优缺点/库里没人评过」 | 「价格口径：到手价/平台快照价」 |
| 候选列表标记 | 「仅参数」 | 「快照价」 |
| 字段卡一行 | 「评价：库里有人写过优缺点/只报参数」 | 「价格口径：到手价/平台快照价」 |
| 首轮推荐尾巴 | 「这台的评价库里还没有 —— 上面这些是配置和价格」 | 直接删掉 |
| 列表页每台 | 「这台库里没人写过优缺点，只有配置和价格」 | 直接删掉 |

**为什么换成「价格口径」**：用户真正需要知道的是「这个数字是到手价还是平台快照价」，
两者含义完全不同（一个能直接比预算，一个不能）。这比"有没有人评过"有用得多。

后端配套：`server.py` 的 `/api/model` 投影里补了 `priceIsEstimate`
（原来没传，前端判断永远是 `undefined`，标记不会显示）。

## 2. 刷新数据：点按钮 → 自动抓 → 交叉验证

### 2.1 为什么是「触发 + 轮询」而不是同步等

全量抓取要 3-5 分钟，HTTP 请求早超时了；而且刷新时用户还可能在对话，
不能把界面卡住。

```
前端                          后端
  │  POST /api/refresh          │
  │  {preset:"prices"}          │
  │ ──────────────────────────> │  立刻返回 jobId
  │ <────────────────────────── │
  │                             │  后台线程跑步骤
  │  GET /api/refresh/status    │
  │  ?job=xxx   （每 1.5s）      │
  │ ──────────────────────────> │
  │ <────────── progress/steps  │
```

### 2.2 步骤与依赖（`refresh_engine.py`）

| 步骤 | 脚本 | 干什么 | 依赖 |
|---|---|---|---|
| `prices` | `price_multisource.py` | 抓 ZOL 详情页价格 | — |
| `apply_prices` | `apply_prices.py` | 写进池（不碰 net/final） | prices |
| `bench` | `bench_fetch_nbc.py` | 抓 Notebookcheck 跑分 | — |
| `apply_bench` | `bench_merge_nbc.py` | 合并（带 aggregated 标记） | bench |
| `verify` | `verify_bench.py` | 跑分交叉验证 | apply_bench |
| `notes` | `derive_notes.py` | 从规格推导客观提示 | — |
| `fix_weight` | `fix_weight_unit.py` | 修重量单位错 | — |
| `stats` | `refresh_stats.py` | 重算统计 | notes, fix_weight |
| `coverage` | `coverage.py` | 重算判定覆盖率 | stats |
| `pages` | `make_pick_page.py` | 重建静态页 | coverage |

**四个预设**（前端按钮给的粒度）：

| 预设 | 步骤 | 耗时 |
|---|---|---|
| `quick` | 不联网，只重算 | ~2 秒 |
| `prices` | 抓价格 + 重算 | 1-3 分钟 |
| `bench` | 抓跑分 + 重算 | 1-2 分钟 |
| `full` | 全部 | ~5 分钟 |

### 2.3 交叉验证（用户明确要求）

刷新跑完自动做一次核对，四项：

```
[ok] 价格：76 台到手价、147 台平台快照价
[ok] 跑分：R23 覆盖 50 颗、GB6 16 颗、可做交叉验证 16 颗
[ok] 缺口：perf 缺 61、weightKg 缺 34、price 缺 0
[ok] 可答缺点：222 / 223 台
```

**口径纪律**：交叉验证**只对同一字段的同一量纲**做。
不会拿「ZOL 参考价」去核「京东到手价」——那两个本来就是不同口径，
强行比会制造假冲突（见 `AGENTS.md` §5.2）。

## 3. 做这个功能时踩的五个坑

### 坑 1：预设依赖不闭合 → 整条链被跳过

首版 `quick = ["notes","stats","coverage"]`，但 `notes` 的 `depends=["apply_prices"]`，
而 `apply_prices` 不在 `quick` 里 → 三步全被「依赖未成功」跳过，**什么都没干**。

修法：① 每个预设必须依赖闭合；② `notes` 其实不依赖价格抓取（它只读规格字段），
`depends` 改成空。加了自检：

```
quick    5 步  OK
prices   6 步  OK
bench    7 步  OK
full    10 步  OK
全部闭合: True
```

### 坑 2：脚本不在同一目录

`derive_notes.py` 在 `tools/agent/`，其他脚本在 `tools/`。
首版按 `tools/` 找，报「脚本不存在」。加了 `where` 字段区分。

### 坑 3：前端用相对路径，没有 `API` 前缀

项目里所有请求都是 `fetch('/api/xxx')`，我写了 `fetch(API+'/api/xxx')`。
`API` 变量不存在 → 全部 404。

### 坑 4：统计刷新函数名写错，而且静默失败

```js
if(typeof loadOverview==='function') try{ loadOverview() }catch(e){}
```

函数实际叫 `facts(ov)`，`typeof` 判断让它**静默跳过** —— 顶栏数字永远停在刷新前。
这类"防御性判断"掩盖了真 bug，改成直接调用 + try。

### 坑 5（最严重）：顺手抓到一个真实数据错误

做交叉验证时输出：

```
带出门这件事：这台 1.09 kg；同品类同预算里记了实测重量的 28 台，
             最轻 1.07 kg、最重 1000 kg。
```

**1000 kg 的笔记本**。查下来 7 台是「克当成千克」：

```
戴尔XPS            1000.00 kg → 1.00 kg
ThinkPad           992.00 kg → 0.99 kg   (×3)
机械革命星耀14      1000.00 kg → 1.00 kg
华为MateBook Pro S   798.00 kg → 0.80 kg
微软Surface Pro      890.00 kg → 0.90 kg
```

根因：ZOL 参数页写「笔记本重量 992g」，解析时取了数字没换算单位。

新增 `fix_weight_unit.py`，判据是现实区间：
- `> 30kg` → 一定是单位错，`/1000`
- `4.5~30kg` → 可疑（台式整机可能），只报告
- `< 0.5kg` → 可疑（可能单位是磅/斤），只报告

修完最重是 `华硕GFX71JT4710` 4.8kg —— 那是真实的 17.3 寸老游戏本，不是错。

## 6. 怎么用

```bash
cd tools/agent
python server.py          # 起服务（7860）

# 浏览器打开 http://127.0.0.1:7860
# 右上角「↻ 刷新数据」→ 选粒度 → 看进度和交叉验证结果
```

命令行也可以：

```bash
python refresh_engine.py --dry --preset prices   # 看会跑什么
python refresh_engine.py --preset prices         # 真跑（前台等结果）
```

API：

```bash
curl http://127.0.0.1:7860/api/refresh/options        # 有哪些预设
curl -X POST http://127.0.0.1:7860/api/refresh \
     -H 'Content-Type: application/json' -d '{"preset":"prices"}'
curl 'http://127.0.0.1:7860/api/refresh/status?job=xxx'
```

**并发保护**：同一时刻只允许一个刷新（两个进程同时写 `machine_pool.json` 会打架）。
再触发会返回 409 + 正在跑的 jobId。
