# 跑分覆盖提升（2026-11-16 晚）

> 起点：推荐池 223 台，有跑分 131 台（**58.7%**）。
> 结果：有跑分 **162 台（72.6%）**，无跑分 92 → 61 台。
> 净增 31 台，全部带来源留痕。
> **附带产出：交叉验证第一次有了可信结论（rho 0.500 → 0.947）。**

---

## 0. 三个额外发现（比覆盖率本身更重要）

### 0.1 交叉验证的 rho=0.500 是假的

`verify_bench.py` 原来报「样本 3 颗、rho = 0.500、严重不一致」。
交接文档据此写下「GB6 样本 3 颗时算的 rho 没有意义」。

**真实原因是字段名不一致**：脚本读 `geekbench6`，而 NBC 批量入库写的是 `gb6`。
两个都读之后：

```
样本 3 → 16 颗
rho  0.500（严重不一致）→ 0.947（一致，数据可信）
百分位差：全部 16 颗都在 30 以内（最大 20，Ultra 7 356H）
```

**这是本项目第一次有足够样本量支撑的交叉验证结论。** 之前那句"数据有问题"
是脚本 bug，不是数据问题。

### 0.2 三颗芯片「有原始分但没算 perf」

```
i5-14450HX   R23 1838/13881   perfCurrent = None
Apple M4     R23 2055/12100   perfCurrent = None
Apple M5     R23 2511/16014   perfCurrent = None
```

数据在库里，只是漏了换算，于是对应机器一直显示「无跑分」。
补算后 `bench.json` 的**无分芯片归零**（68 个有分键 / 0 个无分）。

### 0.3 `verify_bench` 把「功耗墙差异」误判成「数据错」

`Ultra 7 356H` 多核 9019~20298（差 60%）、`Apple M5` 单核 2080~2511（差 19%）
被判 FAIL，但它们的 `observedR23.detail` 里**早就写清了原因**：

```
Ultra 7 356H：ThinkPad X1 超轻薄（9019）vs 游戏本（20298）—— 功耗墙
Apple M5：IT之家接电 2511 vs specforge 欧洲机型 2080 —— 测试条件不同
```

交接文档 §5.3 自己写着「一颗 CPU 一个分数本身是错的」，
判据却把这种**正常现象**当不合格。

修法：`observedR23.detail` / `note` 里有解释的 → 最多 WARN（标注"已记录原因"），
没有解释且超限的 → 才 FAIL。结果：**不合格 2 → 0，注意 4 条全部带解释**。

## 2. 真正的卡点：三个，不是一个

写了 `bench_coverage.py` 把「无跑分」拆成三类，让下一步知道该修哪：

| 类 | 含义 | 初始 | 修完后 |
|---|---|---:|---:|
| A | 归一化能救（跑分表里有，只是写法不同） | 7 | **0** |
| B | 真的没这颗芯片（要补数据） | 71 | 49 |
| C | 型号不可用（系列名/空/非 x86） | 14 | 14 |

### 2.1 A 类：`_cpu_key` 归一化漏了两条规则

同一颗 CPU 有七八种写法，归一化没覆盖全：

```
酷睿Ultra 5 125H  → 'coreultra 5 125h'  ❌ 匹配不上 'ultra 5 125h'
U7-255HX          → 'u7 255hx'          ❌ 匹配不上 'ultra 7 255hx'
酷睿i5 12500H      → 'corei5 12500h'     ❌ 匹配不上 'i5 12500h'
英特尔 酷睿i5 12500H → '英特尔 酷睿i5 12500h' ❌ 中文前缀没剥
```

补了两条规则（`core.py::_cpu_key`）：

```python
s = re.sub(r"^(英特尔|intel)\s*", "", s)      # 剥厂商前缀
s = re.sub(r"^(amd|超微|苹果)\s*", "", s)
s = re.sub(r"^coreultra\s+", "ultra ", s)     # 酷睿Ultra → ultra
s = re.sub(r"^core\s*i([3579])", r"i\1", s)   # 酷睿i5 → i5
s = re.sub(r"^u([3579])\s*[-\s]\s*", r"ultra \1 ", s)  # U7-255HX → ultra 7
```

**只合并写法，不替换型号** —— `U7-255HX` 与 `Ultra 7 255HX` 是同一颗芯片的两种写法
（联想官网用 U 简写），但 `U7-255HX` vs `U7-256HX` 仍是两颗，不做模糊匹配。

效果：A 类 7 → 0，覆盖 58.7% → 60.5%。

### 2.2 B 类：Notebookcheck 现在可达了

交接文档说「国际跑分站全 000（Geekbench/3DMark/Notebookcheck/cpu-monkey）」。
2026-11-16 晚实测 **Notebookcheck 已可达（HTTP 200）**，这条路重新可用。

数据源：`https://www.notebookcheck.net/Mobile-Processors-Benchmark-List.2436.0.html`
（5.9MB 汇总表，569 颗 CPU）。

**跑分列是 CSS class 编码的**，不是文本表头：

| class | 基准 |
|---|---|
| `bv_768` | Cinebench R23（两个值 = 单核 / 多核） |
| `bv_967` | Geekbench 6 |
| `bv_244` | Cinebench R15 |
| `bv_552` | 7-Zip |

**一个坑**：值后面常带 `n8`/`n2` 后缀 —— 那是**样本数**，不是小数。
`1685.5n8` 必须剥掉 `n8` 再转 float，否则整批解析失败。

## 3. 入库纪律：`perfCurrent` 不许从别处抄

新增了 `bench_merge_nbc.py`，但它**不自己发明尺子**：

```
perf = 100 × (0.5×单核/2400 + 0.5×多核/40000)
```

这个公式来自 `prices.json` 的 meta（项目定的），脚本直接复用。
抓到的 NBC 数据先落到 `data/bench_nbc.json`（中间产物），
再由合并脚本算 perf 并写进 `bench.json` —— **两步入库，可回滚**。

每条都带：

```json
{"aggregated": true,
 "source": "Notebookcheck Mobile Processors Benchmark List",
 "sourceUrl": "https://www.notebookcheck.net/...2436.0.html",
 "capturedAt": "2026-11-16 20:49",
 "note": "跨机型聚合值（NBC 汇总表），不是单机实测"}
```

`aggregated: true` 是必须的 —— 交接文档 §5.3 记过「一颗 CPU 一个分本身是错的」，
Ultra 7 356H 多核从 9019 到 20298（差 2.25 倍）是功耗墙的真实差别。
NBC 给的是跨机型中位，**必须与单机实测区分开**。

## 8. 给下一个人的四句话

1. **交接文档 §5.4 的结论是错的** —— 不是"型号写得不清楚"，是"归一化漏规则 + 缺数据"。
   照旧文档回 ZOL 补型号，白干。
2. **`rho=0.500` 是脚本 bug，不是数据问题** —— 字段名 `gb6` vs `geekbench6` 不一致。
   修完是 16 颗样本、rho=0.947。**别再引用旧结论说"数据不可信"。**
3. **「有原始分」≠「有 perf」** —— 两件事。查跑分覆盖时要同时看 `bench.r23` 和
   `perfCurrent`，只补一个会留下"数据在库里但显示无跑分"的哑弹。
4. **离散度大 ≠ 数据错** —— 先看 `observedR23.detail` 有没有记录原因。
   功耗墙差异是真实存在的，判据把它当 FAIL 只会制造假警报。
