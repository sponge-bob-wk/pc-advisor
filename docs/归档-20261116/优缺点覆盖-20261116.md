# 让「问缺点」有答案（2026-11-16 晚）

> 问题：推荐池 223 台里只有 **34 台**有人工写的优缺点，其余 189 台
> 用户问「有什么缺点」只能答"没评价"——把最常见的追问挡在门外。
>
> 结果：**222/223 台**现在能答，且区分「人工评价」和「规格事实」两种口径。

---

## 1. 先试了两条"抓评测"的路，都不可靠

### 1.1 ZOL 点评页 —— 绝大多数机型没有

`detail.zol.com.cn/<id>/review.shtml` 能打开，但抓到的容器是：

```html
<div class="empty-comment">   ← 空态
```

实测多台都是空的。这条路覆盖不了。

### 1.2 ZOL 评测文章 —— 抽出来的不是本机缺点

`nb.zol.com.cn` 的评测文章能抓到正文，用「但/不过/不足」这类转折词抽缺点，
结果是这样的：

```
但这游戏对硬件要求不低，尤其是显卡渲染和CPU响应速度   ← 说游戏，不是说这台
但在CPU调度、屏幕素质和便携性上，各有各的好           ← 导购文的横向比较
```

而且这些文章多半是**多台机器的横向导购**，一句话里可能在说三台不同的机器。
硬抽等于把噪声当结论。

**结论：自动抽评测不可行。** 项目红线「没数据 ≠ 有数据」在这里是硬约束。

---

## 2. 换一条路：只陈述「规格里的事实」

人工层的 103 条缺点，主题分布是：

| 主题 | 条数 |
|---|---:|
| 内存形态（封装/板载/焊死） | 19 |
| 重量 | 12 |
| 屏幕（色域/素质） | 11 |
| 售后网点 | 11 |

**这四类全都能从数据推导**，而且不需要主观判断：

| 数据 | 推出的事实 | 为什么不是"评价" |
|---|---|---|
| `upgrade=0` / `slots=0` | 「内存板载焊死，16G 就是顶格」 | 物理事实 |
| `weightKg=2.5` | 「重 2.5kg，天天背着会累」 | 数字 + 常识阈值 |
| `gpu.type=integrated` | 「核显，跑不了要独显的任务」 | 物理事实 |
| `efficiency` 为空 | 「未查到能效备案，国补不一定拿得到」 | 数据缺失的如实陈述 |

区别在于：评价说「这台做工一般」，我们只说「1.98kg / 核显 / 内存焊死」——
**用户自己会判断**。

新增 `derive_notes.py`，产出 `derivedNotes` 字段（`{kind, text, basis}`，
`kind ∈ {con, pro, note}`），每条都带 `basis` 写清是从哪个字段推的。

**结果：242/243 台推得出，共 786 条**（con 403 / pro 383）。

### 2.1 一个保守取舍

`ram.slots=2` 但 `ram.form` 为空时，**不下「有插槽」的结论**。
因为 `form` 为空意味着"能不能加内存"其实没核实过，
`slots` 可能来自参数页但没归一化。

首版就是 `form or "非板载"` 默认当成非板载，等于把未核实说成事实。
改成只在 `form` 明确是 `sodimm/socketed` 时才说 pro。

## 3. 接进 agent：三条边界不许破

`derivedNotes` 进 `answer_followup` 时，踩了三个坑：

### 坑 1：模型会念内部字段名

首版把空列表直接传过去：

```json
{"优点": [], "缺点": [], "要提醒的坑": ""}
```

模型输出：

```
这台缺点为空。优点为空。要提醒的坑为空。
```

**违反项目既有判据**：「内部字段名和 null 绝不许出现在用户可见的句子里」
（`_screen_of` 那处注释已记过同款事故）。

修法：**空值连键都不传**（照项目既有做法）。

### 坑 2：模型只挑一条说

`derivedNotes` 有 3 条时，拼成一句「；」分隔的单串传过去，
模型只报了其中 1 条（挑的是最后那条 note）。

修法：**逐条给数组**，并在提示里要求「不利的必须全部说出来，一条都不许漏」。

### 坑 3（最隐蔽）：自家事实被审计判成"串台"

战66 八代 14 英寸的回答一直是：

```
战66 八代 14 英寸（2026 款锐龙版） 库里记的缺点是：。
```

查下来是 `_foreign_fact` 误判：它说「1.48kg」是**惠普战 66 八代锐龙版**的信息，
不是这台。但 1.48kg 明明是这台自己的 `weightKg` 推出来的。

根因：**`_one_corpus` 没收录 `derivedNotes`**。
这台 `pros/cons` 为空，语料只剩 spec 那 48 字，于是「1.48kg」在自己语料里
找不到，却命中了人工层同系列机型的 cons「1.48kg 在 14 寸里偏重」→ 判串台
→ 触发重写 → 重写后输出空模板。

修法：`_one_corpus` 把 `derivedNotes` 也算作这台的可引用语料。

> 补充：池里的「战66 八代 14 英寸」和人工层的「惠普战 66 八代锐龙版」
> **不是同一台**（512G/62.5% sRGB vs 1T/100% DCI-P3，不同 SKU），
> 但共享 1.48kg 这个事实 —— 这正是"共享事实"被误判成"搬用"的典型场景。

## 4. 边界：不动 `hasReview`，不动出口审计

| 项 | 处理 |
|---|---|
| `hasReview` | **不动** —— 仍由 `pros/cons` 是否存在决定 |
| 出口审计（拦主观形容词） | **不动** —— 仍按"没人写过评价"拦「细腻/通透/很值」 |
| `derivedNotes` | 独立字段，不进 `pros/cons` |
| 措辞要求 | 必须说「按规格看…」「从参数上看…」；不许说「评测认为」「口碑上」 |

这样两种口径在回答里是分开的：

```
这台只有配置和价格，没有人工写过的优缺点。          ← 人工层缺失，如实说
按规格看，内存是板载焊死的，32G 就是顶格。          ← 规格事实
```

### `test_weight` 拦下了我的违规

首版 `derive_notes.py` 直接读 `m["weightKg"]`，`test_weight` 的 **W8 结构性检查**
立刻报错：

```
FAIL W8 还有 3 处直接读 weightKg，可能漂移
  ⚠ derive_notes.py:58  w = m.get("weightKg")
```

这条检查的存在理由（测试注释里写着）：重量有四个出口
（brief / build_recommendation / server 投影 / 字段卡），各读各的字段迟早会漂 ——
曾经同一台机器在正文说 1.48kg、字段卡说 2.1kg。

改用 `core.effective_weight()`（唯一入口，会在结构化字段为空时从文本兜底）后恢复全绿。

**这是测试正确的拦截，不是测试过严。**

## 8. 还没做的

1. **`能跑PS吗` 这类匹配度追问仍然绕** —— 它会绕回"库里没人评过"。
   这是追问路径与匹配度判断的边界问题，属既有行为，不是本轮引入。
2. **人工优缺点仍是 34 台** —— `derivedNotes` 只解决"能从规格说的"，
   真实使用体验（做工、噪音、售后体验）只能靠人写或真实评测。
   要提升这部分，得靠 `harvest_samples.py` 攒真实对话 + 人工标注。
