## 三、补全脚本 `fill_from_zol.py`

### 3.1 设计要点

**① 只补不覆盖**

```python
if new and not cur:      # 已有值 → 不动
    m[key] = new
elif new and cur and 差异过大:
    conflicts.append(...)   # 冲突记录，留人工
```

**② 冲突不覆盖，只记录**

实测 0 冲突，说明已有数据和 ZOL 一致。

**③ 记录数据来源**

```python
df[key] = "ZOL 参数页 2026-11-25"
m["dataFrom"] = df
m["backfilled"] = sorted(bf)
```

**④ 限速**

```python
time.sleep(0.6)   # 别把人家服务器打爆
```

### 3.2 踩的坑：ZOL 的推广后缀

原始值长这样：

```
电池类型 = '6芯锂电池>，83瓦时'      ← 有个 >
外壳材质 = '复合材料>'
屏幕尺寸 = '16英寸16更多16英寸笔记本>'
最高睿频 = '5.8GHz运行流畅'
```

那个 `>` 和「更多…」「运行流畅」是 ZOL 的推广链接残留，会干扰数值提取。

**清洗**：

```python
v2 = v2.replace(">", "").strip()
v2 = re.sub(r"更多[^，,；;]*$", "", v2).strip()
v2 = re.sub(r"(极速运行|运行流畅|耗电高|超高清屏|热门游戏本|"
            r"旗舰机)$", "", v2).strip()
```

### 3.3 踩的坑：`batteryWh` 提取取错

```
'6芯锂电池，83瓦时'
```

用 `parse_num`（取第一个数字）会得到 **6**（「6 芯」的 6），不是 83。

**修法**：用专门的正则：

```python
mm = re.search(r"(\d+(?:\.\d+)?)\s*瓦时", val)
new = float(mm.group(1)) if mm else None    # → 83.0
```

## 六、交叉验证做了什么

用户要求「三方获取交叉验证」。这次的实现：

| 情况 | 处理 |
|---|---|
| 已有值 + ZOL 新值一致 | 不动（隐式确认） |
| 已有值 + ZOL 新值差异大 | **记录冲突，不覆盖** |
| 已有值缺失 + ZOL 有 | 补入，标记来源 |
| 两边都缺 | 留空 |

**实测 0 冲突** —— 说明之前的采集和 ZOL 是一致的。

**为什么冲突不覆盖**：ZOL 也可能错（不同 SKU、不同批次）。覆盖会丢掉原始值。
记录冲突留给人工判断，更安全。

### 8.2 「数据完整性」的诚实表述

> 本文的数据池包含 243 台机型，覆盖 20 余个字段维度。
> 其中核心字段（品牌、品类、价格、CPU、GPU、屏幕、内存、硬盘）
> 覆盖率达 95% 以上；扩展字段（电池容量、重量、接口）
> 覆盖率达 80% 以上。
>
> **部分字段覆盖率较低（散热 28%、保修 24.7%、续航 14%），
> 原因是公开数据源本身不提供这些信息**。经实测验证，
> ZOL 参数页的 10 台抽样中「散热系统」字段命中率为 0，
> 说明这不是采集脚本的缺陷，而是数据源的客观限制。
>
> 系统对这些缺失字段的处理方式是**如实说明「库里没有」，
> 而非推测或填充默认值** —— 这与本系统「说出口的每一句都站得住」
> 的设计原则一致。

**这段话可以直接用在答辩 PPT 的「数据局限性」一页。**
