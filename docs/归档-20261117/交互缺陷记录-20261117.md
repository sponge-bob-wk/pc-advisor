## 1. 缺陷 A：「换一台」在还有 113 台可选时报 exhausted

### 现象

库里有 **117 台游戏本**，「换一台」却说「就这几台，都看过了」。
日志里 `seen` 只有 3 台。

### 根因（已实测定位）

```
游戏本总数              117 台
  budget ≤ 8000          21 台
  _minRam ≥ 32           46 台
  两者都满足              4 台   ← 只剩 4 台
```

`build_recommendation(known, exclude=seen)` 排除已看的 3 台后 → **0 台**。

所以 `exhausted` 在**技术上是正确的**：在 `_minRam=32 + budget=8000` 这个
约束组合下，真的只剩 3 台。

**但用户没要求 32G 内存。** 这个约束是系统自己加的。

### 约束从哪来的（**已定位到根因，比我最初想的更直接**）

```
用户说「我想打游戏」
  → core.match_major("我想打游戏") 返回 ("游戏艺术设计", ...)
  → 该专业 req.ramMin = 32
  → slots["_minRam"] = 32   ← 硬约束
  → 117 台游戏本砍到 4 台
```

**`match_major` 是子串匹配**（`key in t`），而专业索引里有一条**别名 `'游戏'`**：

```python
# core._major_index 里含「游戏」的键：
'游戏艺术设计' -> 游戏艺术设计
'游戏'        -> 游戏艺术设计   ← 就是这个别名害的
```

于是**任何含「游戏」二字的句子都命中**，实测：

| 用户原话 | match_major 结果 | 对不对 |
|---|---|---|
| 我想打游戏 | 游戏艺术设计 | ❌ 只是要打游戏 |
| 打游戏 | 游戏艺术设计 | ❌ |
| 预算8000打游戏 | 游戏艺术设计 | ❌ |
| 我想玩游戏 | 游戏艺术设计 | ❌ |
| 能打游戏吗 | 游戏艺术设计 | ❌ |
| 我学游戏设计 | 游戏艺术设计 | ✅ 这个才对 |

**7 句里 6 句误判。** 这是本轮最严重的问题——
用户只要说"打游戏"，系统就擅自按"游戏艺术设计专业"提内存要求。

### 这是"别名设计"的典型翻车

`match_major` 的注释写着：

> ⚠️ 只认**表里有的**专业名/别名，不做相似度猜测 ——
> 猜错专业等于把人家的四年配置搞错，比不认更糟（宪法第 3 条：宁可弃权）。

**设计意图是对的，但别名表里塞了「游戏」这种泛词，等于把"弃权"变成了"乱猜"。**

`'游戏'` 这个别名本身就该删 —— 它不是专业名，是动词短语的一部分。

## 2. 缺陷 B：说「可以」放宽预算，又推回同一台

### 现象

```
A: 「这个条件下库里就这几台，都看过了。要不放宽预算，或者换个品类我再看看？」
U: 「可以」
A: 「这台是联想拯救者 i7 14650HX、32G、RTX4050…」   ← 和上一次完全同一台
```

### 根因

「可以」是**同意放宽预算**，但：

1. 系统没有把"放宽预算"变成具体的 `budget` 调整（8000 → ？没说放宽多少）
2. 更没有清空 `seen` —— 于是重新推荐时，排序结果还是原来那台第一

**"放宽预算"这个动作没有实现。** 系统只是把同一份 known 重跑了一遍。

### 待定设计问题

「放宽预算」放宽到多少？三种方案：

| 方案 | 做法 | 风险 |
|---|---|---|
| A. 固定倍数 | budget × 1.25 | 可能推出一台贵很多的 |
| B. 反问具体数 | 「放宽到多少？」 | 多一轮，但准确 |
| C. 分档试探 | 8000→9000→10000 逐档找 | 逻辑复杂 |

**倾向 B**：一句反问比猜错强。但要注意别和"问预算"重复。

## 3. 缺陷 C：「限电 500W」被当成问配置，答了屏幕参数

### 现象

用户说「限电 500W」（宿舍限电 500 瓦），系统回了一段**屏幕参数**。

### 根因（**和我最初判断的不一样，已实测更正**）

我一开始以为 `dormWatt` 没实现。**错了** —— 实测：

```python
agent.extract_slots('限电500W')
# → {'cat': None, 'budget': None, 'purpose': [], 'years': None,
#    'carry': None, 'dormWatt': 500}   ← 抽出来了！
```

`dormWatt` 的**抽取和使用都已经实现了**：

| 位置 | 作用 | 状态 |
|---|---|---|
| `agent.py:25` | 提示词里声明槽位 | ✅ |
| `agent.extract_slots` | 从原话抽 `dormWatt=500` | ✅ 能用 |
| `core.ask_expert` | 没限电信息时主动问「宿舍限电吗」 | ✅ |
| `core.py:1935` | 限电 <600W 时加 warning「游戏本满载可能跳闸」 | ✅ |

**真正的问题在路由**：

```python
intent_layer.route('限电 500W')
# → intent=state_new_need, topic=config, fit=False
```

模型把「限电 500W」判成 **`topic=config`（问配置）**，
于是走了 `answer_followup` → 按"配置"面回答 → 报了屏幕参数。

**但这是一条「补充条件」，不是「问配置」。** 正确动作应该是：
记下 `dormWatt=500` → 重新跑推荐 → 顺带把 warning 说出来。

### 这是「意图分类错」导致「正确答案没机会触发」

底层数据链路是通的（能抽、有 warning 逻辑），
但路由把这句话送错了分支，warning 永远没机会出现。

### 同类风险

任何「补充条件型」的短句都可能被误判成"问配置"：

```
限电 500W      → 应该：记条件
要 32G 内存     → 应该：记条件
得能带出门      → 应该：记条件
宿舍没空调      → 应该：记条件（散热权重）
```

这些都不是"问这台的配置怎么样"，是"我还有个要求"。

## 4. 缺陷 D：推荐了轻薄本给"打游戏"的用户，没有先说够不够用

### 现象

```
U: 华为MateBook D16怎么样
A: 「…到手 ¥4589…你主要拿它干什么？」
U: 我想打游戏
A: 「预算大概多少？」      ← 直接问预算，没说这台打游戏够不够
```

用户的疑问（也是本轮的原始提问）：

> 他推荐的华为 matebook 我问拿来干嘛，我说打游戏，
> 那他是不是应该先给我说够不够用，再换一个推荐或者啥的

**对。这是缺失的一步。**

MateBook D16 是核显轻薄本，打游戏明显不合适。系统**明明能判断**
（`gpuKind=integrated` 就是硬伤），却直接跳过"够不够"去问预算。

### 为什么没判

`_answer_current` 的匹配判断需要 `purpose`，而用户说「我想打游戏」时
purpose 已经抽到了（`purpose=['gaming']`），理论上该触发匹配判断。

实际走了 `clarify`（问预算）—— 说明**匹配判断被槽位收集抢先了**。

这和昨天修的「问细节却回头问槽位」是同一类问题的**另一个面**：
昨天修的是"问细节被槽位拦"，这个是"给用途被槽位拦"。

## 5. 缺陷 E：这些回答是模型写的吗？为什么这么死板

### 用户的原问

> 还有这些交互是模型在回答吗，咋感觉还是那么死板

### 答案：是模型写的，但它被规则捆得很死

当前架构：

```
用户说话 → 代码确定性排序（模型无权）→ 模型只负责"把数据说成人话" → 出口审计
```

**模型的权限被刻意压到最小**：

| 模型能做的 | 模型不能做的 |
|---|---|
| 把字段组织成句子 | 改数字 |
| 换措辞 | 改排序 |
| 决定先说什么后说什么 | 编评价 |

### 死板的真实原因（三条，按影响排序）

**① 大量固定模板在模型之前就生成了回复**

看日志 #7 和 #10，回复几乎一模一样：

```
#7  「这台联想拯救者配置是 i7 14650HX 处理器、32G 内存搭配 RTX4050 显卡…」
#10 「这台是联想拯救者，配置是 i7 14650HX、32G 内存、1T 硬盘和 RTX4050 显卡…」
```

这种"配置 + 价格 + 专业要求"的三段式，是 `compose()` 里的**固定模板**，
模型只是把槽填进去。所以两次措辞略有不同，但结构完全一样。

**② 出口审计会否决模型的自由发挥**

模型想说得生动一点 → 触发 `_praise_no_review`（不许评价）→ 重写
→ 重写后只能报参数 → 更死板。

这是**为了不编造而付出的代价**，是设计取舍，不是 bug。

**③ `answer_followup` 的提示词要求"只谈数据里出现过的，不许改写"**

```
1. 只谈数据里出现过的内容，不许改写得更好听或更概括。
2. 直接回答他问的那一点就停。
5. 两到三句。
```

「两到三句」+「不许改写」= 必然死板。

### 结论

**不是模型不行，是架构故意不让它自由。** 这个取舍是对的（毕设项目的
核心卖点是"不编造"），但**用户感知是"死板"**。

改进方向不是"放开模型"，而是：
- 让固定模板**有变化**（同一台机器第二次介绍时换个说法）
- 让"够不够用"这类**判断**由代码做完、模型只说结论（现在是干脆不说）

## 6. 下次修正的优先级

| 优先级 | 缺陷 | 为什么这个顺序 |
|---|---|---|
| **P0** | 缺陷 A：`_minRam=32` 过度推断 | 一条约束把 117 台砍到 4 台，影响所有"打游戏"的对话 |
| **P0** | 缺陷 C：`dormWatt` 没实现抽取 | 用户说了具体条件，系统当没听见 |
| **P1** | 缺陷 D：给用途后不判够不够 | 最伤体验的一步（用户明确指出了） |
| **P1** | 缺陷 B：「放宽预算」没实现 | 承诺了动作但没做，用户会觉得被敷衍 |
| **P2** | 缺陷 E：模板死板 | 是设计取舍，改起来最费劲，收益最主观 |

### P0-1 的具体改法（建议）

**删掉专业别名表里的 `'游戏'`**（在 `data/majors.json` 或 `core._major_index` 的别名来源里）。

理由：

- `'游戏'` 不是专业名，是动词短语的一部分（「打游戏」「玩游戏」「能打游戏吗」）
- 它让 `match_major` 从"宁可弃权"退化成"乱猜"，违反自己的设计原则
- 真正的专业名「游戏艺术设计」「电子竞技运动与管理」都在表里，删别名不影响

**验证改法的三条命令**（改完应全部返回 `未匹配`，除了最后一条）：

```python
import core
for t in ['我想打游戏', '打游戏', '预算8000打游戏', '我想玩游戏', '能打游戏吗']:
    print(t, core.match_major(t)[1])   # 都应为 None
print(core.match_major('我学游戏设计')[1])   # 应为「游戏艺术设计」
```

**补充建议**：加一条"专业必须由专业名触发"的判据 ——
`match_major` 只认**完整专业名**，别名限制在"不会出现在日常用语里"的范围内
（比如「计科」「软工」可以，「游戏」不行）。

> ⚠️ 注意：`majors.json` 是 ②（静态选机）也在用的数据。
> 改别名前先跑 `python tools/check_majors.py`（应 7/7）和
> `python tools/coverage.py`（应仍是 94.0% / 45.4%），确认没影响 ②。

### P0-2 的具体改法（建议）

**`dormWatt` 的抽取和使用都已实现，不用补。要改的是路由。**

`intent_layer` 里 `state_new_need` 的定义要加一条：**补充条件型短句**。

```python
# 现在：限电 500W → topic=config（错，被当问配置）
# 应该：限电 500W → state_new_need, topic=none（对，是加条件）
```

判据：句子里**有具体条件值但没有疑问词** → 加条件，不是问配置。

```
限电 500W     ← 有数值、无疑问词 → 加条件
要 32G 内存    ← 同上
得能带出门     ← 同上
屏幕怎么样     ← 有疑问词 → 问细节（现状正确）
```

**改完之后的行为应该是**：

```
U: 限电 500W
A: 记下了，宿舍限电 500W。游戏本满载大概 200~280W，
   500W 基本够用，但别同时开空调/吹风机。
   （然后继续当前推荐，或按新条件重排）
```

**注意**：`core.py:1935` 的 warning 条件是 `dormWatt < 600`，
500W 会触发「游戏本满载可能跳闸」。但实测游戏本满载 200~280W，
500W 其实**够用** —— 这条 warning 的阈值可能偏保守，一并复核。

### P1 的具体改法（建议）

用户给了 purpose 但当前推荐的机器**明显不匹配**（核显 + gaming）时：

```
先说：「这台是核显轻薄本，打游戏不合适」  ← 结论由代码判
再问：「要我按游戏本重新找吗？预算多少？」  ← 承接下一步
```

而不是跳过"不合适"直接问预算。
