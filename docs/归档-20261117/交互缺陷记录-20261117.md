## 1. 缺陷 A：「换一台」在还有 113 台可选时报 exhausted

### 现象

库里有 **117 台游戏本**，「换一台」却说「就这几台，都看过了」。
日志里 `seen` 只有 3 台。

### 根因（已实测定位）

```
游戏本总数              117 台
  budget ≤ 8000          21 台
  _minRam ≥ 32           46 台
  两者都满足              4 台   ← 只剩 4 台
```

`build_recommendation(known, exclude=seen)` 排除已看的 3 台后 → **0 台**。

所以 `exhausted` 在**技术上是正确的**：在 `_minRam=32 + budget=8000` 这个
约束组合下，真的只剩 3 台。

**但用户没要求 32G 内存。** 这个约束是系统自己加的。

### 约束从哪来的（**已定位到根因，比我最初想的更直接**）

```
用户说「我想打游戏」
  → core.match_major("我想打游戏") 返回 ("游戏艺术设计", ...)
  → 该专业 req.ramMin = 32
  → slots["_minRam"] = 32   ← 硬约束
  → 117 台游戏本砍到 4 台
```

**`match_major` 是子串匹配**（`key in t`），而专业索引里有一条**别名 `'游戏'`**：

```python
# core._major_index 里含「游戏」的键：
'游戏艺术设计' -> 游戏艺术设计
'游戏'        -> 游戏艺术设计   ← 就是这个别名害的
```

于是**任何含「游戏」二字的句子都命中**，实测：

| 用户原话 | match_major 结果 | 对不对 |
|---|---|---|
| 我想打游戏 | 游戏艺术设计 | ❌ 只是要打游戏 |
| 打游戏 | 游戏艺术设计 | ❌ |
| 预算8000打游戏 | 游戏艺术设计 | ❌ |
| 我想玩游戏 | 游戏艺术设计 | ❌ |
| 能打游戏吗 | 游戏艺术设计 | ❌ |
| 我学游戏设计 | 游戏艺术设计 | ✅ 这个才对 |

**7 句里 6 句误判。** 这是本轮最严重的问题——
用户只要说"打游戏"，系统就擅自按"游戏艺术设计专业"提内存要求。

### 这是"别名设计"的典型翻车

`match_major` 的注释写着：

> ⚠️ 只认**表里有的**专业名/别名，不做相似度猜测 ——
> 猜错专业等于把人家的四年配置搞错，比不认更糟（宪法第 3 条：宁可弃权）。

**设计意图是对的，但别名表里塞了「游戏」这种泛词，等于把"弃权"变成了"乱猜"。**

`'游戏'` 这个别名本身就该删 —— 它不是专业名，是动词短语的一部分。

## 2. 缺陷 B：说「可以」放宽预算，又推回同一台

### 现象

```
A: 「这个条件下库里就这几台，都看过了。要不放宽预算，或者换个品类我再看看？」
U: 「可以」
A: 「这台是联想拯救者 i7 14650HX、32G、RTX4050…」   ← 和上一次完全同一台
```

### 根因

「可以」是**同意放宽预算**，但：

1. 系统没有把"放宽预算"变成具体的 `budget` 调整（8000 → ？没说放宽多少）
2. 更没有清空 `seen` —— 于是重新推荐时，排序结果还是原来那台第一

**"放宽预算"这个动作没有实现。** 系统只是把同一份 known 重跑了一遍。

### 待定设计问题

「放宽预算」放宽到多少？三种方案：

| 方案 | 做法 | 风险 |
|---|---|---|
| A. 固定倍数 | budget × 1.25 | 可能推出一台贵很多的 |
| B. 反问具体数 | 「放宽到多少？」 | 多一轮，但准确 |
| C. 分档试探 | 8000→9000→10000 逐档找 | 逻辑复杂 |

**倾向 B**：一句反问比猜错强。但要注意别和"问预算"重复。

## 3. 缺陷 C：「限电 500W」被当成问配置，答了屏幕参数

### 现象

用户说「限电 500W」（宿舍限电 500 瓦），系统回了一段**屏幕参数**。

### 根因（**和我最初判断的不一样，已实测更正两次**）

**第一次判断（错）**：以为 `dormWatt` 没实现。

实测：
```python
agent.extract_slots('限电500W')
# → {'cat': None, ..., 'dormWatt': 500}   ← 抽出来了
```

`dormWatt` 的**抽取和使用都已实现**：

| 位置 | 作用 | 状态 |
|---|---|---|
| `agent.py:25` | 提示词里声明槽位 | ✅ |
| `agent.extract_slots` | 从原话抽 `dormWatt=500` | ✅ |
| `core.ask_expert` | 没限电信息时主动问 | ✅ |
| `core.py:1935` | 限电 <600W 加 warning | ✅ |

**第二次判断（对）**：问题在 `ask_fit` 没用模型判断。

实测模型的原始判断：

```python
intent_layer.model_route('限电 500W', focus)
# → {'intent': 'ask_current', 'topic': 'battery', 'fit': True}
#    模型认为：用户在问匹配（fit=True），主题是电池
```

但 `agent.py:4909` 算 `ask_fit` 时**只用词表**：

```python
ask_fit = any(k in user_text for k in FIT_KW)   # → False
```

于是模型的 `fit=True` 被丢弃 → 走 `answer_followup` → 按 `topic=battery`
回答 → 但 `battery` 面没有限电相关数据 → 退化报整机参数（含屏幕）。

**所以这是缺陷 E 的一个具体表现，不是独立缺陷。**
「限电 500W」的完整链条：

```
模型：fit=True（在问匹配）
  ↓ 被丢弃（ask_fit 用词表）
走 followup
  ↓ topic=battery 没数据
退化报整机参数
  ↓ 用户看到
「16 寸 2560×1600 IPS 165Hz 100% sRGB」   ← 问限电答屏幕
```

### 同类风险

任何「补充条件型」的短句，只要 `FIT_KW` 没覆盖到，都会被丢弃模型判断：

```
限电 500W      → 模型 fit=True，词表 False → 丢弃
要 32G 内存     → 同上
得能带出门      → 同上
宿舍没空调      → 同上
```

## 4. 缺陷 D：推荐了轻薄本给"打游戏"的用户，没有先说够不够用

### 现象

```
U: 华为MateBook D16怎么样
A: 「…到手 ¥4589…你主要拿它干什么？」
U: 我想打游戏
A: 「预算大概多少？」      ← 直接问预算，没说这台打游戏够不够
```

用户的疑问（也是本轮的原始提问）：

> 他推荐的华为 matebook 我问拿来干嘛，我说打游戏，
> 那他是不是应该先给我说够不够用，再换一个推荐或者啥的

**对。这是缺失的一步。**

MateBook D16 是核显轻薄本，打游戏明显不合适。系统**明明能判断**
（`gpuKind=integrated` 就是硬伤），却直接跳过"够不够"去问预算。

### 为什么没判

`_answer_current` 的匹配判断需要 `purpose`，而用户说「我想打游戏」时
purpose 已经抽到了（`purpose=['gaming']`），理论上该触发匹配判断。

实际走了 `clarify`（问预算）—— 说明**匹配判断被槽位收集抢先了**。

这和昨天修的「问细节却回头问槽位」是同一类问题的**另一个面**：
昨天修的是"问细节被槽位拦"，这个是"给用途被槽位拦"。

## 5. 缺陷 E：这些回答是模型写的吗？为什么这么死板

### 用户的原问（两次）

> 还有这些交互是模型在回答吗，咋感觉还是那么死板
>
> 那还是不是模型交互？我的要求不是模型为主规则兜底吗

### 实测答案：模型每轮被调用 3–5 次，但**部分判断被丢弃**

用日志重放实测每轮调用次数：

| 用户 | stage | 模型调用 |
|---|---|---:|
| 我想打游戏 | clarify | 2 次 |
| 预算 8000 左右 | recommend | 4 次 |
| 屏幕怎么样 | followup | 3 次 |
| 换一台 | exhausted | 3 次 |
| 可以 | recommend | 5 次 |
| 限电 500W | followup | 3 次 |

**模型确实在跑**，每轮都调了路由 + 槽位抽取 + 措辞生成。

### 但发现一处**架构级不一致**（这是本轮最该修的东西）

| 判据 | 数据来源 | 位置 |
|---|---|---|
| `ask_detail`（在问细节吗） | **模型** `lr.get("topic")` | `agent.py:4744` |
| `ask_detail`（同上，另一处） | 词表 `FOLLOWUP_KW` | `agent.py:4748` |
| `ask_fit`（在问匹配吗） | **只用词表 `FIT_KW`** | `agent.py:4909` |

**`ask_fit` 完全没用模型的 `fit` 字段。**

实测「限电 500W」：

```
模型原始判断：intent=ask_current, topic=battery, fit=True   ← 模型说"在问匹配"
但：any(k in q for k in FIT_KW) = False                      ← 词表没命中
→ ask_fit = False
→ 模型的 fit=True 被丢弃
→ 走了 answer_followup，答了屏幕参数
```

**这违反了「模型为主、规则兜底」的架构原则** ——
`ask_detail` 已经改成读模型了（4744 行），但 `ask_fit` 还停在词表时代（4909 行）。

### 这是"反转做了一半"的遗留

2026-11-16 的架构反转把 `intent`/`topic` 交给了模型，
但 `ask_fit` 这条判据漏了 —— 它还在用 `FIT_KW` 词表。

**后果**：模型识别出"用户在问匹配"，系统却按词表判定"没问匹配"，
于是走了错误分支。这类"模型说了不算"的地方，用户感知就是"死板/听不懂"。

### 死板的三个原因（修正版，按影响排序）

**① `ask_fit` 没用模型（架构不一致，是 bug）**

见上。这条最该修，因为它让模型的正确判断被丢弃。

**② 大量固定模板在模型之前就生成了回复**

对比日志 #7 和 #10：

```
#7  「这台联想拯救者配置是 i7 14650HX 处理器、32G 内存搭配 RTX4050 显卡…」
#10 「这台是联想拯救者，配置是 i7 14650HX、32G 内存、1T 硬盘和 RTX4050 显卡…」
```

结构完全一样（配置 + 价格 + 专业要求三段式），是 `compose()` 里的固定模板。
模型只负责填槽，所以两次措辞略变但骨架不动。

**③ 出口审计否决自由发挥（这是取舍，不是 bug）**

想说生动点 → 触发 `_praise_no_review`（不许评价）→ 重写 → 只能报参数 → 更死板。

**这一条要保留**，它是项目最值钱的特性（不编造）。

### 结论

**"不是模型交互"这个感觉是对的，但原因不是"没调模型"，而是"调了模型却不采信它的部分判断"。**

具体说：

- ✅ 意图分类：模型为主（`classify` 14 处规则是**兜底**，实测 7 句里 6 句是模型判的）
- ✅ 槽位抽取：模型为主
- ✅ 措辞生成：模型为主
- ❌ **`ask_fit`（问匹配）：纯词表，模型说了不算** ← 这就是"死板"的技术根源之一
- ⚠️ 措辞被模板和审计捆住（取舍，保留）
