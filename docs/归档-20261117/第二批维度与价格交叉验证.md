## 2. P2：价格多来源交叉验证

新增 `price_cross_check.py`。126 台有 ≥2 个价格来源，可以互相印证。

### 2.1 口径纪律（这条最容易做错）

```
LIST_TIER = (zolRef, jd, tmall, merchantMin)   ← 平台标价，同量纲，可互比
REAL_TIER = (net, final)                        ← 到手价，单独列，不参与冲突判定
```

**不能拿标价去比到手价** —— 到手价含券含国补，本来就低一截，比了全是假冲突。

### 2.2 判定三档

```
≤ 10%   normal    多个来源互相印证
10~30%  watch     留意，可能是不同配置
> 30%   suspect   高度可疑，必须人看
```

阈值是实测定的：正常偏差（zolRef vs merchantMin）多数在 10% 以内，
经销商价本来就比参考价低 5~15%。

### 2.3 抓到一个真问题：`merchantMin` 是串台的

首次跑出来 33 台「可疑」，但看着不对劲——`merchantMin ¥8779` 反复出现，
`¥6434` 出现 **9 次**，落在型号/配置完全不同的机器上。

验证：

```
merchantMin   91 个值  重复最多: [(6434, 9), (8779, 4), (14249, 3)]
zolRef       152 个值  重复最多: [(7999, 4), (14999, 3)]
tmall         30 个值  重复最多: []
```

`6434` 出现在 zolRef 9548~9848 的机器上（差 1.5 倍），
`8779` 出现在 zolRef 14199~25399 的机器上（差 1.6~2.9 倍）——
那不可能是这些机器的经销商报价，**是 ZOL 页面侧栏推荐位的价格**。

这和 `AGENTS.md` §5.7 记的天猫价坑同源：ZOL 详情页的推荐位价格会被误抓。

### 2.4 自动识别不可靠来源：试了三次才对

这个判据我改了四版，前三版都失败，记下来免得重走：

| 判据 | 结果 |
|---|---|
| ① 重复占比 > 20% | **误杀 `zolRef`** —— 7999 出现 4 次是正常同价 |
| ② 同值覆盖 ≥5 个型号前缀 | **骗过** —— 9 台都叫「联想拯救者」，前缀相同 |
| ③ 与其它来源偏差 >50% 的机器占比 >40% | **算不出** —— merchantMin 只覆盖 91 台，多数机器只有一个来源 |
| ④ ✅ 同值机器的其它来源跨度 ≥2 倍 | 正确 —— merchantMin 判死，zolRef 保留 |

最终判据的含义：

> 一个价格值，如果它出现的那些机器，**其它来源的价格跨度达到 2 倍以上**，
> 说明这个值不可能是它们的真实价格（同一台机器的价格不该和别的来源差 2 倍）。

### 2.5 排除 `merchantMin` 后剩下的可疑项

```
可核对 61 台 / normal 35 / watch 11 / suspect 15

联想拯救者        +95%   tmall ¥3799  / zolRef ¥7399
联想拯救者Y9000P  +94%   tmall ¥15499 / zolRef ¥29999
联想小新14        +71%   tmall ¥2168  / zolRef ¥3699
机械革命蛟龙16Pro  +66%   zolRef ¥6199 / tmall ¥10299
```

**`tmall` 仍是主要嫌疑**：¥3799 对 ¥7399 这种「正好差一倍」的比例，
典型的 SKU 串台（8G 版 vs 16G 版）。

这 15 台留给下一次处理——**先不动数据**，因为：
① 要判断是哪个来源错，得逐台打开 ZOL 页核对
② 现在这些值只进 `priceSnapshots`，**不影响到手价和排序**，
   所以不急，但不能忘

### 2.6 接进刷新链路

`refresh_engine._cross_validate()` 现在会跑这个检查：

```
[warn] 价格交叉验证：61 台可核对，15 台偏差 >30%（需人看）；
       已排除不可靠来源：merchantMin
```

> 超过 10 台可疑就报 warn，这样下次刷新能看见它没被忘掉。

## 3. P3：修「问细节却回头问槽位」的 bug

### 3.1 现象

```python
agent.run('有别的颜色吗', focus='zol-2130961')
# → stage=clarify
# → 「是笔记本还是台式？大概想放在宿舍用，还是要能带着走？」
```

用户明明已经在问这台的颜色，系统却回头问最基础的问题。

### 3.2 根因：focus 只有 id，没有槽位

`_run` 里有一段：

```python
miss = core.missing_required(slots)
if miss:
    # 问缺的槽位
```

`focus` 参数只带一个 id，`slots` 是空的 → 缺「品类」→ 触发 clarify。

**这是"先收集槽位"的设计在追问场景下的副作用。**

### 3.3 排查过程（走了三段弯路，记下来）

| 怀疑对象 | 验证结果 |
|---|---|
| 路由层把「有别的颜色吗」判成 `state_new_need` | ❌ 带 focus 时正确判成 `ask_current` |
| `has_new_condition` 误判成改条件 | ❌ 全是 False |
| `TOPIC_TRIGGER` 没有「颜色」主题 | ❌ 加了主题仍然走 clarify |
| **`missing_required` 触发 clarify** | ✅ 找到了 |

教训：**先怀疑"槽位收集"这类前置门，再怀疑分类器。**
分类器错会表现为"答错"，前置门错会表现为"根本没答"。

### 3.4 修法

在 `missing_required` 之后加一个前置判断：

```python
if miss and focus and refers_to_current(user_text, focus) \
        and asks_about_current(user_text):
    # 在问这台的某一面 → 直接答细节，跳过槽位收集
```

**为什么不干脆「有 focus 就跳过」**：用户说「预算 8000」时 focus 也在，
但那是加条件不是问细节，那种该继续收集/重推。

### 3.5 效果

| 问题 | 修前 | 修后 |
|---|---|---|
| 有别的颜色吗 | clarify（问品类） | **followup：这台只有雾屿白一种颜色** |
| 什么颜色 | clarify | followup：这台只有雾屿白一种颜色 |
| 充电快吗 | clarify | followup：未提及充电功率（这台确实没数据） |
| 保修几年 | clarify | followup：整机质保 1 年 |

**顺带修好一条存量失败**：`test_intent` 从 72/74 → **73/74**。
