# 死循环修复（2026-11-17 15:45）

> 用户反馈：「目前陷入一个一直回答一个答案的死循环」

---

## 1. 现象

日志 `chat-2026-11-17.log` 第 35-37 条，**连续三轮回答完全一样**：

| # | 用户 | 回答 |
|---|---|---|
| 35 | 售后怎么样 | 「品牌这块还有一句：别按品牌判断…具体几年我不敢替厂商说…」 |
| 36 | 我说的是好售后吗 | **同一段，一字不差** |
| 37 | 我的意思是，售后网点多吗 | **同一段，一字不差** |

用户换三种说法问同一件事 = 对第一个回答不满意。系统却在复读。

---

## 2. 根因：三层原因叠加

### 2.1 数据层：`brandService` 在原始 offer 里是 None

```python
o = core.get_offer('zol-2128701')
o['brandService']   # None
o['warrantyYears']  # None
o['warrantyPolicy'] # None
o['brandNote']      # None
```

但 `core.brand_info(o)` **能查到** `{'service': 5, 'note': '别按品牌判断...'}`。

**原因**：`brandService` 这个字段只在 `brief()` 里临时算过，`get_offer()` 返回的原始 offer 没有。
而 `_topic_facts(m, q)` 拿到的是原始 offer → 售后分支 facts 永远是空的。

### 2.2 模板层：兜底分支只看 `warrantyYears`，不看品牌分

`_followup_template` 的售后分支：

```python
if wy or wpol or wnote:      # 这台三个都是 None
    ...                       # 不走
if svc: ...                   # pros 里没有"保修/售后"字样
if note: ...                  # brandNote 是 None
→ 落到 "保修年限这一项，库里没有记录"
```

**这台明明有「品牌售后 5/5」，但因为缺"具体年限"就说没有。**

### 2.3 会话层：系统不知道用户在重复问

`answer_followup(user_text, m)` 是纯函数，没有历史状态。
用户第 3 次问同一件事，它和第 1 次表现完全一样。

---

## 3. 修法：四步

### 3.1 售后分支现算 `brand_info`

`_topic_facts` 和 `_followup_template` 两处都改成：

```python
_bs = m.get("brandService")
if _bs is None:
    _bi = core.brand_info(m) or {}
    _bs = _bi.get("service")
```

**有品牌级数据就说品牌级，不要因为缺"具体年限"就说没有。**
「售后网点多吗」问的本来就是品牌覆盖，不是质保年数。

### 3.2 加「重复提问检测」

`run()` 里维护 `known["_askedTopics"]`（最近 6 条主题），
`_merge_offer` 塞进 offer，`answer_followup` 读出来算 `_repeat`。

> 为什么走 `known` 而不是加函数参数：
> `run()/_run()` 的签名被 6 处调用 + server + 前端共用，加参数要改一圈。
> `known` 本来就是自由字典，塞个下划线键最省事。

### 3.3 代码层兜底换角度（不指望模型听话）

实测：第 2 轮模型听话换了角度，第 3 轮又复读 —— **提示词约束不稳定**。

所以在审计之后加代码兜底，按次数递进：

```python
_n = _repeat + 1
if _n == 2:
    reply = "刚才没说到你要的，我直接说结论：{facts}。关于「…」——这个评分说的就是…"
else:
    reply = "这已经是第 N 次问这一项了，库里关于售后就这一条：{facts}。" \
            "我没有更多能说的了 —— 再问也是这个答案。要确切数字只能走两条路：…"
```

**关键：只换措辞和角度，不加任何新事实。**

### 3.4 修一个被我绕过的过滤器

`_clean_brand_note` 是用来过滤「品牌备注夹带别的机型」的。
我在兜底里直接读 `_bi.get("note")`，**绕过了这个过滤**，
导致 `test_neg` 抓到：MateBook 14 问保修，回答里出现了「MateBook D16 在 4589 元…」。

修法：兜底里拿到的 note 也要过 `_clean_brand_note`。

---

## 4. 排查过程中我犯的三个错（记下来）

### 错 1：兜底块放错位置，被后面的 `reply = reply2` 覆盖

第一次把兜底放在审计**之前**，结果审计判不合格 → 重写 → `reply = reply2`
把我的兜底覆盖了。

**教训：`answer_followup` 里有审计重写，任何"最终出口"的兜底都必须放在
`reply = reply2` 之后、`return` 之前。**

### 错 2：用「回答内容」判断是否重复，而不是「提问历史」

第一版判据是「回答里含兜底标记词 → 说明在复读」。

DEBUG 打出来：`repeat=2 topic='售后' fb=False` ——
`_repeat` 算对了，但模型这次换了措辞，标记词没命中，兜底不触发。

**教训：「是不是重复」不该由回答内容判断，该由提问历史判断。
用户问过 N 次同一主题就是重复，不管这次模型说了什么。**

### 错 3：忘了自己绕过了过滤器

`_clean_brand_note` 是既有防线，我在新代码里直接读原始 note 就绕过了。
`test_neg` 立刻抓到。

**教训：读 `brandNote` 永远走 `_clean_brand_note`，不要直接读字段。**

## 5. 修复效果

三轮递进，不再复读：

**第 1 次**
> 联想 的品牌售后网点评分 5 / 5（5 = 覆盖最广）。品牌这块还有一句：别按品牌判断，按型号判断。具体到这一台是整机几年，得看厂商的保修条款…

**第 2 次**
> 刚才没说到你要的，我直接说结论：品牌售后网点评分 5 / 5；这台具体整机几年，库里没有记录。关于「售后网点多不多」——这个评分说的就是网点覆盖广度，5 分是最高档…

**第 3 次**
> 这已经是第 3 次问这一项了，库里关于售后**就这一条**：品牌售后网点评分 5 / 5；这台具体整机几年，库里没有记录。我没有更多能说的了 —— 再问也是这个答案。要确切数字只能走两条路：① 商品详情页找「保修」栏；② 问客服要书面答复…

## 7. 这套机制能推广到所有主题

现在 `_askedTopics` 记录的是**主题**（售后/屏幕/重量…），
所以「连续问三次屏幕」也会触发换角度，不只售后。

**但要注意**：只有**同一主题**才算重复。
用户问完屏幕再问重量，那是正常对话，不该说"你问过了"。

---

## 8. 还没解决的

### 8.1 第 2、3 次的答案仍然是代码拼的，不是模型说的

这是**故意的** —— 模型在这个场景下不稳定（实测第 3 轮必复读）。
代价是这两轮的语气比较机械。

要改善得先让模型稳定听话，那需要更多训练样本。

### 8.2 数据本身只有一条

这台机器的售后数据只有「品牌 5/5」一条。
**再好的对话机制也变不出第二条事实。**

真正的解法是补数据：抓厂商保修政策、逐型号的质保年限。
见 `追问维度补齐-20261116.md` §7 的待补清单。

### 8.3 类似的死循环可能还有

本轮只验证了「售后」这一面。
其他主题（屏幕/重量/散热）如果数据也缺，同样会复读 ——
但现在有 `_askedTopics` 兜底，至少不会一字不差地重复。
