## 0. 一句话说清这是什么

**一个帮准大学生挑笔记本的对话助手。它不是排行榜，也不是电商比价器。**

它的价值不在"知道得多"，而在**"说出口的每一句都站得住"**：

```
用户说预算和用途 → 代码确定性排序 → 模型只把结果讲成人话 → 出口审计拦住编造
```

这条链决定了 UI 的第一原则：**界面上每一个数字都必须来自接口，前端不许自己算、不许自己排、不许自己编推荐理由。**

## 1. 用户在什么状态下打开它

- 刚考完、要买大学四年用的第一台电脑，预算 4000–8000，很怕被坑
- 不懂参数，但会追问「这块屏够不够做设计」「能不能打游戏」「多重」
- 一边看一边怀疑：这机器是不是恰饭、是不是没货了随便推
- 会当场乱测：说半句话、改主意、问东问西、质疑

**所以页面要同时做两件事：让他快速拿到一台具体机器；让他随时能验证"你凭什么这么说"。**

## 2. 数据和能力的真实边界（设计的底线，不能美化）

| 事实 | 数字 | UI 怎么体现 |
|---|---|---|
| 可推荐机型 | **97 台**（人工核定 22 + 京东采集 75） | 首屏就要说清，不许含糊成"海量机型" |
| 其中**有人写过优缺点** | **22 台** | 只有这 22 台可以说"好/不好" |
| **只有参数、没人评过** | **75 台** | 卡片上必须有「仅参数」标识，不许写成卖点 |
| 能算出跑分 | 81 台 | 缺跑分的要标「无跑分」，不能装作有 |
| 品类 | 轻薄 50 / 游戏 41 / 台式 2 / 配件 4 | 配件不是整机，展示要区分 |
| 价格快照 | 2026-11-02 | 页面上要显示数据截止日 |

## 3. 功能清单（按用户旅程，逐条都要有）

### A. 首屏（用户还没说话）
1. 一句话价值主张 + 三个数字（97 台 / 22 台有人评过 / 4 类）
2. 口径说明：这 97 台里哪些能答"值不值得买"、哪些只能答"什么配置多少钱"
3. **示例入口**：从 `GET /api/demo` 取，前端**不许写死**（文案要跟后端能力同步）
4. 输入框 + 发送；支持 Enter 发送、Shift+Enter 换行
5. 顶部健康状态：`GET /api/health`（模型在线/离线），离线时要能说清"现在只能按规则答"

### B. 推荐结果（stage = `recommend`）
1. **首选卡**：机型名 / 完整配置 / 到手价（大号）/ 原价 + 国补拆解
2. **硬伤前置**：`blockers` 里 `level=hard` 的必须显示在优点**之前**；`soft` 的写成"不算强的地方"，不许写成"不能买"
3. **「仅参数」标识**：`hasReview=false` 时，卡片上要有明确徽标（这是本产品最容易被误解的地方）
4. **其他候选**：2 台，名字和价格要分开排（现在挤成一行了）
5. **决策依据**（默认折叠）：解析出的槽位、校验结果（数字可追溯/无库外机型）、数据快照日、排序侧重
6. `warnings`（超预算、放宽条件、限电提醒）用低饱和警示条，不要用红色报错样式

### C. 对话中的其他 5 种状态
| stage | 含义 | UI 要点 |
|---|---|---|
| `clarify` | 信息不够，反问 | 用 chips 给选项（品类/预算/用途/年限），可点选直接发送 |
| `followup` | 追问某台细节 | 纯文本 + 「正在讨论 XX」标识，**不要重复卡片** |
| `fit` | 「这台适合我吗」 | 结论前置（匹配/部分匹配/不匹配/数据不足），依据跟在后面 |
| `compare` | 两台对比 | 并列结构，只比数据里有的字段 |
| `exhausted` | 候选翻完了 | 明确说"这个条件下就这几台"，给放宽建议 |

### D. 三个"新增能力"必须在 UI 上留位置
1. **专业要求**：用户提到专业（如人工智能）时，回答里会带「你这组的配置要求 + 这台差在哪」。UI 要能把这段单独成块（引用样式），不要混在正文里。
2. **携带/重量**：回答会带「这台 X kg；同品类同预算里最轻 Y kg、最重 Z kg」。这是比较信息，做成小字注脚即可。
3. **清单模式**：用户说「把其余推荐列出来」时，回答是编号清单（第 2、3 名 + 配置 + 价格 + 是否有人评过）。UI 要能渲染有序列表，不要退化成一段话。

### E. 边界与拒绝
1. 库外品类（手机/平板/工作站）：`stage=refuse`，明说"不在覆盖范围"，不许软化
2. 库里没有的型号：明说没有，不许拿别的机器糊
3. 模型离线：降级到模板回答，页面上要有提示

## 3.5 可视数据 + 对话入口（首屏必须两者都有）

用户明确要求：**首页既要有可视数据，也要有能直接开口的对话入口**。不是"先看图表再进对话"，而是同一屏里共存。

### 3.5.1 布局建议（可以改，但两者都不能少）

```
┌────────────────────────────────────────────┐
│ 顶栏：品牌 · 数据快照日 · 模型在线状态          │
├──────────────────────┬─────────────────────┤
│ 左：对话区（主）        │ 右：数据概览（辅）      │
│  · 消息流             │  · 库构成（环图）       │
│  · 推荐卡             │  · 价位段分布（柱）      │
│  · 输入框（固定底部）   │  · 品类价格区间（条形）   │
│                      │  · 「这批数据可信度」说明 │
└──────────────────────┴─────────────────────┘
```
窄屏（<900px）时右栏折叠到对话下方，但**不许把对话挤成手机样式**。

### 3.5.2 可以画什么（全部来自 `GET /api/overview`，前端不许自己统计）

| 图 | 数据来源 | 必须标注 |
|---|---|---|
| **库构成**：22 台有人评过 / 75 台仅参数 | `review` | “只有 22 台能答值不值得买” |
| **价位段分布**：7 档各几台 | `priceBuckets[].n` | 柱子里用深浅区分 reviewed / noReview |
| **品类价格区间**：轻薄/游戏/台式/配件的 min–median–max | `byCat[]` | 配件不是整机，单独分组或加注 |
| **可加装分布**：0/1/2/3 档各几台 | `upgrade[]` | 说明 0 分 = 内存焊死 |
| **覆盖度**：有跑分 81 / 无 16；有重量 73 / 无 24 | `perf`、`weight` | 缺的那部分要画成"未知"，**不许画成 0** |
| **价格冲突**：6 处两层报价不一致 | `priceConflicts` | 只做可展开列表，不做结论 |

### 3.5.3 推荐结果里的对比图（这个最有用）

`kernel.ranked` 最多 3 台，天然适合横向对比：
- **价格**（到手价，条形长度）
- **跑分**（`perf`，缺的显示“无跑分”，**不要补 0**）
- **内存**（`ram`：8/16/24/32/64）
- **重量**（`weightKg`，缺的显示“库里没记”）
- **可加装**（`upgrade` 0–3，用 4 格信号格而不是分数）

同一台机器在不同图上颜色要一致；点任意条 → 该机型高亮，与左侧对话里的卡片联动。

### 3.5.4 可视化的三条红线（违反即打回）

1. **不许画库里没有的维度**：续航小时、游戏帧数、返修率、故障率、色准 ΔE、综合评分雷达图 —— 一个都没有数据。画了就是编。
2. **缺数据必须显示为“未知”，不能是 0、不能是灰色空条假装 0**。97 台里 16 台没跑分、24 台没重量。
3. **不许前端做任何聚合计算**（平均、中位数、排名、百分比）。`/api/overview` 已经把该算的算完了；需要新指标就说，后端加，不在 JS 里加。

### 3.5.5 对话入口（不许做成"点开始聊天"的二次跳转）

1. 首屏输入框**默认聚焦可用**，不需要先点按钮
2. 输入框上方一行示例 chips（来自 `/api/demo`），点一下直接发送
3. 图表 → 对话的联动（至少做一条）：点价位段的某一档 → 输入框预填「预算 XX，轻薄本」这类话术，**只预填不自动发送**（自动发送会替用户做决定）
4. 对话一旦开始，左栏消息流成为主区域，右侧数据栏保持可见（可收起），不要整屏跳走
5. 对话中途随时可以继续输入；加载态用三点动画，不要用全屏遮罩

## 4. 接口契约（照这个写，别猜）

### `POST /api/chat`
请求：`{text, known, asked, last_stage, seen, focus}`（前端每轮把上一轮返回的 `slots/asked/stage/seen/focus` 带回来）
响应：
```jsonc
{
  "stage": "recommend|clarify|followup|fit|compare|exhausted|refuse",
  "reply": "…",                    // 已过出口审计的成稿，直接展示，不要二次改写
  "slots": {...}, "asked": [...], "focus": "id", "focusName": "…",
  "kernel": {                      // 仅 recommend 有
    "mode": "…", "dataAsOf": "2026-11-02",
    "warnings": [], "questions": [],
    "untraceable": [], "outside": [], "fabricated": [],
    "ranked": [{
      "id","name","price","spec","perf","upgrade","portable",
      "tag","caution","original","subsidy","sources",
      "overBudget","blockers":[{"purpose","why","evidence","level"}],
      "noPerfData","hasReview","weightKg","ram"
    }]
  }
}
```
`GET /api/stats`：`total/reviewed/noReview/withPerf/noPerf/priceConflicts/byCat/dataAsOf`

`GET /api/overview`（**可视数据专用，能画的都在这里，别自己算**）：
```jsonc
{
  "total": 97, "dataAsOf": "2026-11-02",
  "review": {"reviewed": 22, "noReview": 75},
  "perf":   {"withPerf": 81, "noPerf": 16},
  "weight": {"withWeight": 73, "noWeight": 24, "min": 0.99, "max": 3.42,
             "note": "只有采集池记了实测重量；人工层没有，不参与统计"},
  "byCat": [{"cat":"thin","name":"轻薄本","n":50,"reviewed":10,
             "priceMin":3000,"priceMax":13499,"priceMedian":6336.575,"withWeight":39}, …],
  "priceBuckets": [{"label":"4000 以下","min":0,"max":4000,"n":8,"reviewed":…}, …],

```

`GET /api/demo`：`acts[].turns[]`（示例对话脚本）
`GET /api/health`：`{ok, ollama}`

**`reply` 是成稿，前端一个字都不要改写。** 它已经过了"不编数字、不串台、不替没评价的机器下结论"三道审计。

## 5. 视觉与文案调性

- **像编辑部，不像电商**：现在是米白底（`#FBFBF9`）+ 深绿（`#1C5B47`）+ 衬线大标题，克制、可信。可以优化，但不要变成大促红黄风。
- 价格用低饱和砖红（`#B1573A`），不要用电商那种刺眼红。
- 字重层级靠字号和留白，不靠颜色数量；全页强调色不超过 2 个。
- 版心 760–820px，桌面优先（**这是桌面网页，不要做成手机 App 或移动端优先**）。
- 空状态、加载态、错误态都要有，且文案是"人话"，不是"系统繁忙，请稍后再试"。

### 文案红线（违反即打回）
1. 不许出现「高达」「首选」「性价比高」「值得买」这类评价词——**除了机器本来就有 22 台的人工评价**，那些是数据里的原话
2. 不许把"没数据"写成"没问题"，也不许写成"有问题"，必须写成"没查"
3. 不许出现"库外品类"（手机/平板/工作站）
4. 不许前端自己算差价、算百分比、算排名
5. 不许把 `blockers` 里的硬伤藏进折叠区

## 8. 不要做的事

- 不要做手机端/移动端优先的版式
- 不要加"AI 智能推荐""大数据选机"这类不实的营销话
- 不要在前端生成任何推荐理由、总结、评分
- 不要把 75 台"仅参数"的机器包装成"精选推荐"
- 不要为了好看删掉 hard 级 `blockers` 或 `warnings`
