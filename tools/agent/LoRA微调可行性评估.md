## 一、用户三个问题，直接回答

### Q1：这个模型是不是多模态？要不要换纯文本版？

**不用换。本来就是纯文本。**

```
$ ollama show qwen3.5-4b
  architecture        qwen35
  parameters          4.3B
  context length      262144
  embedding length    2560
  quantization        Q4_K_M

  Capabilities
    tools
    thinking
    completion      ← 只有这三项，没有 vision
```

`Capabilities` 里没有 `vision`，说明拉下来的权重里**不含视觉投影层**，不需要另找版本。
用户担心的「下错成多模态版」这件事不存在，这一点可以放心。

### Q2：能不能用现有测试结果做 LoRA 微调？

**不能直接用，原因不是"数据少"，是"数据是坏的"。**

| 来源 | 表面数量 | 实际可用 | 为什么 |
|---|---|---|---|
| `logs/chat-2026-11-11.log` | 43 轮 | **19 条**（去重后） | 见下方致命问题 |
| `test_*.py` 里的用户输入 | 117 条 | **0 条** | 只有提问，没有回复；要重跑才有 |

**致命问题：日志是修复前产生的。**

```
日志时间范围 : 16:18:15 ~ 16:48:09
agent.py 最后修改 : 20:00
```

日志里明确留有坏死循环样本：

```
用户：我说的就是刚刚你给我推荐的那一台啊
系统：直接上 Redmi Book Pro 14……        ← 用户指代当前那台，系统换了台
```

这正是用户反复吐槽的死循环。**拿修复前的输出当真值训模型，等于把 bug 焊进权重里。**
这 19 条必须重跑后重新采样，一条都不能直接进训练集。

已写 `export_lora_data.py` 做这件事的自动化统计，实跑结果：

```
① 真实日志：原始 43 → 去重 19 条（平均提问 11.4 字 / 平均回复 119.8 字）
② 测试用例：原始 117 → 去重 117 条（全部缺 assistant）
③ 立即可用 19 条 + 需重跑 114 条 = 满打满算上限 133 条
   参考基线 500~1000 → 缺口 367 条
```

代码在 `tools/agent/export_lora_data.py`，`--write` 会落 `lora_data/train.jsonl`。

## 二、技术可行性：能跑，但有三个硬约束

### 2.1 环境一片空白（全部实测）

```
torch           缺
transformers    缺
peft            缺
trl             缺
datasets        缺
accelerate      缺
bitsandbytes    缺
Python          3.13.14
nvcc            command not found
GPU             NVIDIA GeForce RTX 4060 Laptop GPU, 8188 MiB, driver 616.56
磁盘 E:         477G 总 / 130G 可用
```

从零装齐要走一遍。**Python 3.13 是个坑**：`bitsandbytes` 对 3.13 的轮子支持较晚，
很可能要退回 3.11/3.12 建独立虚拟环境。这一步大概率会卡，属于"知道会疼但要试"。

### 2.2 现在这个权重不能训

```
$ ollama show qwen3.5-4b --modelfile
FROM E:\ollama\data\models\blobs\sha256-13c16f42...   (3.0 GB)
```

3.0 GB 是 **GGUF Q4_K_M 量化格式**。LoRA 训练需要 HuggingFace 格式的 FP16 权重，
4.3B 参数约 **8.6 GB**。也就是说：**要重新下一份权重**，不是把现有的拿来用。

下载体积 ≈ 8.6 GB（fp16），或 ≈ 4.3 GB（bf16 也差不多）。
E 盘剩 130G，空间够。

### 2.3 显存够，但紧

4B 参数做 QLoRA（4-bit 加载）：

| 项 | 估计占用 |
|---|---|
| 基座 4-bit | ≈ 2.5 GB |
| 激活（开梯度检查点，seq 1024） | ≈ 2~3 GB |
| LoRA 参数 + 优化器 | ≈ 0.3 GB |
| 合计 | **≈ 6~7 GB / 8 GB** |

**能塞进 4060 Laptop 的 8G，但没有余量。** 序列长度必须压在 1024 以内。
恰好现有回答平均 120 字（≈120 tokens），加上 464 tokens 的系统提示，1024 够用。

⚠️ 以上是**估算，未实测**。实际要等权重下来跑一次才知道会不会 OOM。

## 三、为什么说"方向要挪"：数据分类证据

这是我做这个评估时最想搞清的一件事 —— **这轮修的 bug，到底是"模型不会说话"，还是"代码写错了"？**

把 `语义理解缺陷-诊断与修复.md` 里的缺陷逐条归类：

| 缺陷 | 性质 | LoRA 能不能解决 |
|---|---|---|
| `clarify` 分支不返回 `known` | **代码错误**（漏 return） | ❌ 完全不能 |
| `seen` 只读不写，"换一台"死循环 | **代码错误**（从没往列表里塞东西） | ❌ 完全不能 |
| `_cn_to_int("七千五") → 7000` | **代码错误**（进位写错） | ❌ 完全不能 |
| `12,000` 被拆成 12 和 000 | **代码错误**（正则） | ❌ 完全不能 |
| `_cheapest` 被永久继承 | **代码错误**（状态继承） | ❌ 完全不能 |
| 超预算兜底文案自相矛盾 | **代码错误**（没带条件） | ❌ 完全不能 |
| 数据源里写「能开机」「地板价」 | **数据错误** | ❌ 完全不能 |
| 警告说两遍 | **代码错误**（拼接重复） | ❌ 完全不能 |
| 把 `mismatch` 说成「部分匹配」 | **语言问题** | ✅ 能 |
| 「完全没压力」（词表漏了） | **语言问题** | ✅ 能 |
| 「强 3 倍」自算相对量 | **语言问题** | ✅ 能（但代码也能拦） |
| 跨品类越界「台式机能给你 32G」 | **语言问题** | ✅ 能 |

**分裂非常干净：12 条里 8 条是代码/数据错，4 条是语言问题。**

而这 8 条代码错，恰好是用户抱怨最凶的那些（死循环、预算丢失、数字算错）。
**LoRA 对它们的作用是 0。** 一个把话说得再漂亮的 4B，也不可能因为微调就学会
"记得把 known 返回给前端"。

这就是为什么：**「RAG 为主」是对的，但 LoRA 不该放在"让模型更会推荐"这个位置** ——
那个位置的活儿 90% 是状态机，状态机学不进权重。

### 附带发现：提示词压缩这条收益也不存在

```
ANSWER_SYS   929 字符  ≈ 464 tokens
```

有人做 LoRA 是为了把长提示词固化进权重省 token。这里提示词才 464 tokens，
**省不出东西**，这个动机直接排除。

## 四、真正的天花板：34 台机器

```
$ 统计 data/prices.json
机型总数: 34
品类分布: phone 12 / thin 10 / gaming 6 / upgrade 4 / desktop 2
价格区间: 950 ~ 12124
字段覆盖: upgrade 22/34, portable 22/34, gb6 12/34, efficiency 2/34
```

这是**结构性上限**，换再多对话数据也突破不了。

假设真攒到 1000 条高质量对话，它们必然是这 34 台机器的反复组合。会发生什么：

1. **模型背下这 34 台** —— 而 RAG 已经存着这 34 台了，重复存储没有增量价值。
2. **权重里固化价格，和 RAG 打架** —— 这是最危险的。今天数据里 zhan66 写 5009，
   微调完权重"记得"5009；明天数据更新成 5300，模型会用权重记忆去覆盖 RAG 的答案。
   **项目的红线是"数字零写权限"，而 LoRA 天生就在给模型写权限。**
3. **泛化不到第 35 台** —— 明年新增机型全部落在训练分布外，LoRA 不但没帮助，
   还会用旧机型的措辞去套新机型。

## 五、如果真要做：唯一站得住的目标

### 5.1 别做「生成回答的 LoRA」

理由：回答必须严格受 `compose()` 的六道校验约束（编造/越证据/超预算/跨品类/相对量/结论改判）。
训练出来的模型学的是"像人一样说话"，而校验层要的是"一个字都不许乱说"。
**两者目标相反，LoRA 越成功，校验层拦得越多，白训。**

### 5.2 该做「理解输入的 LoRA」（NLU → 槽位）

这个位置 LoRA 有真实优势：

| 输入 | 现在靠什么 | LoRA 能补什么 |
|---|---|---|
| 「七千五」 | 正则 + `_cn_to_int` | 已验证 19/19，正则够用 |
| 「一万出头」 | 可能漏 | 泛化到没穷举过的口语 |
| 「万元以内」 | 可能漏 | 同上 |
| 「别超我半个月工资」 | 完全不会 | 需要推理，正则无解 |

**输出限定为槽位 JSON，绝不允许输出价格、机型名、结论。**
即使这样，正则仍要作为第二道独立校验 —— 两边不一致时，**以正则/代码为准**，
LoRA 的不一致率本身就是它的准确率指标。

### 5.3 外部数据的关键风险（用户说"可以再从别人那获取"，这条必须提醒）

如果拿的是别人的对话记录，里面**机器名和价格是别人的**。

直接拿来训，会教出这样的模型：用户问轻薄本，它脱口而出一个**我们库里没有的机型名**，
价格还是别的市场行情。这比不训更糟 —— 因为编造从"偶发"变成"权重里长出来的"。

**必须做的处理：**

```
别人数据 → 只保留「用户那句话」→ 丢掉「别人的回答」
        → 用我们自己的内核跑一遍，生成回答 → 这才进训练集
```

这叫自蒸馏。宁可要 300 条自己生成的干净样本，也不要 3000 条别人的脏样本。

## 十一、🔴 关键实测：槽位抽取的 LoRA 增量接近 0

这是决定「要不要训」的核心证据，先给结论：**在已测样本上，模型原生输出与最终结果 100% 一致，

方法（`diag_slot_gap.py`）：把 `extract_slots()` 拆成两段分别取值
- `raw_model()`：只取模型原生 JSON，不经 `normalize_slots` / `guard_budget`
- `agent.extract_slots()`：完整管线最终值
- 逐字段 diff，统计「被后处理修正」的比例

```

被后处理修正的样本: 0  (0%)
被修正的字段总数  : 0

全部 10 条一致，含「七千五」「五千八」「两千五」「九千九」「一万五」「一万二」「四万五」。

## 十二、锦上添花到底添在哪（回答用户直接提问）

用户问：「LoRA 微调可以锦上添花吗」——能，但要分清楚添的是哪朵花。

| 想添的能力 | 现状证据 | LoRA 有效吗 |
|---|---|---|
| 槽位抽取准确率 | 10/10 原生全对，后处理 0 次修正 | ❌ 增量≈0 |
| 去掉多模态 | 确认为多模态模型 | ✅ **但这是换模型，不是 LoRA** |
| 回答更自然不客服腔 | 6 道校验（编造/越证据/超预算/跨品类/相对量/结论改判）压着 | ⚠️ 有空间，但会被校验层重写掉 |
| 修死循环 / 预算丢失 / 金额算错 | 全是代码 bug（8/12 条缺陷属此类） | ❌ 完全无效 |
| 省系统提示词 token | `ANSWER_SYS` 仅 929 字符 ≈ 464 tokens | ❌ 省不出东西 |

**最关键的一条**：回答读起来僵，不是模型不会说人话，是安全层捆住了它。
LoRA 训得越"爱说"，`compose()` 六道校验触发重写的次数越多，训练效果被反噬。

### 唯一真正值得做的位置

**「推理型预算表达」的槽位抽取** —— 这类正则永远无解：
- 「别超我半个月工资」
- 「比上一代贵一千以内能接受」
- 「加上国补一共不超过八千」

判定条件（必须同时满足，否则不训）：
1. 全量 117 条上，模型原生槽位失败率 **> 10%**
2. 失败样本中存在**明显规律**（成簇，不是随机）
3. 纯提示词/正则兜底**解决不了**才轮到 LoRA

先试 (3) 的成本是 20 行代码，训 LoRA 的成本是 8 小时 + 8 GB 权重 + 一次失败的调试。
**顺序不能倒。**

| architecture | qwen35 | qwen3 |
| parameters | 4.3B | 4.0B |

| vision 层 | **有**（GGUF 未导出） | **无** |

新模型来自 `unsloth/Qwen3-4B-Instruct-2507-GGUF` 的 Q4_K_M（2.33 GB），
Modelfile 在 `E:/models/gguf/Modelfile.qwen3-4b-text`，已 `ollama create` 为 `qwen3-4b-text`。

```
fp16 权重也已下全（7.49 GB，`E:/models/Qwen3-4B-Instruct-2507`），4bit 量化加载实测只占 **3.60 GB 显存**。

### 13.2 🔴 实测结果：新模型更差

`test_slot_hard.py`（27 条推理型表达，同一套判据）：

| 模型 | 通过 | 失败率 |
|---|---|---|
| `qwen3.5-4b`（多模态，原用） | **26/27** | **4%** |
| `qwen3-4b-text`（纯文本，新装） | 21/27 | **22%** |

`test_multiturn.py`：两者都是 **8/8**，多轮能力持平。

### 13.3 新模型的失败方式更危险

这是决定不换的真正原因 —— 不是准确率低，是**它会编数字**：

| 输入 | 旧模型（多模态） | 新模型（纯文本） |
|---|---|---|
| 「预算就一个月工资吧」 | `budget: null` ✅ | `budget: 5000` ❌ **凭空编** |
| 「预算够买台MacBook就行」 | `budget: null` ✅ | `budget: 10000, cat: thin` ❌ **编数字+编品类** |
| 「宿舍功率有限，不能太大」 | `dormWatt: null` ✅ | `dormWatt: 1000, cat: desktop` ❌ **编瓦数+编品类** |

**旧模型遇到不确定会留空，新模型倾向于"给个答案"。**
这直接撞项目最硬的红线：**数字零写权限**。
一个会凭空填 5000 的模型，比一个会说"我不知道"的模型危险得多 ——
后者只是体验差，前者会推错机器。

另一个格式问题：新模型输出了 `"cat": "null"`（字符串），不是 JSON 的 `null`。
虽然 `normalize_slots` 会兜住，但说明它对该 schema 的遵从度更弱。

### 13.4 尝试过的最小修复（有效但不彻底）

在 `SLOT_SYS` 后追加严令「没说数字不许填，宁可留空」：
- 「一个月工资」→ `budget: null` ✅ 修好
- 「宿舍功率有限」→ `dormWatt: 1000` ❌ 仍编
- 「主要剪 4K」→ `"cat": "null"` ❌ 仍非标准 null

**结论：提示词能压住一部分，压不干净。** 而"压不干净"在数字红线上等于没压。

### 13.5 决策

**继续用 `qwen3.5-4b`（多模态版）。** 理由：

1. 槽位准确率 4% vs 22%，**差 5 倍**
2. 新模型会编数字，触碰红线，而这个风险无法用提示词完全消除
3. 多模态只是"带了不用的能力"，代价是 0.5 GB 体积；相比之下编数字的代价是整个项目可信度

**⚠️ 但记录一个待验证项**：本次对比只用了 27 条 + 8 条，样本量小。
若后续发现 `qwen3.5-4b` 在真实使用中仍频繁编数字，可回来重做这组对比（判据、脚本都已就绪，
换 `MODEL` 常量一行即可复跑）。

**这个结论推翻了我自己前面"换纯文本版更好"的推测。用户最初让我换版本的直觉是对的
（确实该避开多模态），但实测发现换来的这个纯文本版质量不够，权衡后不换。**
