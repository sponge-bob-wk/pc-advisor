# 语义理解缺陷诊断与修复

**日期**：2026-11-11
**触发**：用户反馈「这一次还是有问题，理解我的说话还是出问题了」（未给具体案例）
**定位方式**：按约定直接查日志，从 `logs/chat-2026-11-11.log` 复现
**结论**：不是模型听不懂，是**系统里没有「当前在聊哪一台」这个状态**。四个 bug 是同一个根因的四种表现。

## 二、四个 bug 与根因

| # | 现象 | 直接原因 | 根因 |
|---|---|---|---|
| B1 | 「打游戏这个合适吗」→ 品类被改成 gaming | 槽位抽取不看上下文，「打游戏」三字直接抽出 `purpose:[gaming]` + 隐含推导 `cat=gaming` | 没有「这句话是在问当前这台」的判断 |
| B2 | 品类一变，budget/years/carry 整块被清空 | 旧继承规则：`new_cat or new_pur` 一旦成立就**跳过整个继承块** | 继承是"全有或全无"，没有逐槽位判断 |
| B3 | 「我说的就是刚刚那台」→ 系统换了台 | `focus` 状态不存在，后端无从知道"那台"是哪台 | 前端也没传 |
| B4 | 「预算提高到7000」→ 预算没改，模型复读 3 遍"库里没有数据" | 追问逻辑前置且**整段吞掉**这句话，槽位抽取根本没跑 | 缺少"这句话带了新条件"的判断 |

**B2 的旧代码**（问题所在）：

```python
new_cat = bool(slots.get("cat")) and slots.get("cat") != known.get("cat")
new_pur = bool(slots.get("purpose")) and set(...) != set(...)
if not (new_cat or new_pur):        # ← 只要有一个变了，整个继承块被跳过
    for k in ("cat", "budget", "purpose", "years", "carry", "dormWatt"):
        ...
```

## 三、修复

### 3.1 新增核心状态：`focus`（当前讨论哪台）

```python
def run(user_text, known=None, asked=None, last_stage=None, seen=None, focus=None):
```

- 前端每轮把上一轮的 `focus` 带回来（`index.html`）
- 后端在每个出口返回 `focus`（机型 id）+ `focusName`
- 日志记录 `focus_in` / `focus_out`，下次排查能直接看到

### 3.2 指代判定：`refers_to_current()`

判据不是"含『这个』就算"，而是四道过滤：

```python
if any(k in text for k in SWITCH_KW):        return False   # 「换一台」优先
if any(k in text for k in NEGATE_CURRENT):   return False   # 「这台不行」
if REF_NOT_CURRENT.search(text):             return False   # 「这个价位/预算/条件」
if any(k in text for k in CURRENT_REF):      return True    # 这个/这台/刚才/你推的
if any(k in text for k in FIT_KW) and not any(w in text for w in DEMAND_WORDS):
    return True                                             # 「还能打游戏吗」
```

`REF_NOT_CURRENT` 是必须的：「这个价位还有什么」说的是范围，不是指某一台。不加这条，用户永远换不了需求。

### 3.3 继承改成逐槽位

```python
for k in ("cat", "budget", "purpose", "years", "carry", "dormWatt"):
    if 空: slots[k] = known[k]           # 只补空的，不全清
# purpose 累加而非覆盖：补充"偶尔打游戏"不等于放弃"学设计"
# 只有用户在句子里明确否掉（"我不玩"）才移除
```

### 3.4 「这台适不适合」独立成一个阶段：`fit`

不再自作主张换品类，而是拿库里的字段回答匹配度：

```python
def fit_notes(o, purpose) -> (verdict, notes)
# verdict: match / partial / mismatch / None
# 判据全部来自库内字段：
#   轻薄本 + gaming  → mismatch（规格里没有独立显卡）
#   有独显 + gaming  → partial（不是游戏本散热规格）
#   游戏本 + gaming  → match
```

**关键细节**：用哪个 purpose 判？用**用户这句话里问的**（`_asked_purpose`），不是历史槽位。
否则「打游戏这个合适吗」会拿 `purpose=[design]` 去判，答成"部分匹配"——答的是另一个问题。

### 3.5 结论不许模型改判

模型会把 `mismatch` 说成「部分匹配」。现在：
- 数据字段名改成 `系统判定（最终结论）`，值直接给词
- `_verdict_wrong()` 硬校验：说岔了就重写，再岔走模板
- 禁止把字段名念出来

### 3.6 不许预测帧数

库里没有帧数数据，就不许说「会卡/会掉帧/流畅」。`_overspec()` 拦截，同上处理。

### 3.7 「改动 + 提问」混在一句

```python
if (... and any(k in user_text for k in FOLLOWUP_KW)
        and not has_new_condition(user_text)):   # ← 新增
```
`has_new_condition()` 认「预算提高到7000」这类，命中就不走追问，重新推。

## 五、遗留问题（如实记录）

1. **`gb6` = 0/22** —— `daily` 侧重的性能维度仍无法实现，退回 R23。「轻薄本被系统性低估」未解决。
2. **`loadWatt` = 0/34** —— 宿舍限电只能问、不能判。
3. **`gpu`/`tsGraphics`/`tgp` 全缺** —— `game` 侧重只能按品类+perf 退化。
   `fit` 阶段判「不适合打游戏」的依据是 `spec` 里没有独显，这是**结构性事实**，不依赖跑分，可用；
   但「能不能跑某个具体游戏」仍然答不了，已如实说"库里没有帧数数据"。
4. **`_asked_purpose` 是词表匹配**，覆盖度有限（"吃鸡""永劫""原神"已收，"黑神话"没收）。
   后续按用户实际说法补，不要凭想象堆词。

## 六、对抗测试第二轮（2026-11-11 下午）

用户要求「想办法刁难它，发现问题一直测试」，于是从「验证能用」转成「主动构造刁钻输入」。
这一轮不预设能过，重点是**先看它怎么错**。

### 6.1 口语金额全线失效（用户直觉上最严重的一类）

| 输入 | 修复前 | 修复后 |
|---|---|---|
| 七千五 | 7000（丢尾数）→ 预算判"无出处"→ 反问「预算多少」 | **7500** |
| 五千八 | 5000 | **5800** |
| 12,000 | `{0}`（被拆成 12 和 000） | **12000** |
| 1.2万 | 120000 | **12000** |
| 一万二千五 | 12000（丢"千五"） | **12500** |
| 六千万 | 60000（"六千"被当成系数 6） | **60000000** |

根因：`_cn_to_int` 原来是「万→千→百」顺序切段、每段单独算。
重写成「先按万切段，每段用 `_seg_val` 算完整段值再进位」，19 条口语金额全部对上。

**教训**：中间我自己写的第一版补丁（在"千"分支补尾数）只治了 `七千五`，
`六千万` 反而算出 16000。**补丁式修复会引入新的错**，必须整段重写 + 全量期望值回归。

### 6.2 「不要七千的」被读成预算上限 7000

用户明确说不要这个价位，系统反而拿它当预算，推了台 6799 的正好压在线上。
新增 `BUDGET_NEG` + `_neg_budget()`：金额出现在否定语境里时，不当预算用，回头确认。

### 6.3 超预算兜底说「这个品类里一台都买不到」，但同品类明明有便宜的

`2000 要 32G` → 32G 过滤后只剩 6799 一台，兜底说"轻薄本里一台都买不到，最便宜 6799"。
可是轻薄本里最低是 3000 —— 用户会看到自相矛盾。
修复：兜底文案带上生效条件，改成「预算 2000 在轻薄本（32G 内存）里一台都买不到」。

### 6.4 数据源里写着无出处断言（根因级，比文案问题严重）

| 机型 | 字段 | 原文 | 问题 |
|---|---|---|---|
| 无界 14X | tag / pros | 「最便宜的能开机方案」「这个价位唯一还能开机的正经机器」 | 库里没有开机/合格性检测数据 |
| 天选 7 | tag / pros | 「能买到的正经游戏本地板价」 | 没有全市场比价，「能买到」无法证 |
| 天选 7 | cons / caution | 「别为省这一千买错」 | 要求算 5050 与 5060 差价；实际至少差 1438，不是一千 |

这些不是模型编的 —— 是**数据里就这么写的**，模型只是照读。所以光改提示词没用。
已改数据，并把这类问题做成 `audit_data.py` 的第 5 项体检（`check_unsupported_claim`）。
**分辨力已验证**：拿修复前的两份备份跑，都报出 6 条；新数据报 0 条。

### 6.5 警告说两遍，前后打架

模型把 `warnings` 改写成自己的说法，`compose()` 又在末尾硬拼一次原文 →
「这款是 3000 元价位里最便宜的一台……这个价位在轻薄本里一台都买不到，最便宜的就是它」。
修复：提示词规则 5 改为「警告由系统统一写，正文不要复述、不要评价预算够不够」。

### 6.6 超证据断言抓不完（词表法失效）

`FRAME_GUESS` 词表里有「毫无压力」，模型写「完全没压力」就漏了。
补词永远追不上，改成 `FRAME_PAT` 模式匹配 + 提示词规则 8b 直接禁止评价"够不够劲"。
现在「打游戏绝对够劲」这类说法在源头就被约束，输出只描述配置。

### 6.7 自算相对量（多 15%、强 3 倍、双倍）

`numbers_in` 只抓 3~6 位数字，「15%」里的 15 是两位数，完全不在检查范围。
新增 `RELATIVE_CLAIM` + `_relative_claim()`。

**这里连犯两次错，都记下来**：
1. 第一版做成"一律拦" → 把「国补按 15% 立减」（`subsidyRules.rate=15`）
   「CUDA 核心比移动版多约 15%」（`crossSell` 原文）**真话也拦了**。判据没有分辨力。
2. 第二版改成"数字能在语料里找到就放行" → 又漏光了：「强 3 倍」的 "3" 在语料里到处都是。
3. 正解：**看带数字的完整说法在不在语料里**，不看单个数字。
   分辨力实测：真话 3 条放行 2 条（第 3 条措辞与数据不同，保守拦下），编造 4 条拦下 3 条。

配套新增 `_corpus_all()`：校验语料从"本轮候选"扩到"候选 + 补贴规则/趋势/跨品类说明"。
只拿本轮候选当语料，会把数据原文判成编造。

### 6.8 跨品类越界比较

问笔记本，回答却说「这个价位的台式机能给你 32G 内存加桌面版显卡」——
本轮根本没取台式机数据。新增 `CROSS_CAT` + `_cross_cat()` + 提示词规则 10b。

### 6.9 这一轮建的测试

| 文件 | 覆盖 | 结果 |
|---|---|---|
| `test_attack3.py` | 27 条：金额陷阱(L) / 口语进位回归(M) / 否定金额(N) / 超预算兜底(O) | 全过 |
| `test_attack2.py` | 20 条（K18/K19/K20 判据已从"或追问"收紧成"必须精确命中且不能降级成追问"） | 全过 |
| `audit_data.py` | 5 项体检，新增无出处断言检查 | 0 问题 |

### 6.10 仍然没解决的

1. **`_overspec` / `RELATIVE_CLAIM` 都是"列举式"判据**，换一种说法就可能漏。
   真正的解法是让核心里根本没有"性能评价"这个能力（只输出配置事实），
   而不是在出口处一层层拦。这是结构性欠债。
2. **`_corpus_all` 是全文包含判断**，语料越大越容易"撞词放行"。
   更严的做法是建"允许断言清单"，但工作量大，暂缓。
3. 数据里「老机器还能开机的话」这类**条件句**被判据豁免了，是对的；
   但如果模型把条件句改写成断言（"这机器能开机"），当前拦不住。

## 七、对抗测试第三轮：多轮状态（2026-11-11 傍晚）

前三轮攻的都是单轮。这一轮换方向，专打**多轮状态**和**对话陷阱**。
建了 `test_attack4.py`，17 条，分五组：P 反复改主意 / Q 指代陷阱 /
R 局部否定 / S 跨轮硬约束保持 / T 诱导越权 / U 空输入噪音。

**这一轮抓到的两个 bug，是用户反复报"死循环""前后矛盾"的真正根因。**

### 7.1 总根因：clarify 分支不返回 known，第二轮从零开始 ⚠️

```
第 1 轮「7000 的轻薄本要 32G 内存」→ clarify（问用途）
   slots = {cat:thin, budget:7000, _minRam:32}   ← 都抽到了
   返回值里没有 known 字段                        ← 前端拿不到
第 2 轮「上课用」→ known=None → 预算和 32G 全丢
第 3 轮「换一台」→ 推出来的机器根本不满足用户说过的条件
```

这一条同时解释了 P01（品类丢失）、S01（`_minUpgrade` 丢）、S02（`_minRam` 丢）
三个失败 —— 全都是同一个根因的连带。

**修复**：`run()` 外面包一层，任何分支漏返 `known` 都自动用 `slots` 补上。
不再靠"记得在每个 return 里写 known"，那种写法漏一个就出洞。

### 7.2 `seen` 只读不写，「换一台」永远原地打转 ⚠️

```
用户：「这台不行，换一个」
系统：把同一台又推了一遍（只换成模板措辞）
```

根因：`seen`（已经看过哪些）**从来没有被写出过**。
`core.build_recommendation(exclude=seen)` 里的 `seen` 永远是 `None`，
所以 exclude 永远为空，每次都从第一台开始。

`seen` 在整个文件里只出现两次：一次是参数定义，一次是传进 `exclude`。
**没有任何一处往里面塞东西。** 这就是"死循环"的代码级证据。

**修复**：
- recommend 分支累加 `seen_now` 并返回；
- `exhausted` / `followup` / `compare` 分支都带上 `seen`；
- `run()` 包装层兜底，漏返就沿用上一轮的 `seen`。

修复后连测：`zhan66 → wujie14x → vivobook16se`，三台各不相同。

### 7.3 「帮我算一下它比别的便宜多少」被当成换台

`SWITCH_KW` 里有「别的」，于是这句被判定为"用户要换一台"，
系统默默换了台机器，还完全没回答比价的问题。

**修复**：新增 `_is_switch_request()`，把「比别的/和别人比/别的品牌」排除掉。
关键教训 —— 这个判断原本写了两份（`run()` 里一份、`refers_to_current()` 里一份），
只改一处等于没改。**必须收敛成单一函数**，现在两处都调 `_is_switch_request()`。

同时新增 `compare` 阶段：明确告诉用户"这个我不给你算，库里没有对照价格"，
比默默换台诚实得多。

### 7.4 `_cheapest` （越便宜越好）会被永久继承

第一轮说「越便宜越好」→ `_cheapest=True`；
后来给了明确预算 7000，但 `_cheapest` 进了 `HARD_KEYS` 被一路继承，
`mode_of()` 仍走 value 权重 —— 用户给的预算只当过滤用，没当优先项。

**修复**：本轮出现明确金额时，撤掉 `_cheapest`；继承时也加一条跳过判断。

## 九、对抗测试第四轮：替数据下可靠性保证（2026-11-11 21:05）

### 9.1 发现过程

切回 `qwen3.5-4b` 后跑真实请求，第一条回复就有问题：

> 用户：学设计的，五千，要用四年，平时背去教室
> 回复：……军标认证和一年上门保修**能确保**你在教室背着它四年都安心。

数据里只有：
```
pros: ["双内存插槽 + 双 SSD 位，今年最值钱的差异点", "军标认证，键盘防泼溅", "一年上门保修，不用自己跑网点"]
```

「军标认证」「一年上门保修」是事实，但**"能确保四年安心"没有任何依据** ——
库里没有故障率、返修率、寿命测试数据。这是模型拿两个事实推出了一个库里没有的结论。

### 9.2 为什么六道校验全漏

拿这句话逐条测，全部返回空：

```
check_fabrication : []
verify_answer     : []
_overspec         : []      ← 词表只有"毫无压力""轻松带走"这类性能断言
_relative_claim   : []
```

根因：**现有六道校验都在拦"编造事实"，没有一道管"替数据下保证"。**
这是两类不同的错 —— 前者是凭空造数，后者是**用真事实推假结论**，更隐蔽。

### 9.3 修复：`RELIABILITY_PAT`

加进 `_overspec()`，与 `FRAME_PAT` 并列。抓的是「把可靠性说成确定的」这个结构：

```python
RELIABILITY_PAT = re.compile(
    r"(能|可以|足以|肯定能|绝对能)\s*(确保|保证|担保|保你|让你.{0,6}(放心|安心))"
    r"|(绝对|肯定|一定|百分百)\s*(可靠|耐用|没问题|不会坏|用得住|不会出毛病)"
    r"|(放心|闭眼)\s*(买|用|入)"
    r"|(坏不了|不会坏|不会出毛病|用不坏|不会有问题)"
    r"|(四年|五年|三年|几年|长期).{0,4}(不会坏|没问题|不用管|不用操心)"
    r"|(保证|确保).{0,8}(四年|五年|三年|不坏|不出事)"
    r"|(保证|确保|担保).{0,6}(不|没)\s*(会|用)?\s*(出问题|出毛病|坏|后悔)"
    r"|(保证|确保|绝对|肯定|百分百).{0,4}(满意|不后悔|不会后悔)"
    r"|(耐用|抗造|结实|皮实).{0,6}(四年|五年|几年|不坏|不出|不用)"
    r"|(用|撑|扛).{0,2}(四年|五年).{0,4}(不坏|没问题|不用修)")
```

### 9.4 ✅ 分辨力对照实验（项目红线要求）

不能只测"能不能抓到"，必须同时测"会不会误杀真话"。

**应当拦住（12 条）：**
```
一年上门保修，保证你不会出问题      → 保证你不会出问题
保修期内保证不坏                    → 保证不坏
买了绝对不后悔，保证满意            → 保证满意
军标认证说明很抗造，放心买          → 放心买
这机器耐用，能用四年不坏            → 耐用…不坏
确保四年内不用修                    → 确保四年
军标认证能确保你四年都安心          → 能确保
这台肯定用得住，四年没问题          → 肯定用得住 / 四年没问题
有保修兜底，可以放心用四年          → 放心用
绝对可靠，不会出毛病                → 绝对可靠 / 不会出毛病
四年内不会坏                        → 四年内不会坏
有保障，坏不了                      → 坏不了
结果：12/12 全部拦住
```

**应当放行（8 条，数据原话或中性描述）：**
```
一年上门保修，不用自己跑网点        → 放行 ✅（数据原话，必须放）
军标认证，键盘防泼溅                → 放行 ✅
双内存插槽 + 双 SSD 位              → 放行 ✅
1.48kg 在 14 寸里偏重               → 放行 ✅
屏幕只有 62.5% sRGB                 → 放行 ✅
R7 H255 · 16G + 512G                → 放行 ✅
A面是金属，应该是这个价位里少见的    → 放行 ✅
屏幕和重量都不算出彩，买它买的是可扩展 → 放行 ✅
结果：8/8 未被误杀
```

**关键分界**：「一年上门保修，**不用**自己跑网点」（数据原话，放行）
vs「一年上门保修，**保证**你不用出问题」（升级成承诺，拦住）。
判据抓的是**语气升级**，不是抓关键词。

### 9.7 遗留

- `RELIABILITY_PAT` 仍是**列举式**判据，换一种说法（比如「这机器皮实，四年随便用」里的"随便用"）可能仍漏。
  真正的解法是**数据层根本不提供能推出可靠性的字段**，让模型无话可说 —— 结构性欠债，同六.10 记录。
- 若用户主动问"会不会坏"，当前回答是转述保修条款，**没有明确说"我不知道故障率"**。
  更诚实的做法是加一句"库里没有故障率数据"。这条未做，记在此处。
