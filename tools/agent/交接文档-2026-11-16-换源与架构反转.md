## 4. 架构：模型为主，规则兜底（本轮最重要）

### 4.1 设计

**一次模型推理出全部路由决策**，不是每张词表各调一次（那会 3×0.23s）：

```json
{"intent": "六选一", "topic": "追问的哪一面(11选一)", "fit": true|false}
```

```
_run 入口
  └→ intent_layer.route(text, focus)     ← 每轮只调一次，存 _LAST_ROUTE
       ├→ model_route()：模型一次出 intent+topic+fit（缓存共享）
       ├→ classify()：intent 过规则否决层（模型已知偏向的矫正）
       └→ topic/fit 缺失时词表兜底
  └→ 本轮所有路由点读 _LAST_ROUTE：
       asks_about_current / named 分流 / _topic_facts 裁事实
```

### 4.2 模型负责什么、规则保留什么

| 路由面 | 反转前 | 反转后 |
|---|---|---|
| 六类主意图 | 模型为主（11-13 已做） | 同左 |
| 追问主题（问的哪一面） | FOLLOWUP_KW 30 词 | **模型 topic 字段** |
| 匹配度（这台行不行） | FIT_KW 11 词 | **模型 fit 字段** |
| 追问总入口 `asks_about_current` | 词表并集 | **模型优先** |
| named 分支分流 | 词表 | **模型 fit/topic** |
| `_topic_facts` 裁事实 | TOPIC_TRIGGER | **模型 topic**（英文→中文映射表 `_ROUTE2CN`） |

**规则只保留两种身份**（这就是"兜底"的全部内容，不许再加第三种）：
1. **形态明确的硬否决** —— 每条背后都有一次真实翻车，见 §4.3
2. **降级兜底** —— 模型挂了/超时/字段非法（`model_ok=False` → 全词表，系统必须还能跑）

### 4.3 否决层清单（每条都有事故记录，别删）

都在 `asks_about_current` 和 `intent_layer.classify` 里，按生效顺序：

1. `_CONSTRAINT_FORM`（"我的要求是…"）→ 给条件不是追问 —— M05 真实事故
2. `_GIVE_COND_VERB`（"提高到/加到/控制在…"）+ 无疑问形态 → 更新槽位，**即使模型判了 ask_current** —— 「预算提高到7000，屏幕素质我有要求」被模型判成问屏幕
3. `topic=price` / `PRICE_Q_KW` 命中（**排除**保值/二手/残值）→ 让位给价格位置专门通道 —— 「这个价算什么水平」必须代码实算排名；「它保值吗」是机器属性要留在追问
4. `pros_cons` 不算具体面 → 「联想小新16如何」是整机泛问，走 intro 引导，不倒缺点
5. 「还有更X的吗」（4f2）→ 换台不是列清单 —— 「还有更便宜的吗」被模型判 list_others
6. `unmatched_model_name` 改**前缀对齐**（§7 坑 7）—— 中间子串误命中

### 4.4 数据里的标记（都是反转时加的，别丢）

- offer 的 `priceIsEstimate`（bool）—— 平台标价≠到手价，**必须在 `core.build_recommendation` 的投影里透传**（首版在这里丢过，见 §7 坑 3）
- `_pool_to_offer` 的 `origin`（"zol"/"jd-pool"）—— 靠 `m.get("source")=="zol"` 判断，转换层漏了 source 字段就全变 jd-pool
- `agent._price_label(o)` + 出口替换 `re.sub(r"到手\s*价?", "平台标价")` —— 提示词管不住模型，口径校正在**代码出口**做

## 6. 红线（全部继承自主交接文档，本轮新增 3 条）

继承：数字零写权限 / 没数据≠有数据 / 不许把"查不到"写成"没有" /宁可弃权不许自信地做错 / 判据只能代码定，模型无权发明 / 注释和代码不许相反。

本轮新增：
1. **价格口径不混**：`price.final`（到手价）和 `price.list`（标价）是两个口径，任何字段、文案、判断都不许混。混了的表现是"数字全对、口径全错"——用户不会怀疑
2. **"上游加标记、下游要用"的字段必须过投影层检查**：`build_recommendation` 返回的 ranked 是**重新投影**的对象，加在原始 offer 上的字段在这里会被丢掉
3. **去重判据：确认不了就都留着**——宁可冗余不可误删。配置指纹四项（cpu数字/ram/storage/gpu）全有值且相同才判重

## 7. 坑清单（按"会不会再踩"排序，全部实测）

1. **ZOL 页面下方的竞品价格**：全局搜"参考价：￥16999"抓到的是 ROG 幻X 的价——只认「平台域名 + price-cell」结构
2. **`price.final` 只认到手价 → ZOL 163 台静默全丢**：`_pool_to_offer` return None 不报错，池子大小没变就以为没采到。修法：`final or list` + `priceIsEstimate` 标记
3. **投影层丢字段**：`priceIsEstimate` 加在 `_pool_to_offer` 里，`build_recommendation` 的 ranked 投影把它丢了 → 出口校正拿到 None 整段白写。**教训：加了字段必须查投影**
4. **硬约束在排序后过滤只对前 12 台**：池子 80 台时没事，243 台时前 12 台恰好全是无 upgrade 数据的 → 0 候选，且 warning 写"已放宽"实际没放宽。修法：排序**前**对全池过滤
5. **品牌取名称前两个字**：ROG→RO、ThinkPad→Th。"redmibookpro14" 含子串 "ro" → 触发品牌否决 → 问 Redmi 答不上来。修法：品牌词典 `_BRAND_DICT`（子品牌归母公司）
6. **`_cpu_key` 缺 Intel 连字符规则**：跑分表 `i7-14650HX` vs ZOL `i7 14650HX` 对不上，18 台被判无跑分。补 `i(\d)\s*-\s* → i\1 `（和 AMD 那条对称，只增不减）
7. **`unmatched_model_name` 双向包含太宽**：`vaiosx14` 中间含荣耀 X14 的别名 `x14` → 该报"库里没有"的没报。修法：前缀对齐（startswith）
8. **池子变大后型号歧义**：Y7000P 3 台、极光X 6 台、隐星P16 2 台 → `match_named_model` 并列弃权是**正确设计**（"暗影精灵怎么样"早就是这判据）。测试期望同步更新，理由写在测试里
9. **`config_key` 两次失效**：读错字段（池格式是 `ram.gb` 不是 `ramGB`）+ 正则 `\d{4,5}`（Ultra7 255HX 只有 3 位）。**去重是否生效要独立统计验证，别信脚本自己报的 0**
10. **ZOL 分页路径**：notebook/cell_phone 可翻页；**desktop_pc 分页恒 502 但首页有 79 个 id**（FLAT_CATS 模式）；memory 参数结构不同未纳入
