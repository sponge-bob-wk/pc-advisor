## 1. 这是什么

一个**对话式选机助手**。核心不是"排行榜"，是一条站得住的推导链：

```
用户说预算和用途 → 代码确定性排序 → 模型只负责把结果讲成人话 → 出口审计拦截编造
```

**架构分工是硬边界（这是整个项目的立身之本）：**

| 层 | 文件 | 谁干 | 不许干什么 |
|---|---|---|---|
| 排序内核 | `core.py` | **纯函数，不依赖模型** | 不做措辞、不调 LLM |
| 组装层 | `agent.py` | 模型只做两件事：<br>① 人话 → 槽位 ② 数据 → 人话 | **数字零写权限**，不许自己算、不许换推荐对象 |
| 出口审计 | `agent.py` 的判据函数 | 纯规则，拦模型 | 判据必须过分辨力对照 |
| 服务 | `server.py` | HTTP + 前端联调 | 不碰业务逻辑 |
| 前端 | `index.html` | 单文件 | |

**模型**：`qwen3.5-4b`，本地 Ollama（`http://127.0.0.1:11434`），`temperature=0`。

## 3. 核心机制：三层数据（**这是理解所有数字的关键**）

```
① 采集层（京东）     80 台   ← machine_pool.json，只有参数和价格

③ 淘宝 145 条        不进推荐池（仅 1 条单 SKU，无法跨源对齐）
────────────────────────────────────────────
推荐池 = ② ∪ ① = 93 台（去重后），其中只有 22 台有人写过优缺点
```

**为什么是 97 而不是 100**：首版报 100 是去重键有洞。修好后少掉 5 台 ——
3 台两层重复（天选7 / 小新 Air 15 / REDMI Book Pro 14）+ 1 台池内真重复（荣耀 MagicBook Pro 16）。

**池子构成（实算）：**
```

  池内真重复        1 处    ← 荣耀 MagicBook Pro 16，¥8455 vs ¥6969
```

## 4. 已经踩过的坑（**别重犯，每一条都是实测打回来的**）

### 4.1 判据漂移 —— 同一个洞被踩了四次

**"判据只写一遍，其余路径调它"是产品宪法第 9 条。** 已经复现四次：

| # | 路径 | 现象 |
|---|---|---|
| ① | `compose()` 的 `_audit` | 有「参数当卖点」判据（基准） |
| ② | `answer_followup()` 的 `_f_audit` | 漏了 → 追问答「看着非常细腻通透」 |
| ③ | `_answer_current()` 的 `_bad_answer` | 漏了 → 答「屏幕色彩很好」 |
| ④ | `_intro_model()` 的 `_bad` | 漏了 → 点名问机器通篇编造 |

第④处最难看，因为它走的是**最常见的入口**（用户点名问一台机器、还没说用途）。
六条判据在跑，全部放行 —— 不是判据不好，是**没被调**。

### 4.2 扩池带出来的连锁问题（v0.4 → v0.4.1）

池子从 22 扩到 97（现 93），**推荐列表变了但取数口子没变**，两个口子各埋一个洞：

- `get_offer()` 仍查 22 台 → 采集池机器成为 focus 后返回 `None`
  → **后续所有判据拿到 `m=None` 全部 `return None` 放行** → 模型对着空数据自由发挥
- `match_named_model()` 仍查 22 台 → 刚推荐给用户的机器，点名追问时答「库里没采到这台」

> ⚠️ 这类 bug 的特征：**判据单测全绿，端到端却编**。因为单测拿 `m` 直接调，
> 端到端里 `m` 是 `None`。**判据测试必须包含"输入无效时它会怎样"。**

### 4.3 去重键的三个版本（v1 → v2 → v3 → v3.1）

```
v1  只按全名          → 品牌前缀不一致的合不上
v2  名字 + 完整 spec  → 失败，采集层 spec 是代码拼的、人工层是手写的，格式对不上
v3  名字 + 显卡型号    → 基本正确
v3.1 补两个洞：
     ① 括号必须先剥（采集层把配置写在名字里：天选7 2026（锐龙7 H260/RTX5050））
     ② 四位年份要剥，但型号代数不能剥（天选7 的 7 是代数，6 代和 7 代是两台机器）
```

**两个更隐蔽的坑：**
- **去重范围不许扩到池子内部**。第一版修好键后价格冲突从 2 条涨到 8 条，全是自己造的 ——
  因为 `seeded[k] = o` 在循环里继续加，导致采集池内部互相去重
  （小新 Pro 14 锐龙版 ¥6629 / 酷睿 Ultra 7 版 ¥8329 被合成一台，丢掉一整台机器）。
  修法：`base_keys` 隔离，**只有人工层的键有权"吃掉"采集层条目**。
- **池内真重复要按原始全名判，不能按去重键**。键相同只说明「型号本体+显卡一样」，
  不代表同一条记录（差内存硬盘的两台本来就该同键）。改用剥括号前的原始全名。

### 4.4 点名匹配（97 台后难度陡增；现 93 台）

三个修正：
1. 生成别名**前**先剥括号（否则「暗影精灵 11（2026，Ultra7-251HX/RTX5060）」的中文主体变成 `暗影精灵，`）
2. 「锐龙版/酷睿版」**不是泛词**，不能从 `GENERIC_TOKENS` 剥 —— 它们是用户真正用来区分机型的词（差价 4000+）
3. 数字后的单个字母（`14x` 的 `x`）是型号后缀，要保护不被剥

两个否决条件：
- **否决④加绝对差**：只按比例判太松（短名字天然贴得近）。"惠普战 66" vs "战66" 差 2 个字被判弃权，实际是同一台。改成「长度差 ≥2 才弃权」；差 1 时看多出来的字符是不是字母/数字。
- **否决⑤裸主体弃权**：「暗影精灵怎么样」不许认成「暗影精灵 Pro 15」（池里有 3 台）。判据**动态算**哪些别名被 ≥2 台共享，不硬编码。

### 4.5 追问模板：问屏幕不许念整条 spec

实测：问「屏幕怎么样」，答出「R7 H260 · 16G + 512G · RTX 5050 · 2.5K 165Hz OLED」——
问屏幕，答了 CPU 内存硬盘显卡。

根因：`if any(k in spec for k in SCR_KW)`，而 `SCR_KW` 含「OLED」，整条命中。

修法 `_screen_part()` 两层切分：
1. 按 `·` 分段
2. 每段用屏幕锚点（`\d+寸` / `\d{3,4}×\d{3,4}` / `2.5K|4K`）找起点，**剥掉锚点前面的内容**

第 2 层是被逼出来的：采集池 spec 里屏幕跟显卡用**空格**接
（`RTX 5070 16 寸 2560×1600 IPS 300Hz`），只按 `·` 切会把显卡混进去。

### 4.6 「参数当卖点」判据的词表有三批，第三批最危险

| 批次 | 典型词 | 为什么危险 |
|---|---|---|
| 一 | 高达 / 首选 / 得满分 / 配置很顶 | 夸得直白，好抓 |
| 二 | 细腻 / 通透 / 跟手 / 保值率 / 定位就是 / 不算便宜 | 观感和市场定位，库里没这些字段 |
| **三** | **入门级 / 主打性价比 / 强核弱显 / 是单通道 / 没有独立显卡插槽** | **听起来像内行拆过机。用户最容易信，而库里连"内存通道数""有没有独显插槽"这些字段都不存在** |

第三批是 2026-11-12 实测抓到的，原文：
```
「这是典型的入门级游戏本，主打性价比。」
「属于强核弱显的配置。」「16G 内存是单通道。」
「这台机器没有独立显卡插槽，想升级显卡基本没路了。」
```
四句话，库里**一条依据都没有**。说「高达 240Hz」只是语气问题，
说「没有独显插槽」是在**陈述一个库里不存在的硬件事实**。

### 4.7 判据漂移第五、六次（2026-11-12 页面首屏实录）

同一个洞，两处新变种 —— 都是「只在一处做了，其余路径没做」：

| # | 位置 | 漏了什么 | 实测现象 |
|---|---|---|---|
| ⑤ | `answer_followup()` | caution 没走 `_clean_caution`（另外三条路径都走了） | 问「屏幕怎么样」→「小新 16SE 有双 M.2 硬盘位，同价位更值得看」 |
| ⑥ | `_f_audit()` | 没挂 `_other_model_pitch`（compose / `_intro_model` 都挂了） | 上面那句**没有任何判据拦**，直接上了页面「注意」区块 |

⑤ 有个隐蔽处：`_foreign_fact()` 在这里天然失效 —— 它拿"这台的语料"做双向核对，
而那句 caution 本来就存在这台的语料里。**数据源里混进了别家信息时，出口核对是查不出来的，必须在入口洗。**

⑥ 还有个前缀坑：`_other_model_pitch` 判"是不是在说它自己"用的是 `cur in seg`，
`联想小新 16` 是 `联想小新 16SE` 的子串 → 16SE 冒充 16 被放行。已改成看命中处后面跟的是不是 SE/Pro/数字。

### 4.8 用途和品类打架，系统一声不吭（2026-11-12 用户实测反馈）

用户原话：**「我强调了我要设计和打游戏，他依旧给我推荐 matebook」**。

链路：
```
第一轮「学设计」      → cat=thin
第三轮「我还想打游戏」 → purpose=[design,gaming]，cat 仍是 thin
内核在 thin 里照排    → 首位 MateBook 14 2026（核显）
下一轮追问            → 「这台不适合打游戏」
```
**同一件事，页面推它、回答否它。** 三处根因：

1. `BLOCKER_RULES["gaming"]` 只认文案「没有独立显卡/纯核显」，而采集池的 spec 里不写核显
2. 采集池明明有结构化 `gpu.type="integrated"`，但 `_pool_to_offer()` 没接出来 → 内核不知道
3. 冲突没有任何出口，静默推第一名

修法（三处缺一不可）：
- `_pool_to_offer()` 带出 `gpuKind`/`gpuModel`（**不叫 `gpu`**，避免动 `_gpu_key()` 的去重键）
- `purpose_blockers(gaming)`：`gpuKind=="integrated"` → hard 硬伤，evidence 用显卡型号
- `build_recommendation()` 标 `noGamingInCat` → `_gaming_conflict_note()` **用代码写在推荐前面**（不交给模型）

⚠️ 两个反直觉的点，改之前先读：
- **不能把"spec 没写独显"判成没独显**（test_attack8 有专门对照）。只有结构化字段明标 integrated 才算证据。
- **排序要分情况**：预算内确实有独显机时才按核显降权；一台都没有时只陈述不排序 ——
  否则"数据更全"的机器反而被降权，人工层 22 台没写显卡字段的会白占便宜。

### 4.9 三件事在 2026-11-12 用户试用中被抓出来（都修了，别再退回去）

**① 「要带去教室」不是「换成轻薄本」。**
学生几乎都要带电脑出门，把携带当换品类信号，等于把性能需求扔掉。
- 现象：已定游戏本 + 限电 500W，用户补一句「要带去教室」→ cat 被改回 thin → 首位变 MateBook 14
- 修法：`CARRY_ONLY`（陈述句）+ 已有 `MOBILITY_ASK`（问句）共用"保留 known 品类"分支；
  `CAT_EXPLICIT` 让路（用户明说"我要轻薄本"时照办，但 `_gaming_conflict_note` 会把"打不了游戏"写在前面）
- 携带需求改由 `_carry_note()` 回答：报这台实测 kg + **同品类同预算**的重量区间（不点名别家、不换推荐对象）

**② 专业要求表 `majors.json` 一直没被读过（grep 零引用）。**
10 个专业组，每组带 `req`（ramMin/ramRec/gpu/vramMin）和 `hardGates`。
- 现象：「人工智能专业大一，预算 7000」→ 只抽 purpose=dev → 推 MateBook 14（16G / 核显 / 焊死）
- 表里写的是：16G 底线、32G 推荐、显卡不限、**hardGate = upgrade≥2**（焊死等于四年没后路）
- 修法：`core.match_major()` → slots 带上 `_majorId/_majorName`，把 `ramMin` 喂 `_minRam`、
  `hardGates[upgrade]` 喂 `_minUpgrade`（**不新造机制**，复用已有硬约束 + 放宽兜底）
- 出口必须说清：`_major_note()` 用表里的原文说明要求，并指出这台差在哪个档

**③ 口语问法不带"吗"就认不出来。**
- 现象：「没独显确定够用？」不在 FIT_KW（只收了「够用吗」）→ 判成新需求 → 同一台再推一遍，
  用户原话：「它又推荐一次不回答我问题」
- 修法：FIT_KW 补「够用」「可以吗」；`test_intent` 补三条口语对照片

### 4.10 对付"扛不住乱测"的办法：不靠穷举，靠兜底方向和不变式

用户原话（2026-11-12）：**「没有真正的扛得住我乱测的方法吗」**。

穷举说法是死路 —— 说法无穷，分支有限。这一轮改了两件事：

**① 把"听不懂"的默认动作从「动手」改成「反问」。**
原来 `classify_intent` 判成 `unknown` 之后，`_run` 里没有任何分支接它，
于是一路落到 `build_recommendation` → 把首位再讲一遍。
**默认动作是行动的时候，每句没写过的说法都会表现成"答非所问"。**
现在 `_run` 的 6e：unknown + 槽位没变 + 不是换台/比价 → 直接反问。

**② 加了一条不依赖意图判断的护栏：同一台不许连着推两遍。**
「你说呢」「这两个比一下」这类不一定会被判成 unknown，
所以 6f 单独判：首位 == 上一轮那台、且这轮没改任何条件 → 不重推，改成问一句要做什么。
这条不猜用户想干嘛，只禁止一件不该发生的事。

**③ 新增 `test_fuzz.py`（乱测夹具）—— 这个才是给用户"随便测"用的东西。**
它不预设"这句话该走哪个分支"，只检查 4 条不变量：
I1 同一台连推 / I2 偷偷改品类 / I3 编数字 / I4 回复为空。
说法用「前缀 × 动作」组合随机采样，全部跑一遍，只数违规。
实测：40 条 0 违规；100 条 0 违规；stage 分布 fit 15 / recommend 7 / clarify 14 /
followup 32（其中兜底反问 14）/ exhausted 24 / compare 8 —— 反问没有泛滥。
它还顺手抓到一条真 bug：¥4240.65 被 `verify_answer` 误判成"数字不可追溯"
（`numbers_in` 抽整数 4240，`allowed` 按 round 记 4241），已修。

**④ 说法可以交给模型现场生成**（`python test_fuzz.py --gen 60`）。
手写组合只能撞到你想得到的说法；让模型（temp 0.8，只在测试里开）扮演准大学生写"下一句"，
能撞到「那不行，我要能玩 3A，非要独显！」「那换个不跳闸的，能上 5060 的有没有？」这种。
实测：40 条 0 违规、60 条 0 违规。

**这一轮夹具抓到的两个真问题（都已修）：**
1. **「那换台 RTX4060 的」把 cat 从 thin 改成 desktop** —— 模型把显卡型号当成了台式机。
   修法：`_run` 里 cat 的护栏从"只看移动性问句"扩成
   「**没有品类词（CAT_EXPLICIT）也没有用途词（CAT_PURPOSE_WORDS）就不许改品类**」。
2. **反问太笼统**：「再加点钱上独显」被回成「① 列清单 ② 换一台 ③ 问参数」。
   修法：6e 的反问必须**复述用户原话** + 给贴着这句话的选项（提到独显就换成"只看带独显的机型"）。

**还查不出来的一类（诚实记下来）**：夹具只查"不许发生的事"，
查不出"用户明确要独显、系统只是警告+反问，没有真的按独显筛"。
现在的能力是：能说清"这个预算的轻薄本没有独显"，并问要不要看游戏本；
**没有**"按显存/显卡型号筛机型"的槽位。要做的话是 kernel 新增硬约束，不在这一轮范围内。

⚠️ 结论：**没有"证明扛得住"的方法，只有"持续搜索 + 每次违规都变成一条护栏或一个不变式"**。
乱测夹具的意义是把这件事变成可重复的，而不是靠人一句句试。

## 5. 产品宪法（不可违反，违反即返工）

1. **数字零写权限。** 模型不许生成任何数据里没有的数字。排序、算差值、算百分比全归代码。
2. **"没数据" ≠ "有问题"，也 ≠ "没问题"。** 三者必须分开表达。缺跑分就说缺，不能说低分；没写缺点就说没查，不能夸好。
3. **宁可弃权，不许答错。** 分不清就问，宁可啰嗦，不可答非所问。
4. **判据必须有分辨力。** 每条新判据都要做**对照实验**：拿故意错的输入试它会不会照样通过。**没做过对照的判据不算证据。**
5. **硬伤必须说在前面。** 只夸优点的推荐等于骗人。
6. **不许串台。** 别的机型的信息一个字都不许安到当前这台头上 —— 哪怕那句话在库里真实存在。「说了真话但安错了人」比编造更危险。
7. **没人评价的机器，不许替它评价。** 参数可以报、价格可以报，「高达」「很顶」「值得买」一个都不许说。
8. **如实记录未解决项。** 做不到的写进边界，不许包装成"即将支持"。
9. **判据不许抄第二遍 —— 要抄就抄成一处。**

## 7. §9.1b 的实证：**别重复我犯的错**

我说过「16 台查不到跑分，CPU 不在 bench 表里」。**这句话三处都不对**：

1. **4 台是配件**（DDR5 内存 ×2 / PCIe 固态 / 升级方案），没有 CPU，不该进分母 → 真机器 **12 台**
2. **12 台只涉及 5 个 CPU**，不是 8 个 —— `Ultra7 356H` / `Ultra7-356H` / `Ultra 7 356H` 归一化后是同一个
3. **这 5 个 CPU 在 bench.json 里、R23 分数齐全**，缺的只是 `perfCurrent` 字段。
   bench 36 条里 31 条有分、5 条没有，正好这 5 个 —— **不是没人测，是测了没换算**

按现有标尺内插的估计值（54 / 54 / 61 / 51 / 62，两侧锚点最近只差 1-3 分），
**我没有写进 `bench.json`** —— 那是编数据。估计值和锚点只记在 PRD §9.1b 供参考。

**教训**：报"缺 N 台"之前，先把这 N 台逐条打出来看。分母里混着配件、同一个 CPU 的三种写法、
以及"有数据但没换算"三种情况，混在一起报数字就是不严谨。

## 8. 淘宝数据为什么不进推荐池

145 条，按价格口径过滤后只剩 **1 条**单 SKU。原因：
- 机型名是标题式长串，和京东对不上
- 价格口径有 5 种（券后价 / 卡片价 / 到手价 / 划线价 / 补贴后）
- 品类是推断的，内存列被屏幕尺寸污染过

**结论：不做跨源比价，需要同 SKU 对齐，当前做不到。** 这条已写进 PRD §4.4，
不要试图"先合起来看看"——会在出问题时分不清是谁的锅。
