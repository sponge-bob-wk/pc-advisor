---

## 一、产品概述

**一个面向准大学生的对话式选购助手：用户说清预算和用途，系统给出一台具体机型，并优先说明这台机器在该用途下的短板。**

产品的核心价值不在"信息量大"，而在**可核对**：推荐结果由确定性规则产出，回答中出现的每个数字都能追溯到数据源或用户原话；无法追溯的内容会被出口审计拦截。

首屏即呈现三个关键事实，作为对用户的第一层承诺：

| 93 台 | 22 台 | 4 类 |
|---|---|---|
| 可推荐机型 | 有人逐台写过优缺点 | 覆盖品类 |

> 另外 71 台来自采集渠道：配置、价格、跑分可查，但**没有任何人工评价**。系统对这些机型只陈述参数，不输出"值不值得买"。

---

## 二、背景与问题

准大学生购买第一台电脑时，普遍卡在四件事上：

| 用户困境 | 现有方案的不足 |
|---|---|
| 参数表看不懂 | 电商页只列规格，不解释"这对我的用途意味着什么" |
| 评测难以判断可信度 | 内容多为结论式推荐，缺少可核对的依据 |
| 价格口径混乱 | 划线价、券后价、国补价、到手价并列展示 |
| 推荐与专业不匹配 | 买到不适合本专业软件栈的机型，且事前无人提示 |

前三项是信息呈现问题，第四项是**决策质量问题**——也是本产品的切入点。

---

## 三、目标用户

- **主要用户**：准大学生。预算 4000–8000 元，首次自主购机，不熟悉硬件参数，担心被误导。
- **次要用户**：代为选购的家长。关注"是否够用、总价多少、有无明显短板"。
- **共同特征**：会连续追问、会中途修改条件、对长篇参数表缺乏耐心。

---

## 四、产品原则

以下三条为不可违反的设计约束，贯穿全部功能：

1. **数字零写权限**
   排序、差价、百分比、排名全部由代码计算。语言模型负责把结果转述成人话，不参与任何数值生成。

2. **"没有数据"必须明说**
   缺失数据既不等同于"有问题"，也不等同于"没问题"。例如库内没有游戏帧数实测，系统不会预测"能不能流畅运行"，而是明确说明未收录，并给出去哪儿查。

3. **短板前置**
   只呈现优点的推荐等同于误导。当前用途下的硬伤必须出现在推荐理由之前。

## 五、功能范围

### P0（已上线）

| 功能 | 说明 |
|---|---|
| 对话式推荐 | 支持分批提供条件（预算、用途、是否携带、宿舍限电等），输出 1 台首选 + 2 台候选，含机型、完整配置、到手价。**回答按固定字段呈现**（结论 + 机型/到手价/价格拆解/配置/评价/性能分/内存/重量），模型措辞折叠为「详细说明」 |
| 短板前置 | 针对当前用途标注硬伤，等级分为"硬伤"与"不算强"，前者必须先行说明 |
| 追问不编 | 屏幕、保修、重量、匹配度等追问只引用库内内容；未收录则明确告知，并指出查询位置 |
| 出口审计 | 回答中的数字需可追溯；无出处评价词、库外机型、跨机型串用信息均会被拦截并重写 |
| 数据概览 | 展示库构成、价位段分布、跑分与重量覆盖度；侧栏支持收起 |

### P1（已上线）

- **专业路径**：识别用户专业后，依据专业配置表输出内存底线与推荐档、是否要求内存可加装、显卡是否设门槛，并指认当前机型与该要求的差距。
- **同类对比**：最多三台并列比较价格、跑分、内存、重量与可加装性；缺数据项标注"未知"，不以 0 填充。
- **候选清单**：输出第 2、3 名机型清单，标注是否有人工评价。
- **价格拆解**：页面价 → 优惠券 → 国补 → 到手价，逐步可核对。

### P2（部分上线）

- 重量比较：输出机型实测重量，并给出同品类、同预算区间的重量区间
- 结果深链：`/?q=<问题>` 可直接携带问题打开
- 双机对比按钮（规划中）

## 六、非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 排行榜 / 综合评分 / 雷达图 | 数据中不存在"综合分"字段，任何评分均为人为构造 |
| 帧数、续航时长、返修率、色准 ΔE | 上述维度无实测数据，不做预测 |
| 手机、平板、工作站、macOS 机型 | 不在覆盖范围，遇到即明确拒答，不以其他机型替代 |
| 登录注册、云端同步、移动端应用 | 现阶段聚焦单一场景，不做账号体系 |
| 前端计算 | 排名、差价、百分比一律由服务端计算，前端仅负责呈现 |
| 第三方框架与 CDN 依赖 | 保持单文件、可直接打开 |

## 七、用户流程

1. 打开页面，看到产品说明、三个关键数字与输入框
2. 输入条件（示例：学设计的，预算 5100，要带去教室）→ 得到首选机型、短板说明、到手价与三台对比
3. 追问细节（如"屏幕怎么样"）→ 仅回答该项；无人工评价时明确说明"只报参数"
4. 询问匹配度（如"这台行不行"）→ 给出匹配结论，不擅自更换机型
5. 索取对比或清单 → 输出并列对比或第 2、3 名清单
6. 询问覆盖范围外的品类 → 明确拒答

## 九、技术架构

```
用户输入
   ↓
① 排序内核（core.py）      纯函数，确定性排序，不依赖模型
   ↓
② 组装层（agent.py）       模型仅承担两件事：人话 → 槽位、数据 → 人话
   ↓
③ 出口审计（agent.py）     规则校验：数字可追溯、无库外机型、无凭空评价
   ↓
页面呈现
```

- **前端**：单文件 `index.html`，无框架、无构建流程
- **后端**：Python 标准库 `http.server`，端口 7860，仅绑定本机
- **模型**：本地 Ollama `qwen3.5-4b`，`temperature=0`，仅承担转述
- **数据**：JSON 只读；程序不写入、不修改原始数据

## 十、验收标准

| # | 标准 |
|---|---|
| 1 | 输入完整条件后，输出具体机型、到手价与至少一条短板 |
| 2 | 同一机型经四个入口（首推、追问、匹配度、点名）询问，结论一致 |
| 3 | 询问未收录信息时明确说明缺失，并给出查询途径 |
| 4 | 询问覆盖范围外的品类时明确拒答，不以其他机型替代 |
| 5 | 推荐文案中不出现"高达""首选""性价比高"等无出处评价 |
| 6 | 自动化测试 827 项全部通过；另有 60 条乱测夹具的不变式检查 0 违规；数据一致性检查 0 项异常 |
| 7 | 服务启动后页面可用；模型不可用时降级为规则模板回答 |
