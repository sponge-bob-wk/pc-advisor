## 二、淘宝数据质量：能用的比预期少

### 2.1 价格口径

| 项 | 数量 | 占比 |
|---|---|---|
| 总行数 | 145 | 100% |
| **价格可信（到手价/净价）** | **41** | **28%** |

## 三、为什么比价做不了：三个硬障碍

### 障碍 1：粒度不对等（最致命）

京东侧每台机器是**单一确定配置**：

```
华硕天选 7            ¥6799   spec = R7 H260 · 16G + 512G · RTX 5050 · 2.5K 165Hz OLED
Redmi Book Pro 14     ¥6799   spec = U5-338H · 32G + 1TB（原价 7999）
机械革命 极光 X        ¥9287   spec = U7-251HX · 16G + 1TB · RTX 5060 · 300Hz
```

淘宝侧一条记录对应**一个链接，链接里多个 SKU**。
两者没法一对一。

### 障碍 2：匹配率太低

设了品牌隔离（见障碍 3）之后：

```
淘宝总条数        : 145
能对上京东机型    : 23  (16%)
其中价格口径可信  : 5
对不上的          : 122
```

16% 的匹配率，加上只有 5 条价格可信，样本量根本不够支撑「跨平台价差」这个结论。

### 障碍 3：剩下的匹配仍然是假差价

这是最要命的一点 —— **就算品牌、系列都匹配上了，差价也是假的**：

```
淘宝「天选7 Pro 酷睿Ultra HX」   ¥15252  ←→  京东「华硕天选 7」  ¥6799   差价 +8453
淘宝「天选7 Pro 英特尔版」       ¥15299  ←→  京东「华硕天选 7」  ¥6799   差价 +8500
淘宝「天选7 Pro 英特尔酷睿Ultra7」¥15799  ←→  京东「华硕天选 7」  ¥6799   差价 +9000
```

+8453 元不是渠道差价，是**顶配对基础款**的差价。
用户看到「淘宝贵 8453」，会得出完全错误的结论。

还有一类更隐蔽的：

```
淘宝「小新Air14 2026 酷睿Ultra5 14英寸 AIPC」  ¥6799
京东「联想小新 Air14 柔光版」                    ¥5100   spec 里写着「原价 6799」
```

配置确实对得上，但**淘宝那个 6799 正好是京东的原价** ——
这个 +1699 的「差价」反映的是京东在降价，跟渠道无关。

## 四、顺带修掉的两个真 bug

数据入库这件事本身，暴露了两个原来潜伏的问题。都已修好并有测试。

### bug 1：换数据源直接崩

`meta` 结构两个源不一样：京东有 `updated`，淘宝只有 `collectedAt`/`builtAt`。
`build_recommendation` 里写死 `d["meta"]["updated"]` → `KeyError: 'updated'`。

修法：`core.data_as_of()` 统一出口，按 `updated → collectedAt → builtAt → 未知` 兜底。

### bug 2（严重）：缺字段被当成 0 分，把整张表的排序带歪

原实现：

```python
if mode == "carry":
    return (o.get("portable") or 0) * 33.3      # ← portable 缺失 → 0 分
```

淘宝 41 条 `portable`/`perf` 全空，于是全部拿到 **0 分**。
后果不只是淘宝条目垫底 —— `rank_offers` 拿**整个池子**算 p33/p66 分位数：

| 品类/侧重 | 仅京东 p33 / p66 | 合并双源 p33 / p66 |
|---|---|---|
| gaming / game | 56.0 / **77.0** | 0.0 / **0.0** |
| thin / carry | 66.6 / 66.6 | **0.0** / 66.6 |
| thin / value | 98.1 / 123.8 | **0.0** / 94.1 |

gaming 的 p66 从 77.0 掉到 0.0 —— **所有机型都进最高档，三档分级彻底失效**。
也就是说「没数据的机器」把「有数据的机器」的档位一起带歪了。

这违反项目红线：**「没有数据」不能读成「性能为零」**。
而且 `prices.json` 的 meta 里本来就写着这个口径：

> 「内存条与固态没有 CPU，此项存 null、显示「不涉及」，并从加权里摘除后按比例重新归一，**不判 0 分**。」

代码没照这句话实现。`weighted_score` 里同样是 `(o.get("perf") or 0)`。

修法：
1. `main_score` 算不出来时返回 `None`，不返回 `0.0`
2. `rank_offers` 的分位数**只用真拿到分的**算；缺分的排最后并打 `_nodata`
3. `weighted_score` 缺项**按比例重新归一**，而不是判 0
4. `_nodata` 透传到对外出口（`noPerfData`），上层能如实说「这台查不到跑分」

修复后京东侧排序**逐条比对完全没变**（这是必须验的，见测试 ①②）。

### 附带发现：模型会编「淘宝价」

新判据 `SRC_ASK` 上线前，实测三种编造：

| 提问 | 模型回答 | 性质 |
|---|---|---|
| 淘宝上是不是更便宜 | 「价格往往比 5100 元**更高**」 | 凭空给行情判断 |
| 这个在淘宝卖多少 | 「这台在**淘宝**到手价是 5100 元」 | 把京东价冒充淘宝价 |
| 淘宝和京东哪个便宜 | 答非所问，回避比较 | 该拒绝时没拒绝 |

第二条最危险。而且这三条**全部通过了原有的 `untraceable_numbers` 校验** ——
因为它没编数字，只是给数字换了主语。数字校验管不到「数字是对的、出处是假的」。

修法：新增 `SRC_ASK` 判据 + `compare` 阶段直接拒绝。
分辨力对照 **20 条必须拦住 + 22 条不能误杀 = 42/42**。

## 五、建议（三选一，需用户决策）

### A. 放弃跨源比价（推荐）

淘宝数据只做**单源检索**：用户说「想在淘宝买」，就用淘宝那 41 条给他排。
不报任何跨平台差价。

- 成本：0
- 风险：无
- 代价：双源的价值只剩「多一个渠道的候选清单」

### B. 降级为「只提示有别的渠道，不报差价」

回复里说「我库里只有京东价，淘宝的数据我有一份但不完整，不给你算差价」，
然后引导用户自己去查。

- 成本：0（已实现，就是当前 `compare` 阶段的文案）
- 风险：无
- 代价：用户可能觉得「你都有数据了为什么不算」

### C. 补采集字段后再做

要求淘宝采集时**带上 SKU 级的配置字段**（内存/硬盘/CPU 各一列，且一条记录只对应一个 SKU），
并且价格统一取到手价。

- 成本：要重新采集，且要保证采集侧质量
- 风险：采集质量不可控
- 前提：还得让京东侧也能提供**同款同配置**的对照 —— 目前京东 22 台里，
  能跟淘宝对上的只有 5 条配置可信

**我的判断：选 A。** C 的收益是「能比价」，但要重新采集 + 补齐两边配置粒度，
在这个项目当前的阶段（槽位理解准确率 96%、推荐链路已闭环）投入产出不划算。
A 已经能回答用户 90% 的问题，剩下 10%（跨平台比价）交给用户自己查，
比给一个可能差几千块的假差价安全。

## 六、如实记录：未解决 / 未验证

1. **`match_sources.py` 的匹配仍有误判风险。** 品牌隔离挡住了
   「荣耀 MagicBook Pro 14 ↔ 小米 Redmi Book Pro 14」这类跨品牌误匹配，
   但同品牌同系列不同配置（天选7 Pro vs 天选7）**无法从标题区分**——
   因为没有 SKU 级配置字段。这不算 bug，是数据缺失，无法在代码层修复。

2. **淘宝的品类是规则推断的，不是原始字段。** 145 条里 thin 73 / gaming 67 / desktop 5，
   推断规则写在 `build_taobao.py` 的 `GAMING_SERIES` / `DESKTOP_SERIES`。
   `meta.catInferred = true` 已标记。误判率**没有独立验证** ——
   因为没有人工标注的 ground truth。这是一个已知的盲区。

3. **淘宝那 41 条没有 `perf` 分，所以它们在排序里永远排在京东机型之后。**
   这是有意为之（`_nodata` 优先），但意味着**淘宝单源推荐时，
   所有机器都是无跑分状态**，排序退化成「按价格 + 加权兜底」。
   实测确认：淘宝单源推荐的前 3 名全部带 `noPerfData=True`。
   要真正用起来，得给淘宝机型补跑分（CpuBench 实测或按 CPU 型号映射）。

4. **`SRC_ASK` 是列举式判据。** 42/42 是当前这批说法，换说法可能漏。
   已知边界：「你们和淘宝哪个便宜」这种带「你们」的说法没覆盖到。

5. **跨源比价在代码层已经堵死**（`core.cross_source_delta()` 恒返回拒绝），
   但这是**约定**层面的保护 —— 如果有人绕过它自己写减法，代码不会报错。
   真正的约束是：`load_all()` 默认 `price_ok_only=True`，
   且 `ACTIVE_SOURCE` 默认 `jd`，正常路径拿不到完整的淘宝价格。
