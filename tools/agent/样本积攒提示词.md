# 训练样本积攒提示词（发给执行 Agent 用）

> 用法：把本文件全文发给负责维护本项目的执行 Agent，作为它的常驻附加指令。
> 依据：《LoRA微调可行性评估.md》（2026-11-11）+ `export_lora_data.py` 实跑结果。
> 目标只有一句话：**让未来某天决定训 LoRA 时，数据条件已经备好，而不是从零开始攒。**

---

## 0. 你的任务边界

训练的事**现在不做**。你只做"积攒"——把样本积累嵌进日常工作流，具体是三件事：

1. **修完 bug 后再生样本**（自蒸馏，见 §2）
2. **人工标注工序**（系统不知道自己错了的那类，见 §3）
3. **定期报数**（离立项门槛还差多少，见 §4）

训不训 LoRA 不由你决定，由三个门槛决定（§5）。你只负责让门槛条件在持续逼近。

---

## 1. 四条铁律（违反任何一条，样本作废）

| # | 铁律 | 原因 |
|---|---|---|
| 1 | **答案标签只能来自自己的内核/系统**（自蒸馏） | 外部回答（DeepSeek、别人的对话）带着别人的机型和价格，训进去 = 把编造焊进权重，撞"数字零写权限"红线 |
| 2 | **bug 修复前的系统输出，永远不进训练集** | 「拿修复前的输出当真值训模型，等于把 bug 焊进权重里」——昨天 19 条旧日志一条都不能直接用 |
| 3 | **外部模型只许出题，不许答题** | DeepSeek 对抗测试的输入是好题，但它的回答一个字都不能当标签 |
| 4 | **每条样本必须可追溯**（`_src` 字段记来源） | 将来发现某批数据有问题，要能整批撤掉 |

---

## 2. 日常动作 A：修完 bug 就再生（自蒸馏）

**触发时机**：每次修完一个涉及对话输出的 bug。

**动作**：
1. 把触发该 bug 的**用户原话**收集起来（原话本身永远是好的，错的只是回答）
2. 用修复后的系统重跑这些原话，拿到正确回答
3. 追加进样本池（格式见 §6），`_src` 标 `distill:<bug标识>:<日期>`
4. ⚠️ 重跑时确认服务加载的是**修复后**的代码——不确定就重启 `python server.py` 再跑

**为什么这条最重要**：一条错误样本 → 修完 → 再生 = 一条干净训练对，同时产出两份资产（更稳的代码 + 一条样本），而且对抗测试出的刁钻题越多，这条路的产量越高。

---

## 3. 日常动作 B：人工标注"系统不知道自己错了"的轮次

**背景**：日志的 `issues` 字段只标记"系统自己知道错了"的轮次。**"模型听错了但系统不知道自己错了"**（把追问当新需求重推一遍等）在日志里 `ok:true`、`issues` 空——不会自动打标，必须人工补。

**动作**（每次试用/演示结束后）：
1. 回忆或记录使用中感觉"答非所问"的轮次
2. 用 `python view_log.py 40` 回查：对上原话、槽位、当时的回答
3. 确认是"听错意图"（不是"听不懂但正确反问"——后者是兜底行为，不算错）
4. 把该轮记进 `lora_data/pending_manual.md`，格式：`日期 | 用户原话 | 系统实际反应 | 应该是什么意图`
5. **只记不改**：修复这类问题属于开发任务，走正常流程；修完后这些原话自动进入动作 A 的再生队列

**判断口诀**：系统反问了 = 兜底成功，不记；系统自作主张答了 = 听错，记一条。

---

## 4. 日常动作 C：定期报数

每次收工前跑一次：

```bash
python export_lora_data.py
```

⚠️ **口径消歧**：脚本会打印「缺口 282 条」——那是按**风格对齐 LoRA 的通用参考线 500 条**算的，不是本项目的立项线。本项目立项线以《LoRA微调可行性评估.md》§12 的 **300 条干净样本**为准，报数一律按 300 报（2026-11-12 基线：立即可用 78，缺口 222）。两个口径不要混用，也不要当成谁写错了。

在收工报告里带上三个数字：
- **立即可用样本数**（2026-11-12 实跑基线：78 条）
- **距 300 条立项线的缺口**（当前缺口 222 条）
- 本轮新增（再生 + 人工标注各几条）

顺带一提：脚本还显示有 140 条"只有提问、需重跑补回复"的存量（满打满算上限 218 条）——离 300 还差的新增里，优先把这类补齐，成本低于收集新原话。

---

## 5. 立项门槛（你自己不判断，只报数）

三个条件**同时满足**才轮到训 LoRA（评估文档 §12）：

1. 全量样本上，模型原生槽位失败率 **> 10%**（当前 27 条难样本实测只有 4%）
2. 失败样本**成簇**、有明显规律（如推理型预算表达：「别超我半个月工资」）
3. 纯提示词/正则兜底**解决不了**（先试兜底，成本 20 行代码；训 LoRA 成本 8 小时 + 一次失败调试的风险，顺序不能倒）

报数时顺带报：新增失败样本是否成簇、属于哪类说法。数据到位时用户自然会看到门槛状态。

---

## 6. 样本池格式与位置

- 目录：`E:\电脑涨价分析\tools\agent\lora_data\`
- 主池：`train.jsonl`（`export_lora_data.py --write` 生成/追加）
- 人工标注待办：`pending_manual.md`（动作 B 专用）
- 每行一条 JSON：

```json
{"messages": [{"role": "user", "content": "用户原话"}, {"role": "assistant", "content": "自己内核生成的正确回答"}], "_src": "distill:<bug标识>:<日期>", "_ts": "<ISO时间>"}
```

- 去重规则沿用脚本内置的：同一句归一化后只留第一条

---

## 7. 明确不许做的事

- ❌ 不训任何 LoRA（训练动作等用户明示启动，且门槛满足）
- ❌ 永不训"决定推荐哪台"的 LoRA——这条没有期限，是**永远**
- ❌ 不为了凑数把攻击测试用例（「六千万像素」「12,000」这类人造边界输入）混进真人样本池
- ❌ 不改 `data\*.json`（零写权限，与样本积攒无关但重申）
- ❌ 不把训练样本写进任何对话回复给用户看——样本池是内部资产

---

## 8. 一句话版本

> **每修一个 bug 就用原话再生一条样本，每次试用后人工标记系统不自知的错误，每次收工报三个数；答案只准自己内核出，外部模型只准出题；训不训等门槛，你只管把 78 攒到 300。**
